# Link：关系语义、前后顺序、自动反向关系与双向查询

状态：Ontology 设计文档，尚未编码。Link 自动生成反向关系、支持正向和反向查找为已明确要求；Schema 间还需覆盖组合、上下级、继承等关系，以及同一产线内设备从前到后的顺序。下文的关系语义分类、顺序/上下文、约束、方向视图、接口及存储方案为候选设计，尚未验证；扩展关系清单不等于全部进入首期。本文统一维护实例关系语义、自动反向关系、基数、查询协议、存储候选及验收；示例是候选格式。

## 1. 用途与边界

Link 描述同类或不同类实体如何关联，Metadata 的 link 模块管理一份当前关系定义；Data 管理实际关系事实、读写约束与路径查询。端点仅按稳定 ID 引用 [Schema](Schema.md) 的当前定义，不设置业务 version，也不复制端点的字段规则。

组织归属和分类内跨类型名称唯一性见 [组织与隔离](../组织与隔离.md)。Link、两端 Schema 及关系实例必须属于同一租户；允许引用同租户其他分类的 Schema，不能跨租户连边或遍历。

当前设计范围包括关系定义维护、自动正反向入口、关系实例增删、端点及基数校验、正反向邻接查询、多级固定路径、关联过滤、去重和分页，并覆盖租户权限、分表端点定位、计算属性依赖及定义生效。原有这些通用能力可以记录关系事实，但不能仅凭“包含”“上级”“下一台”等名称就保证组合生命周期、独占归属、无环或业务顺序；补充规则见第 2 节。继承是 Schema 的类型关系，由 [Schema](Schema.md) 维护，不能用一条普通实例 Link 代替。具体实现和性能均待后续开发验证；排序所需的最小关系元数据及通用关系属性为新增候选，不定长遍历和图算法尚未纳入已确认基础范围。

## 2. 定义结构与业务规则

创建一份 Link 后，系统自动提供正向 `out` 和反向 `in` 两个方向的关系入口，并支持合并相邻方向的 `both` 查询，以及多级路径和关联过滤。关系定义应描述名称、两端 Schema、正反向名称、1:1／1:N／N:1／N:M 基数、重复边规则和删除行为。

例如：`工单 --使用设备--> 设备 --所属产线--> 产线 --所属车间--> 车间`。既可以从工单查车间，也可以沿反向关系查某车间内的相关工单。

查询协议需要区分固定路径和不定长遍历，明确路径端点、每层过滤、去重、分页以及返回实体、关系或路径的方式。限制最大跳数、扫描量、结果数与执行时间，防止关系分支导致路径数量膨胀。四跳是候选测试范围，尚未确定为产品上限。

首期建议实现有界固定路径；不定长遍历、可达性、最短路径及图算法是否进入首期仍待确认，不能因支持 Link 就宣称支持全部图查询能力。存储方案见下文，性能条件统一见 [性能与容量](../性能与容量.md)。

| 内容 | 含义 |
| --- | --- |
| id、tenantId、categoryId、groupId | 稳定关系标识及组织归属 |
| name、labels | 主展示名及多语言显示信息 |
| source、target | 两端 Schema 的稳定 ID 引用 |
| forwardName、reverseName | 正向与自动反向入口的展示名称；程序查询使用 Link ID 与方向，不以名称解析关系 |
| cardinality | 1:1、1:N、N:1 或 N:M，以 source → target 为基准，反向视图自动交换基数 |
| relationKind | 候选语义：association（普通关联）、aggregation（聚合）、composition（组合），默认普通关联 |
| topology | 独立的候选拓扑约束：unrestricted、tree、dag，以及直接前后边使用的 chain；有序成员集合不直接等于 chain，不替代基数和归属约束 |
| ordering、context、edgeProperties | 新增候选：有序成员配置、产线/路线等作用域、关系实例属性定义；最终字段结构待定，实例属性不写进 Link 定义作为全体实例共用的值 |
| constraintScope | 新增候选：明确基数、重复及拓扑的检查范围；前后链可选择 context，具体上下文在每条关系事实和查询步骤中携带；不能覆盖组合的全局归属约束 |
| symmetry | 新增候选：默认有向；业务对称关系须明确端点可交换性、规范化及查询规则，自动反向入口本身不表示对称 |
| sourceTypeMatch、targetTypeMatch | 候选端点匹配：默认 exact；显式 includeSubtypes 才接受该端点 Schema 的具体子类型，须完成类型及存储能力校验 |
| duplicatePolicy、onDelete | 重复边和端点删除的处理，发布前须明确 |

### 关系语义与覆盖范围

以下是针对新增关系需求的候选规则，不代表现有系统已具备这些约束。关系语义和拓扑分别声明，例如“设备组合部件”可以同时选择 composition 和 tree；仅设 tree 不自动表示拥有部件或级联删除。

| 关系 | 示例与含义 | 通用 Link 之外需要补充的规则 |
| --- | --- | --- |
| 普通关联 association | 工单使用设备、设备位于车间、设备依赖电源 | 复用端点、基数、双向查询；“依赖”等业务名称本身不启用自动调度、删除或无环规则 |
| 聚合 aggregation | 设备集合收录设备，整体和成员可独立存在 | 成员能否被多个整体共享由基数决定；移除成员不删除实体，删除整体不推断级联删除成员 |
| 组合 composition | 设备由部件组成，部件受整体管理 | 跨组合 Link 的独占归属、归属图防环、整体/部件生命周期及受控转移 |
| 上下级 tree / dag | 部门上下级、设备层级；树单父、DAG 可多父 | 定义约束范围、父节点数量、防环、换父及有界祖先/后代查询 |
| 继承 is-a | 电机是一种设备 | Schema 定义级的基类、有效字段及类型匹配；详见 [Schema](Schema.md)，不为每个实例保存“继承边” |

### 扩展关系清单与配置维度

除上述结构关系，还应检查以下业务关系。它们大多复用 association，不为每个业务动词增加一个互斥的 relationKind；Link 的稳定 ID 定位具体谓词，名称仍只展示。按需组合语义、拓扑、排序、对称性、上下文及有效时间，只有明确声明且已认证的约束才自动执行。

| 关系族 | 业务例子及自动反向入口 | 需要明确的语义 |
| --- | --- | --- |
| 顺序、紧邻 | 上一工位/下一工位，先于/后于 | 区分直接相邻和任意先后；序列限定在产线/路线等上下文，不能用设备 ID 或创建时间替代业务顺序 |
| 流向、上下游 | 供给/接收，流向/来自 | 允许分支、汇合、并行和回流；物理流向、工艺执行顺序、页面排序分别声明，有回流时不能强制当作 DAG |
| 依赖、先决 | 依赖/被依赖，前置条件/后续受影响项 | 指明依赖的对象、条件及作用域；要求无环时才选择 DAG，记录依赖不自动触发计算、调度或控制 |
| 连接、邻接 | 连接/连接，相邻/相邻 | 电气、管路、机械、通信分别定义，可细化到端口；区分有向输送和对称连接，连接或相邻本身不传递 |
| 空间位置 | 位于/容纳，左侧/右侧，上方/下方，接触/接触 | 指明坐标系、观察方向、精度及适用对象；空间包含不自动表示组合所有权，空间前方也不自动等于工艺上游 |
| 时间区间 | 早于/晚于，紧接/被紧接，重叠/重叠，期间内/期间包含 | 时间点/区间及边界、时区和空值语义明确；由事件时间计算还是人工记录须选定，时间重叠不表示可以并行执行 |
| 职责、作用、资源 | 控制/受控，测量/被测，驱动/被驱动，使用/被使用 | 记录业务角色、资源需求及条件；“控制”关系不授予权限，“使用”关系不自动占用或锁定资源 |
| 等价、对应、相似 | 等价/等价，映射到/映射自，相似/相似 | 区分同一对象、业务等价、编码映射和相似；保留不同内部 ID，不自动合并实例或推广传递性 |
| 替代、备份 | 可替代/可被替代，备份/被备份 | 替代可有方向，需条件、能力、优先级及适用范围；A 可替代 B 不推出 B 可替代 A 或 A 可替代 B 的所有替代项 |
| 互斥、兼容 | 互斥/互斥，兼容/兼容 | 声明产品、时间及资源等条件；未记录兼容不能推断为互斥，关系声明不自动执行排产或联锁 |
| 来源、派生、生产消费 | 来源于/派生出，生产/由其生产，消耗/被其消耗 | 保留来源、批次、数量/单位及必要的执行记录；区分溯源事实与计算依赖，不凭有边就承诺自动重算 |

同一批实体可以同时具有多种关系。例如设备既属于产线，又连接电源，并在特定产品路线上先于另一设备；这些 Link 使用各自稳定 ID 和约束，不能共用一个笼统的“相关”关系后靠名称猜含义。是否对称、可传递或需要级联也不能从中文动词自动推断。

### 前后顺序：有序成员、直接相邻与工艺路线

产线设备从前到后建议先表达为一个有上下文的有序成员集合。例如某条产线的某条路线为 `上料机 → 清洗机 → 检测机 → 包装机`。这表示完整线性顺序；“清洗机的下一台”是检测机，“清洗机后面的所有设备”则还包括包装机，两类查询不能混用。

候选优先方案是在“产线/路线 → 工位或设备”的成员关系实例上保存受控排序键，按租户、Link ID、具体产线/路线身份及排序键查询。排序值属于这一次成员关系，不放在设备的全局属性上；同一设备在不同产线/路线中可处于不同位置。若同一设备在同一路线中出现多次，建议建立有独立 ID 的“工位/工艺步骤/出现位置”Schema，位置引用设备，避免端点对去重丢掉某次出现。

| 表达方式 | 权威事实与查询 | 适用边界 |
| --- | --- | --- |
| 有序成员集合（优先候选） | 维护成员及排序键，按范围有序读取；上一项/下一项由相邻排序位置计算 | 展示、调整产线工位顺序及完整列表；成员 Link 的反向仍是“所属产线/路线”，上一项不是这个反向入口 |
| 显式直接前后边（另一候选） | 保存 A → B 的“直接后继”事实，反向自动为 B → A 的“直接前驱”；chain 在同一范围内限制每个位置至多一前一后且无环 | 邻接本身就是业务事实时使用；空/单节点须有成员登记，多节点还需检查所有成员属于同一条链，不能只验证局部 1:1 就宣称完整序列 |
| 工艺路线/流向图 | 保存步骤间的流向及分支条件；有界查询上游/下游 | 分支、汇合、多路径、返工或回流；可选 DAG 或显式允许环，不把一个排序号当作流程执行模型 |

同一个范围只选一种权威顺序表达；另一种若作为索引或导航加速，必须只读派生并随真实变更维护，不允许排序键与 next/previous 边各自编辑。序列范围内的基数和排序唯一性按上下文约束，不能把每条路线最多一个后继误设成设备在整个租户只能有一个后继。前后边只连接同一范围的合法成员，自环、跨路线连边和同一位置重复排序应按契约拒绝。

插入、移动、交换、删除成员及跨路线移动须在可覆盖的本地事务中更新顺序，校验权限、完整性、依赖并提交一次真实变更；删除成员不自动删除设备或将工艺流程重新接通。自动并发校验或范围锁避免两人拖动相互覆盖，内部凭证不引入业务 version。有序列表的起止位置、正反序、上一项/下一项及前面/后面查询都携带范围，支持稳定分页；顺序变化后旧游标按快照契约继续，或明确失效重查，不能悄悄漏项/重项。

排序键可评估整数、稀疏编号或受控排序字符串，必须定义比较规则、并发分配及必要重排；不预设每次移动都全量更新或遍历全图。候选访问索引为 `(tenant_id, link_id, scope_id, order_key, membership_id)`，scope_id 对应已校验的具体范围身份；每 Link 独立表时可省略 link_id，排序唯一约束另按范围建立。顺序查询逐范围裁剪且不逐设备取 Metadata；权限过滤后不能将被隐藏节点两侧误称为直接相邻，也不暴露隐藏邻居身份。

#### 前后关系的定义、实例与调用示例（候选）

Link 定义回答“哪两类对象可以怎样关联，按什么规则约束”，关系实例回答“具体哪两个对象在什么上下文中关联”。大多数前述业务关系可这样表达，并复用受控查询；只写展示名不能启用对应约束。继承依旧由 Schema 管理，业务调度或控制动作也不由一条 Link 自动执行。

为直接说明正向与反向访问，本例选择“显式直接后继边”作为这一范围的权威顺序，产线 L1 的设备为 `上料机 A → 清洗机 B → 检测机 C → 包装机 D`。同一设备在此产线只出现一次；重复出现时按前述规则改用工位/步骤实例作为端点。本例和前面的有序成员方案是两种候选表达，同一范围选定一种事实来源。

**定义阶段**：先有“产线”和“设备”两个 Schema，再创建一份“产线设备直接后继”Link。以下为候选定义片段，省略租户/分类/分组等共同必需信息；字段不是已冻结的 API。context 中声明的成员 Link 表示“产线 → 设备”，本例允许设备参与不同产线，因此其基数为 N:M，重复成员拒绝；完整链校验使用这份成员登记，不只检查已有前后边。

```json
{
  "id": "c4828011-d383-47bc-ad11-125c097f3511",
  "name": "产线设备直接后继",
  "source": {"id": "09228a4b-f3e8-4a3b-9581-a95d29bd5d2b"},
  "target": {"id": "09228a4b-f3e8-4a3b-9581-a95d29bd5d2b"},
  "forwardName": "下一台",
  "reverseName": "上一台",
  "relationKind": "association",
  "cardinality": "1:1",
  "topology": "chain",
  "context": {
    "schemaRef": {"id": "50d140c3-76af-4a9d-92fb-2c116cb9e511"},
    "required": true,
    "membership": {
      "linkRef": {"id": "23dbd0a1-c628-4ca0-a504-64504c088332"},
      "direction": "out"
    }
  },
  "constraintScope": "context",
  "duplicatePolicy": "reject",
  "onDelete": "restrict"
}
```

这里两端都是设备 Schema，声明“一台设备可直接在另一台设备之前”；context 的类型为产线 Schema。1:1 表示同一产线内每台设备至多一个直接前驱和一个直接后继，允许首尾；不是设备在整个租户内只能有一个后继。生效后设备 Schema 可发现同一 Link 的 out“下一台”和 in“上一台”两个入口；成员 Link 的反向“所属产线”是另一项导航。

**数据阶段**：产线和设备实例可先创建；在本例的单链模式下，四条成员事实与三条直接后继事实应在一次受控事务中一起建立，不能先提交不完整成员链，再逐条补边。下表 M1～M4、E1～E3、L1、A/B/C/D 均为稳定 ID 的简写，名称只帮助阅读。

| 关系实例 | 成员 Link ID 的简写 | source：产线 | target：设备 |
| --- | --- | --- | --- |
| M1 | L_MEMBERS | L1 | A：上料机 |
| M2 | L_MEMBERS | L1 | B：清洗机 |
| M3 | L_MEMBERS | L1 | C：检测机 |
| M4 | L_MEMBERS | L1 | D：包装机 |

L_MEMBERS 指上述成员定义 `23dbd0a1-c628-4ca0-a504-64504c088332`，回答“这条产线有哪些设备”；下面另一份 L_NEXT 定义 `c4828011-d383-47bc-ad11-125c097f3511` 回答“在这条产线中谁紧接谁”。两份 Link 描述不同业务事实，成员登记不另存一份排序；本例的唯一顺序来源仍是 L_NEXT。

| 关系实例 | Link | 上下文 | source | target |
| --- | --- | --- | --- | --- |
| E1 | 产线设备直接后继的 ID | L1 | A：上料机 | B：清洗机 |
| E2 | 同一 Link ID | L1 | B：清洗机 | C：检测机 |
| E3 | 同一 Link ID | L1 | C：检测机 | D：包装机 |

```json
  "linkRef": {"id": "c4828011-d383-47bc-ad11-125c097f3511"},
  "source": {
    "schemaRef": {"id": "09228a4b-f3e8-4a3b-9581-a95d29bd5d2b"},
    "entityId": "dc66a390-11e3-40c1-a998-000000000002"
  },
  "target": {
    "schemaRef": {"id": "09228a4b-f3e8-4a3b-9581-a95d29bd5d2b"},
    "entityId": "dc66a390-11e3-40c1-a998-000000000003"
  },
  "context": {
    "schemaRef": {"id": "50d140c3-76af-4a9d-92fb-2c116cb9e511"},
    "entityId": "ab0bfb4e-9ee8-4c29-b726-5ec0b1ee6101"
  }
}
```

E2 已同时支持 B 查下一台 C 和 C 查上一台 B，无需再保存 C → B 的另一条关系事实。其他产线若有不同顺序，保存各自产线上下文的事实，既不改 Link 定义，也不覆盖 L1 的事实。建立、移除成员与完整链维护须协调校验；空产线和只有一台设备的产线即使没有前后边，也能由成员登记表达。

**查询整条产线的设备**：从产线 L1 沿成员 Link 的 out 一跳，批量得到 A、B、C、D；不需要从第一台设备逐台查询下一台。以下为候选请求，分页字段仍待协议确认。此处调用者有示例对象的合法权限。

```json
{
  "start": {
    "schemaRef": {"id": "50d140c3-76af-4a9d-92fb-2c116cb9e511"},
    "entityId": "ab0bfb4e-9ee8-4c29-b726-5ec0b1ee6101"
  },
  "path": [{
    "linkRef": {"id": "23dbd0a1-c628-4ca0-a504-64504c088332"},
    "direction": "out"
  }],
  "return": "entities",
  "page": {"limit": 100}
}
```

Data 按租户、成员 Link、source=L1 读取一页成员，再批量定位和读取设备；空产线返回空集合，单设备产线也能返回该设备。一次返回的是受限的一页，结果要说明是否还有下一页；客户端按游标读完才得到完整集合，不能固定 limit 后就称“全部”。成员接口不承诺工艺顺序；若要求从前到后，候选序列读取接口在一致快照内批量读取该范围的成员及后继边，检查首尾、单链和成员覆盖后按链返回，并定义排序分页契约。不得逐设备远程请求下一台，范围过大或链不完整时不得假报完整成功。

**查询某设备的前一个设备**：例如“在 L1 查询清洗机 B 的上一台”使用以下候选请求。它沿用第 3 节固定路径的 start/path 结构，新增本层必需的 context；查询的是 L_NEXT 的反向，与成员 Link 不是同一次导航。

```json
{
  "start": {
    "schemaRef": {"id": "09228a4b-f3e8-4a3b-9581-a95d29bd5d2b"},
    "entityId": "dc66a390-11e3-40c1-a998-000000000002"
  },
  "path": [{
    "linkRef": {"id": "c4828011-d383-47bc-ad11-125c097f3511"},
    "direction": "in",
    "context": {
      "schemaRef": {"id": "50d140c3-76af-4a9d-92fb-2c116cb9e511"},
      "entityId": "ab0bfb4e-9ee8-4c29-b726-5ec0b1ee6101"
    }
  }],
  "return": "entities"
}
```

| 使用需求 | 指定的查询 | 预期业务结果 |
| --- | --- | --- |
| B 的下一台 | 从 B 沿该 Link 的 out 一跳，context=L1 | 检测机 C |
| B 的上一台 | 从 B 沿同一 Link 的 in 一跳，context=L1 | 上料机 A |
| B 后面的第二台 | 同一 L1 上下文连续两跳 out | 包装机 D |
| B 前后直接相邻设备 | 从 B 用 both 一跳，context=L1 | A、C，结果分别说明 in/out；both 本身不保证产线排序 |
| D 的下一台 | 从 D 沿 out 一跳，context=L1 | 合法空结果，表示已到末尾；不能与邻居被权限隐藏混淆 |
| B 后面全部设备 | 使用另行认证的有界后继遍历，携带范围、预算及终止条件 | 在足够预算下返回 C、D；不等于一次 out，也不把两跳固定路径的终点当作全部结果 |

Data 解析当前定义、上下文、成员身份及权限后，按租户、Link、L1、起点和方向的索引访问同一份边事实，再批量读取合法结果；调用者不用知道物理表或分表位置。后继遍历不是现有固定路径接口自动具备的能力，未认证时可明确请求有限层数的路径，不默认执行无限追踪。前台可先发现当前 Schema 的方向入口再用稳定 Link ID 调用，不按“下一台”展示名解析。

对于上面的 in 查询，候选关系库访问条件是当前租户、L_NEXT、context=L1、target=B，读取对应边的 source 得到 A；out 则按同一范围的 source=B 读取 target 得到 C。前后索引还包含实际 Schema 身份及必要的 context，不扫描整个租户的设备。结果中的字段、关联设备及真实邻居均按权限读取；未授权或未完成读取不能伪装成真实首尾。

**保存设备关系**：业务设备实例由实例接口维护；关系保存接口只操作成员和前后事实，既不把设备字段塞进 Link 定义，也不每次新建一份 Link。以下为候选“设置范围内完整设备序列”的命令正文，不是已实现的 HTTP 路由。为减少重复，orderedMembers 中的 entityIds 共用所声明的具体 schemaRef；这些都是真实实例 ID。本例仅面向已认证、可在同一本地事务维护的范围。

```json
{
  "membershipLinkRef": {"id": "23dbd0a1-c628-4ca0-a504-64504c088332"},
  "sequenceLinkRef": {"id": "c4828011-d383-47bc-ad11-125c097f3511"},
  "scope": {
    "schemaRef": {"id": "50d140c3-76af-4a9d-92fb-2c116cb9e511"},
    "entityId": "ab0bfb4e-9ee8-4c29-b726-5ec0b1ee6101"
  },
  "orderedMembers": {
    "schemaRef": {"id": "09228a4b-f3e8-4a3b-9581-a95d29bd5d2b"},
    "entityIds": [
      "dc66a390-11e3-40c1-a998-000000000001",
      "dc66a390-11e3-40c1-a998-000000000002",
      "dc66a390-11e3-40c1-a998-000000000003",
      "dc66a390-11e3-40c1-a998-000000000004"
    ]
  },
  "ifMatch": "<本次读取返回的范围状态凭证>",
  "idempotencyKey": "1e4bfcde-aef2-4fb8-a6c8-ef854af87dd6"
}
```

该命令表达“把 L1 在这两份 Link 下的完整成员及顺序设置为 A、B、C、D”，属于明确的范围替换，不是将一页查询结果追加保存。被移出的成员和该范围相关前后事实会移除，设备实体及其他产线关系保留；调用者须持有完整范围的编辑权限并基于完整读取提交，服务端不能把客户端可见的一小部分当作整个范围。

候选处理顺序：解析两份当前 Link，验证 sequence.context 指定的成员定义与 membershipLinkRef 一致；校验范围、设备存在/类型/同租户、权限、重复和预算；在范围锁或等价并发协议下核对状态凭证，计算最终图及差异；对完整成员覆盖、一前一后、防环和其他约束校验；在同一本地事务内提交成员差异、后继差异、幂等记录和真实变更 outbox。当前 Link 在校验到提交之间变化也须拒绝过期执行。首次为空范围也应先取得该范围状态凭证；凭证只防覆盖，不引入业务 version。

首次保存本例产生 M1～M4 四条成员事实和 E1～E3 三条后继事实，反向入口不产生额外事实。未改变的关系保留原 edge ID；被替换的关系移除并为新关系分配 ID。相同幂等键与相同命令重放返回原操作结果，不重复写边或发事件；同键不同命令拒绝。状态冲突要求重读再编辑，失败全部回滚；超过同步事务或范围预算时拒绝或进入另行明确的受控流程，不能拆批提交后假报原子成功。

对普通无单链完整性要求的 Link，可提供按端点创建或按 edge ID 删除的通用关系接口；本例的成员增删、插入设备和换位需要受控序列命令，避免独立提交单条边破坏完整链。输入有序 ID 列表是本次保存意图，不额外保存成第二份可编辑顺序。若选择有序成员模式，同类命令改为维护成员和排序键，前后导航只读派生，不能又写一套可编辑的 L_NEXT 事实。

**调整阶段**：将 B 移到 C 后面，目标变为 `A → C → B → D`。受控重连操作在同一事务中移除原 A-B、B-C、C-D，建立 A-C、C-B、B-D，并对最终图验证成员覆盖、单链、防环、基数及并发条件，回滚不暴露半条链。设备 ID 和 Link ID 保持不变，后续正反查询立即按已提交的新顺序读取；不因调整顺序创建定义 version。若采用有序成员作为权威，则通过移动成员调整排序键，前后导航只读派生，具体规则沿用上文。

### 对称、推导、上下文及关系属性（候选扩展）

自动反向与业务对称是不同维度。“供电/被供电”有两个方向入口，事实仍有方向；“相邻/相邻”才可能是对称关系。对称候选先限定 association 的对等端点，声明允许的可交换类型及规范化身份键，A-B 与 B-A 不重复落边。数量约束先评估对等的 1:1 或 N:M，1:1 按一个实体在任一存储端的全部邻居计算，不能套用有向两侧各自唯一索引。对称模式下 out/in 两个方向视图应提供等价的合法邻居集合，both 去重；存储端点的规范顺序不能使其中一侧漏查。第 3 节的 source/target 定向规则默认用于有向关系，对称模式只有在端点、写入、权限、基数和查询语义完整认证后开放。

配置维度需要兼容性校验：组合/聚合的整体与部件角色、tree 的父子、chain 的前后及有向 dag 都有明确方向，不与业务对称模式混用；多分支流向不能声明为单链。反向入口、对称性、拓扑及排序分别描述不同规则，不能靠增加一个“关系类型”值绕过其他约束。

直接事实与推导结果分开。例如 A 直接后继 B、B 直接后继 C，可查询 A 先于 C，但不能把 A-C 又保存成“直接后继”；A 邻接 B、B 邻接 C 也不推出 A 邻接 C。候选派生关系应显式声明来源、推导范围、权限、预算及新鲜度，不能任意写入或自动持久化完整传递闭包。自动反向入口仅是同一事实的方向视图，不新增一份业务事实；本轮不引入通用 OWL 推理或任意规则引擎。

关系实例可能需要顺序、距离、长度、数量、占比、条件、优先级、端口及有效时间等属性。候选通用关系属性复用 [Schema](Schema.md) 的稳定字段 ID、类型、单位、Enum、权限和索引校验规则，但字段声明归当前 Link 定义，具体值归边事实；展示名不作为属性或上下文引用键。首先区分排序必需的最小元数据和可选的通用属性能力，不能把尚未认证的所有属性都算作已有支持。

上下文应引用同租户的真实产线、路线、产品、班次等稳定实例身份；重复边、基数、查询、缓存及派生依赖均按声明范围处理，任一方向写入不能丢掉上下文。复杂的多人/设备/班次/职责等多元事实，或自身具有状态、生命周期的安装记录、工艺步骤，建议提升为独立业务 Schema 再用 Link 关联各角色，避免拆成多条二元边后丢失同一次业务事实的对应关系。

关系有效时间表示“何时成立”，与创建时间、事件发生时间和定义生效时间分别保存，不是恢复业务定义 version。时态扩展需明确区间边界、时区、开放端点、当前/指定时点查询及重叠规则；例如“某设备何时安装在哪条产线”可保存不同业务区间。独占或基数约束须检查相关区间是否重叠，不能只看当前时刻。未具备区间约束和查询能力时只开放当前关系，不宣称已支持时态关系。

类型继承仍归 Schema；状态值可使用 [Enum](Enum.md)，允许的状态迁移及副作用归 [Action](Action.md) 的行为契约；单纯数值比较、按坐标/时间计算的关系可作为受控查询条件。只有需要独立维护的关联事实才保存为 Link，避免重复保存可由权威字段直接计算的结果。物理流向、空间关系、替代、资源等扩展的优先级仍待业务场景确认。

### 组合：独占归属与生命周期

候选约定 source 为整体、target 为部件，反向入口自动表达“所属整体”，方向仍按同一 Link ID 导航。组合基数只能选择 1:N 或 1:1；单个部件在同一租户的全部组合关系中最多有一个直接整体，不能通过另一条组合 Link 或不同方向重复认领。部件作为整体继续组合下级时，沿所有组合 Link 构成的实例归属图必须无环，禁止自我组合；Schema 端点图出现循环不等于实例图已经成环。

建议 Data 以租户、部件的实际 Schema ID 和实例 ID 维护统一归属登记，与边事实、实例变更及 outbox 在已认证的本地事务中提交。每条 Link 自己的 target 唯一索引不足以保证跨 Link 的独占归属；并发认领、转移和整体删除还需要统一锁或等价串行化协议，不能先查再写。跨源或无法覆盖这些记录的事务布局暂不承诺组合写入能力。

删除关系与删除部件实体是不同操作。建议整体删除默认 restrict：存在部件先拒绝；明确配置整体级联删除时，预览删除范围并检查其他入边、权限、计算依赖、分表及执行预算，不能因 1:N 自动级联。删除部件也必须按它的其他关系约束处理，不能反向删除整体；级联协议须区分删除哪一端，不能用一个无方向的 cascade 值推断全部行为。超出单事务预算的删除需另行设计可恢复的受控流程，不能逐页删除后声称整体原子成功。

部件是否必须始终有整体、是否允许待装配状态须单独声明并在生效前校验，不从最大基数推断最低数量。声明必有整体时，创建部件与关系应同事务，单独解除关系不能留下孤儿；换整体按受控转移执行，保留部件 ID，重新检查独占、防环和其他约束。转移不自动搬迁物理表；若用于关联来源分表，沿用 Schema 的创建时快照或显式维护搬迁规则。

### 上下级：树、DAG 与换父

候选约定 source 为父、target 为子；自动反向入口提供查父，正向提供查子。tree 表达允许多个根的森林：每个子节点至多一个父节点，基数限于 1:N 或 1:1；dag 允许多个父节点，但同样禁止自环及有向环。普通 unrestricted 关联可成环，而 composition 无论是否另设 topology 都必须满足组合归属图无环。

未声明额外上下文时，候选默认拓扑检查范围为同租户、同一 Link 的全部实例边；声明产线/路线等上下文时，按同租户、Link 和已校验上下文中的全部成员及边检查。跨多条 Link 组成统一层级时，必须显式登记共同约束范围，并验证端点可连接及合并图上的父数量与防环规则，不能只分别检查每条 Link。组合的跨 Link 独占及防环始终按上一小节执行，不能用不同上下文绕过部件唯一归属。约束检查覆盖该范围内完整事实，不受调用者可见邻居子集影响，对外错误仍遵守权限边界。

创建边、反向写入、换父、导入及批量操作共用同一校验。A 挂到 B 下、B 同时挂到 A 下等并发场景，须由约束范围的锁或等价串行化协议阻止，单次查无环后插入并不充分。换父在支持的本地事务内删除原边、验证新父不在后代中并建立新边；涉及组合时一并更新归属登记。若使用路径、深度或闭包加速，必须定义事务维护或明确的新鲜度，不能读取过期路径绕过约束。跨源强一致层级维护须另行认证。

直接父子查询复用 out/in；祖先、后代、子树查询属于新增候选能力，需明确最大深度、扫描/分支/结果及时间预算，DAG 返回节点还是不同路径也必须显式选择。可按后端能力评估递归 CTE 或应用层批量迭代，不默认维护完整闭包，也不将这些查询等同于任意图算法。层级结构本身不触发级联删除或权限继承。

### 继承端点与具体类型

Link 默认只接受定义中精确的端点 Schema。显式启用 includeSubtypes 后，才按当前 Schema 继承图接受相应端点的具体子类型；Metadata 在合法具体子类型侧也派生可发现的方向入口，无需复制 Link 定义或边。写入、路径连接、基数、归属登记和返回结果均保留实际具体 Schema ID，不能将所有子类型实例伪装成基类实例。

查询基类端点和子类型端点都须先校验当前类型匹配及实体权限；子类型的加入、移除或继承链变化会改变可用端点集合，需重新检查现有边、依赖、方向发现及缓存。跨具体表的查询、分页和约束未认证时，拒绝该扩展，不能只接受写入却漏掉反向查询。类型继承不自动继承访问权限、Action/Function 绑定或其他 Link 的关系事实。

## 3. 自动反向 Link 与双向查找

### 自动生成及生命周期

建议将一份 Link 的正反两个方向表示为自动派生的方向视图：正向位于 source Schema 的可用关系中，反向位于 target Schema 的可用关系中。两者都可发现、查看和用于查询；即使暂时没有关系实例，也应能从 Schema 的关系列表看到入口。保存草稿可预览两个方向，正式生效后同时向业务开放，无需用户再创建反向定义或逐条补反向边。

每个方向视图返回 linkRef、direction、起点/终点 Schema、展示名称和该方向的基数。稳定定位键为 `(linkRef.id, direction)`，共同引用同一份当前 Link 定义和边事实；反向视图不分配可独立编辑、生效或删除的第二份业务定义。方向描述可按当前定义派生或缓存，使用前按当前态规则校验，不维护两份可能不同步的权威正文。

例如 `工单 --使用设备--> 设备` 生效后，自动在工单侧提供“使用设备”，在设备侧提供“被工单使用”。建议 forwardName 未填写时使用 Link.name；reverseName 未填写时生成“〈正向展示名〉（反向）”作为默认名称，允许在同一 Link 草稿中修改反向展示名。系统只生成明确的方向提示，不推断“管理/被管理”等业务语义。两个方向名称是 Link 内部展示元数据，Link.name 仍按所属分类统一校验，方向入口不另占一份分类定义名称登记。

修改展示名、换组或同租户跨分类移动时，两方向保留原 Link ID；反向入口在目标 Schema 下可发现，不因 Link 定义归属另一个分类而漏掉。停用或删除 Link 时两个方向一起停用或移除，已有引用、关系事实及运行中操作先按迁移规则处理；不能单独删除反向入口后让正向仍可用。修改端点或基数时两个方向一并重新校验，不能静默互换原 source/target 的含义。

### 基数与方向

| source → target 的基数 | target → source 自动显示的基数 | 数量约束 |
| --- | --- | --- |
| 1:1 | 1:1 | 每个 source 至多一个 target，每个 target 至多一个 source |
| 1:N | N:1 | 每个 source 可有多个 target，每个 target 至多一个 source |
| N:1 | 1:N | 每个 source 至多一个 target，每个 target 可有多个 source |
| N:M | N:M | 两端均可关联多个实例 |

此处 1 表达最大数量，不自动要求每个实体始终至少有一条边；必关联及最小数量约束需另行明确，并验证创建、删除及事务语义。Schema 的关联属性分表需要恰好一个有效目标时，按其更严格的取值规则检查。反向访问继承原关系的基数、重复和删除约束，不能通过换方向放宽限制。

表中数量默认针对同租户、同一 Link 的当前关系；候选上下文扩展需显式声明基数及重复判定的作用域，并将真实上下文纳入约束，不能只在查询中筛选它。有序成员和时态关系的范围规则见第 2 节，组合全租户独占仍优先于局部范围配置。

### 查询方向与结果

| direction | 起点及查找行为 | 例子 |
| --- | --- | --- |
| out | 起点匹配 source Schema，按 source 实例查询 target | 从工单查使用的设备 |
| in | 起点匹配 target Schema，按 target 实例查询 source | 从设备查使用它的工单 |
| both | 按当前端点类型规则匹配起点的角色，执行适用的正/反向查询，再按结果类型归并 | 同一 Schema 的上下级关系可同时查上级和下级；接受子类型时也按实际类型执行所有匹配方向 |

默认有向模式下，direction 始终相对当前 Link 定义的 source/target，使用反向入口返回的 `linkRef + in` 后不再额外交换一次方向。起点 Schema 不匹配或路径某层无法连接时明确拒绝。自关联 Schema 同时具有 out/in 两个入口，即使展示名相同也按稳定方向键区分；both 提供双向导航，关系本身的业务语义和已保存的端点顺序仍保持有向。

以上表格及端点角色规则描述默认有向模式；业务对称扩展遵守第 2 节的等价邻居约定。out/in 是访问方向，不是成员排序或工艺前后；有序成员的升/降序和邻居查询需另外携带排序范围。

以下为两个独立的候选请求，分别从工单和设备查询同一个 Link；实例 ID 仅为示意。示例省略过滤、分页和预算字段以突出方向，实际执行仍须应用服务端限额。

```json
{
  "start": {
    "schemaRef": {"id": "f5e1bc42-9e6b-4e43-8dc3-230b53da2a83"},
    "entityId": "97e56d83-b843-4efa-aaf1-19909ebd2891"
  },
  "path": [{"linkRef": {"id": "d0a3bbd7-c351-4e78-bbb6-7ec48736c386"}, "direction": "out"}],
  "return": "entities"
}
```

```json
{
  "start": {
    "schemaRef": {"id": "09228a4b-f3e8-4a3b-9581-a95d29bd5d2b"},
    "entityId": "bf51a5aa-8d4a-4072-b9bd-33fe31d115b3"
  },
  "path": [{"linkRef": {"id": "d0a3bbd7-c351-4e78-bbb6-7ec48736c386"}, "direction": "in"}],
  "return": "entities"
}
```

每层可独立选择方向，例如工单沿 out 查设备，再沿另一条 Link 的 out 查产线；反向则按相反层序逐层使用 in。关联过滤、端点过滤、排序和分页按整个合法结果集执行，不能先各方向分页再简单拼接。返回实体时按租户、Schema ID、实例 ID 去重，返回边时按同一权威 edge ID 去重；若允许自环，both 不重复返回同一边。返回路径时保留有意义的不同路径，不能仅按终点去重。结果须能说明实际方向和端点，不能只返回易混淆的展示名。

反向入口继承当前 Link 的访问要求，各方向仍校验起点、边、终点和投影字段的当前权限；获得正向入口不意味着自动获得反向关联实体的读取权限。过滤、计数、分页和缓存都遵守同一边界，不能通过反向入口泄露未授权关联。

## 4. 关系事实、接口与执行计划

对象属性的单条/批量保存及对象创建与关系命令的一次本地事务提交，见[数据读写](../数据读写.md)；DataSet 的关系筛选/展开、多跳执行和结果模式独立见[数据查询 / DataSet](../数据查询/DataSet.md)。DataSet 沿用本文的方向、上下文与路径语义；Link 维护自己的关系语义和受控命令，通用 CRUD、批量或 Action 最终写入不能绕过成员覆盖、归属、防环、顺序及权限约束。

定义模块提供草稿维护、端点/引用校验、当前定义读取和变更影响分析；Data 提供关系写入、删除、邻接与路径查询。修改端点、收紧基数或删除 Link 前检查现有关系及当前引用方，必要时先迁移、排空相关操作再替换当前定义，不保留旧定义供业务选择。固定路径协议至少包含起点、每层 Link/方向/过滤、投影、分页及预算，具体 HTTP/DSL 格式待定。

一条关系实例保存一份权威边事实，包含稳定 edge ID、租户、规范的 source/target 实例 ID 及两端实际 Schema ID，并按当前 Link 端点类型规则校验。精确端点可从定义推导具体 Schema，允许子类型时必须保存并返回具体类型身份，不能只用基类 ID 定位。正向和自动反向入口访问同一事实；添加、移除或改变关联后，两方向在同一已提交状态下可见，查询快照和副本延迟按存储契约声明。方向入口不要求再插入一行倒置端点的边，也不复制需要独立维护的关系表。

从任一方向操作关系时，Data 按当前方向和已启用的对称规则规范端点，再执行一致的租户、权限、端点、基数及重复检查；启用上下文、属性、顺序或有效时间时一并校验，规范化不能丢掉这些值。删除按同一 edge ID 定位，逆向发起的同一删除不能只移除某个视图。关系变更与所属 outbox 按本地事务契约提交，同一事实不因有两个方向而产生两次独立业务变更；计算属性、分表来源及订阅按 canonical Link ID、必要上下文和真实边/属性变更定位依赖，避免正反向相互触发形成循环。

Data 在一次查询开始时解析当前 Link、端点 Schema 和物理映射，将路径、方向和逐层过滤编译成受控执行计划，查询内使用一致内容，定义去重、分页和结果形式。优先过滤和投影，使用批量读取或数据库关联，避免逐实体调用形成 N+1 请求。执行计划有跳数、扫描量、分支、结果数和时间预算，超预算返回明确错误；分页期间相关定义变化应使旧游标失效并要求重新查询。

路径使用 Link 稳定 ID，所有关系表及端点查询强制租户条件，不能只在起点过滤租户。反向读取、聚合、分页和缓存也遵循同一边界；展示名变更不影响已保存的路径。

| 主要查询形态 | 优先评估方案 |
| --- | --- |
| 双向关联、固定少量跳数、选择性较强的过滤 | 关系表、双向访问索引、JOIN 或 EXISTS |
| 高频跨源关系、重复出现的复杂路径 | 应用层批量关联、集中关系索引、物化或预计算 |
| 不定长路径、可达性、最短路径、图算法 | 图数据库或专门图计算能力，先确认是否在范围内 |

需要关系查询语义不意味着必须采用图数据库。关系数据库性能取决于数据量、分支度、索引、过滤位置、统计信息和执行计划；图数据库也受路径膨胀影响。固定路径或少于四跳不能证明某种引擎性能最优。

## 5. 存储候选与限制

首批关系数据库适配目标为 MySQL、PostgreSQL、达梦，分别验证明确版本的类型、事务、索引、查询与 DDL 能力。Data 的路径计划经 [统一存储引擎](../存储引擎.md) 编译执行；首轮验证每个 Link 的关系表与双向索引，不使用 ORM 自动关联加载替代固定路径计划。

Metadata 需能按租户及 source/target Schema 反查参与的当前 Link，派生两端方向列表，不能只索引 source 而漏掉自动反向入口。Data 对每个受管理 Link 的候选关系表至少维护正向 `(tenant_id, source_id, target_id, edge_id)` 和反向 `(tenant_id, target_id, source_id, edge_id)` 访问索引；实际列、索引顺序和端点排序需求在三库执行计划中验证。多个 Link 共用表时还需 Link ID 条件及对应索引。

双向访问索引用于查询，基数和重复限制另需真实并发约束。例如 1:N 对 target 侧施加租户内唯一约束，N:1 对 source 侧施加唯一约束，1:1 两侧都受约束；N:M 在 duplicatePolicy 为 reject 时按规范端点对限制重复。受管理存储的具体约束及锁协议逐库验证，不能靠先查数量再插入保证并发正确性。分表/外部端点、跨源或不能建立约束的映射仍需单独证明能力，不能因有反向索引就宣称满足所有写入约束。

上述索引示意以精确端点为前提；启用子类型端点时，实际端点 Schema ID 须参与定位、相应访问索引及基数/重复判定，不能将不同具体 Schema 中恰好同值的局部实例 ID 混为一个实体。组合跨 Link 归属和树/DAG 防环还需第 2 节的额外事务约束，不能以这些单表索引代替。

启用上下文和有序成员时，访问索引及基数/重复/排序约束还须纳入所声明的范围；业务对称关系使用规范化端点判重。有效时间的区间重叠约束须逐后端独立证明，不能以一个起始时间唯一索引代替。源库反向映射也不因这些候选而自动获得平台添加关系属性列或索引的权限。

- MySQL 5.7 缺少递归 CTE，但可执行固定层级 JOIN 或 EXISTS；兼容某种固定路径查询不等于支持不定长遍历。
- 跨数据源路径通常需要应用层批量关联或集中关系索引，不能假设一条 SQL 可以完成跨源访问。
- EdgeDB（现名 Gel）是基于 PostgreSQL 的对象关系数据库，不能简化为 ORM 封装，其 Link 语义也不是遍历性能最优的证明。
- Neo4j 是属性图数据库，ArangoDB 是多模型数据库，Apache AGE 是 PostgreSQL 图扩展，应按能力和实际负载分别评估。

图库可作为特定负载的存储方案或后续加速层。引入前必须评估同步延迟、索引重建、权限过滤及故障回退成本，并确定权威数据来源。缓存、物化、读副本和图索引的引入均需要实测依据。

实例字段的逻辑类型、单位和物理表映射见 [Schema](Schema.md)。跨源查询的批量关联和一致性、路径去重与分页必须在具体适配器中验证；增加应用副本不能消除高分支遍历和数据库锁的瓶颈。

端点 Schema 分表时，关系事实继续引用稳定 Schema/实例 ID，不保存物理表名。Data 按当前规则或可信定位目录批量解析端点，路径每层都计算候选成员和执行预算；跨表过滤、去重及分页不能退化成逐边广播。端点/基数/删除约束与范围归档或移除一并验证，实体搬迁不改 Link 引用，关系表也不因实体分表自动拆分。路由、唯一性和维护迁移契约由 [Schema](Schema.md) 维护，不由应用层一次存在性检查或未认证的跨分区外键替代。

Link 若参与关联属性分表取值，还需登记路由依赖、校验实际单目标基数及同租户权限。创建实例/关系与快照取值的事务顺序、父属性或关联变动后的旧数据位置遵守 [Schema](Schema.md) 的创建时快照契约；当前关系过滤不能只按父对象当前属性选择一张表，丢掉旧成员中的实例。

## 6. 验收与待定事项

| 编号 | 要求 | 验收方法 |
| --- | --- | --- |
| CORE-04 | Link 明确端点、方向、基数、重复与删除规则 | 多对多样例正反向结果一致；违反基数、重复边或删除规则时按约定处理 |
| CORE-05 | 多级查询明确过滤、去重、分页和执行预算 | 对固定路径逐层核对结果；高分支、循环和超预算请求可控结束 |
| LINK-01 | 创建一份 Link 自动提供可发现的正反向入口 | 草稿预览、生效后两端列表、默认/自定义方向名称及空关系均可核对；改名不变 ID，停用/删除及端点变更同时作用于两个方向，无独立反向定义或边事实副本 |
| LINK-02 | out/in/both 及反向基数语义正确 | 四种基数正反对应；端点错配拒绝；自关联、允许自环及混合方向路径不重复边或漏路径，全局过滤/去重/分页与独立基准一致 |
| LINK-03 | 正反向关系操作共用同一约束及变更事实 | 任一方向增删后另一方向一致；同一边 ID 可核对；双向并发重复/基数冲突被约束，事务回滚无残留，一次真实变更不因方向视图重复产生事件 |
| LINK-04 | 自动反向发现与查询遵守当前态、权限及性能预算 | 同租户跨分类端点能发现合法入口，越租户/越权不暴露；两端索引及查询计划可核对，不逐实例回查 Metadata/扫描全部分表；当前定义变化后旧方向缓存及游标失效 |
| LINK-05 | 普通关联、聚合和组合有独立且一致的生命周期语义 | 聚合移除不删实体；组合跨 Link 并发认领最多成功一次；组合环、自我组合被拒绝；转移保留 ID 且回滚无残留，删除按端点策略及预算执行，不绕过其他关系约束 |
| LINK-06 | 树/DAG 的父数量、防环和换父在并发下成立 | 多根树、DAG 多父分别可用；树多父和互相挂接被拒绝；正反向、批量/导入及多 Link 共同范围校验一致；祖先/后代查询有预算，节点/路径去重及换父后的派生结果可核对 |
| LINK-07 | 端点默认精确匹配，显式子类型扩展保留具体身份 | 精确模式拒绝子类型；扩展模式两端发现、正反查询和分页覆盖合法子类型，实际 Schema/实例 ID 可定位，基类无独立副本；继承变化先检查现有边，越权和不支持的跨表约束被拒绝 |
| LINK-08 | 有序成员及直接前后语义按明确范围成立 | 按定义/实例/查询示例核对成员查询、空/单设备产线、分页完整性、整线排序及 in 上一台/out 下一台；两跳终点和 both 不冒充整线顺序；同设备跨路线不串事实，重复出现使用位置 ID；chain 检查成员覆盖和单链完整性，直接/任意先后区分 |
| LINK-09 | 顺序维护并发安全且具有有界查询成本 | 首次一次提交四成员/三后继，未提交半链不可见；全量序列替换与分页数据区分，移出成员不删设备；幂等重放、并发插入/拖动/交换、删除及跨范围移动保持约束，状态冲突拒绝覆盖；失败回滚，派生与权威顺序一致，旧游标按契约处理，索引/扫描/锁/写放大及权限边界可核对 |
| LINK-10 | 对称与推导扩展不改变事实含义 | 对称 A-B/B-A 共用事实，两方向合法邻居一致且 both 不重复；对称 1:1 按全部邻居约束，并发端点换位不能绕过；有向供电不被误作对称，不兼容配置拒绝；直接后继不混入任意后继，相邻不错误传递；推导遵守来源、权限和预算，未支持的规则拒绝 |
