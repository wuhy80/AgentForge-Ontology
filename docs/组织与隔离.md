# 租户、分类、分组与标识

状态：层级、租户隔离、分类内不重名和展示名与 ID 分离为已明确要求；字段、存储及接口为候选方案，尚未实现。本文统一维护五类定义的组织与命名规则。

## 1. 组织层级

```text
租户 Tenant
  └─ 分类 Category：租户内的业务分类
       └─ 分组 Group：分类内的展示与管理分组
            └─ Schema / Link / Action / Function / Enum
```

租户是隔离边界，分类是业务组织及名称唯一性边界，分组用于整理定义。五类定义采用同一层级；分组不是另一套名称空间，也不改变租户隔离规则。首期按固定三层组织，不扩展为任意深度目录；每个定义归属一个分类和一个分组，可由系统提供普通的默认分组。

| 对象 | 归属与作用 | 名称范围 |
| --- | --- | --- |
| Tenant | 独立的数据、定义、权限及运行上下文 | 通过 tenant_id 定位，不以租户展示名判断身份或授权 |
| Category | 必须属于一个 Tenant | 建议同租户内分类名称唯一 |
| Group | 必须属于一个 Category | 建议同分类内分组名称唯一 |
| 五类定义 | tenant_id、category_id、group_id 必须指向同一条归属链 | 同分类内统一检查名称，不因定义类型或分组不同而放宽 |

本文按 Schema、Link、Action、Function、Enum **共享分类名称空间**解释“分类下面不重名”。例如，同分类已有 Schema“设备”，其他分组不能再建“设备”，也不能创建同名 Action；不同分类、不同租户允许出现同名定义。

分类间可以通过 ID 引用同租户的定义，发布时检查依赖和权限；跨租户引用及跨租户 Link 端点一律拒绝。分类和分组不直接决定物理数据库、表名或服务部署。

## 2. 展示名与稳定 ID

| 字段 | 规则 |
| --- | --- |
| id | 服务端生成的全局唯一、不透明且不可变的标识，建议 UUID；不由名称、路径、数据库表名或租户名称拼接生成 |
| tenant_id | 不可变的所属租户；即使 ID 全局唯一，每次读取仍必须校验租户 |
| category_id、group_id | 使用对应对象的稳定 ID；不能保存分类名或分组名作为关联键 |
| name | 主展示名，可修改，参与所属分类的名称冲突校验；不作为程序调用或依赖引用键 |
| labels、description | 可选的多语言展示与说明；labels 不替代主展示名的唯一性校验 |
| 当前定义与草稿 | 每个对象只有一份当前生效定义，最多一份待生效草稿；不设置业务 version |

接口 JSON 可采用 `tenantId`、`categoryId`、`groupId`，存储列采用对应下划线形式。定义引用统一使用 `{ "id": "<稳定 ID>" }`，业务操作解析当前生效定义；租户从已验证上下文继承，携带显式租户时必须与上下文一致。名称仅用于展示和搜索，API 路由、执行、Link 端点、Enum 引用、依赖及物理映射均使用 ID。五类定义共同的当前态及生效规则见 [发布与迁移](发布与迁移.md)。

重命名、同分类换组或同租户跨分类移动不改变 id；跨分类移动先验证目标名称及引用权限，原归属可保留在审计记录。重命名不自动改变数据库表名、列名或索引名。跨租户不能直接移动对象；显式复制须生成新 ID 并重建租户内引用，不继承原租户的数据或凭据。

属性和索引也保存各自的稳定 ID，其名称只在所属 Schema 内校验，不占用分类的五类定义名称空间。JSON 属性键等协议字段与展示名分开，兼容性由 [Schema](模块/Schema.md) 维护；Enum 的稳定业务值编码仍按 [Enum](模块/Enum.md) 规则处理。

Link 自动生成的正反向入口是同一当前定义的方向视图，以 Link ID 和 direction 定位。forwardName/reverseName 是该 Link 内部的展示元数据，不另登记为第二份分类定义；Link.name 继续遵循分类内跨类型唯一规则，正反方向同时出现在各自端点 Schema 的可用关系列表中。自动生成及生命周期规则统一见 [Link](模块/Link.md)。

## 3. 名称校验与并发

建议统一计算 `name_key`：主展示名去除首尾空白、执行 Unicode NFC 规范化，再按固定的大小写归一规则生成比较键；空名称拒绝。归一规则及版本由平台固定，不能依赖三个数据库各自的默认排序规则。具体长度与归一库在协议落地时确定。

Metadata 维护一份轻量的定义登记表，保存 id、tenant_id、category_id、group_id、kind、name 和 name_key。数据库对当前对象登记建立 `UNIQUE(tenant_id, category_id, name_key)`，键中不包含 kind 或 group_id；各模块仍分别维护定义正文与领域规则，通过窄接口登记及检查归属。

登记及当前定义更新在 Metadata 的同一事务内完成。只做创建前查询不足以防止并发重名，最终由唯一约束裁决。名称约束针对当前对象登记，草稿不是另一个对象，保存草稿先校验候选名，生效时重新校验并更新唯一登记；新对象在创建登记时占用名称。尚未完成引用及历史保留处理的删除对象不直接释放登记，ID 永不复用。

tenant/category/group 的归属通过组合外键或等价的事务校验保证，不能将其他租户的分类 ID 或其他分类的分组 ID 写入。分类、分组删除前必须为空或显式完成迁移，不隐式级联删除业务定义。

## 4. 全链路租户隔离

| 环节 | 必须保证的行为 |
| --- | --- |
| 身份与接口 | 服务从认证身份解析并验证 tenant_id，支持多租户身份时验证当前所选租户；不信任请求体里的 tenantId；按 ID 读取、列表、搜索、统计、导入导出及批量接口都校验租户 |
| 存储与查询 | 定义、实例、关系、任务、事件、订阅、调度、迁移及预览记录归属租户；共享表的查询、JOIN、更新、删除及唯一键显式包含 tenant_id；独立物理表/库同样验证租户映射 |
| 引用与关系 | 引用方、被引用定义、Link 及两端实例处于同一租户；知道其他租户的 ID 不能获得读写权限 |
| 缓存与检索 | 缓存键包含 tenant_id、对象 ID、当前内容摘要及实际影响输出的权限条件；使用前校验当前状态，搜索索引、结果缓存和分页游标不能跨租户复用 |
| 执行与触发 | 任务、幂等键、订阅、周期规则和事件携带已验证租户；Worker 使用任务租户的受限身份、凭据、工作目录及制品访问权限 |
| 数据源与预览 | 数据源及连接凭据归属租户，目录发现、反向建模、样例数据与 SQL 预览都校验访问范围；不因数据源连接可访问其他库表就向用户暴露 |
| 日志与运维 | 审计、运行日志、结果下载和运维查询按租户授权；受控平台运维通道单独授权和留痕，不提供业务接口的无租户回退 |

“完全隔离”要求业务访问不能越界。共享表加 tenant_id、独立数据库 schema 或独立数据库是可选物理部署方式；选用共享基础设施时必须验证全部访问路径。若还要求物理资源、备份或故障域独立，部署方案需另行明确，不能把共享表误称为物理独占。

`db_2_schema` 接入已有表时还要验证表中数据的租户归属：租户专用源可绑定专用映射，共享源必须有经校验且不可由用户绕过的行级租户条件；无法证明隔离时拒绝作为租户实例数据源。

## 5. 验收

| 编号 | 要求 | 验收方法 |
| --- | --- | --- |
| ORG-01 | 五类定义遵循租户、分类、分组归属链 | 错租户分类、错分类分组、非空分类/分组的隐式删除均被拒绝 |
| ORG-02 | 分类内共享名称空间，并发修改不突破唯一约束 | 同组、跨组、跨类型同名均拒绝；不同分类或租户同名可创建；并发创建和改名最多一个成功 |
| ORG-03 | 名称与 ID 分离，当前定义的引用保持稳定 | 展示改名、换组和跨分类移动后 id 不变；既有 Link、Action 及物理映射仍可按原 ID 解析 |
| ORG-04 | 租户边界贯穿元数据、实例及所有运行路径 | 用租户 A 身份提交租户 B 的定义/实例/任务/数据源 ID、游标、批量操作及缓存请求，均不能读写或推导 B 的业务数据；跨租户引用被拒绝 |
| ORG-05 | 名称归一与当前态规则跨数据库一致 | MySQL/PostgreSQL/达梦对大小写、首尾空白、Unicode 等价文本、草稿改名及生效给出一致的冲突结果 |

具体存储实现见 [存储引擎](存储引擎.md)，定义生效与执行上下文分别见 [发布与迁移](发布与迁移.md)、[执行与调度](执行与调度.md)。
