# 数据读写：内置写接口、批量操作与关系事务

状态：2026-11-08按用户确认方案实现每Schema八种写操作、能力发现、默认MySQL及受限专用MySQL来源写适配。已补默认平台跨Schema对象事务与Action/Function受控写计划；对象/关系组合事务、异步导入与其他后端写入仍为候选。实际协议见[公共写契约](../contracts/write_operations.go)和[Data服务](../services/data/README.md)，分项验证见[项目总览](项目总览.md#当前实现与验证2026-11-06)。查询语义仍唯一维护在[DataSet](数据查询/DataSet.md)，字段和关系约束分别见Schema、Link。

## 已确认需求（2026-11-08）

每类业务对象自带`create`、`update`、`delete`、`upsert`及`bulk_create`、`bulk_update`、`bulk_delete`、`bulk_upsert`，共八种写操作。这里的对象指Schema管理的业务实例，读取和查询使用既有入口，不计入八项。

用户随后确认按此方案实现。八操作由统一Data引擎动态派生，不生成八份Action/Function；能力存在仍须满足当前权限和来源就绪条件。本批不修改现有知识库对象、来源、账号或部署，也不自动为已有角色授新权限。显式来源须按第9节逐Schema启用。

## 1. 每个 Schema 具备能力，服务共用实现

操作身份为`(schemaId, operation)`，按当前生效定义、稳定字段ID和实例ID执行，中文改名不改变绑定。新增Schema无需生成Controller、ORM或重启服务。业务Action独立维护，源码运行器的纯计算边界不因新增Data接口而改变。

实例写入与定义草稿、模型生效和DDL分别处理：创建实例不会修改Schema或产生定义version。只有已生效且映射就绪的Schema可写，普通实例请求不建表、不迁移平台或来源控制表。

`GET /data/schemas/{schemaId}/write-capabilities`按当前调用者返回八项`name/allowed/reason/writeFields`、安全字段描述、匹配模式、可用唯一键、覆盖授权、覆盖模式的字段/唯一键范围及限额。至少具备该Schema一种基础写权才能发现，不要求整定义读权；不返回物理映射或未授权字段。该结果用于表单和按钮，不替代执行时逐项校验。来源未启用、不支持的组合和维护状态明确不可写。

## 2. 八种写操作的实际入口

以下为Data服务路径，公开网关添加`/api`或OntoApp专用别名前缀。`schemaId`及`entityId`均为稳定ID。

| 内置操作 | HTTP入口 | 语义 |
| --- | --- | --- |
| create | `POST /data/schemas/{schemaId}/instances` | 显式创建；唯一冲突不覆盖，必填幂等键 |
| update | `PATCH /data/schemas/{schemaId}/instances/{entityId}` | 只改提交字段；不存在不创建，必填强If-Match |
| delete | `DELETE /data/schemas/{schemaId}/instances/{entityId}` | 必填强If-Match，遵守已认证引用约束 |
| upsert | `POST /data/schemas/{schemaId}/instances/upsert` | 明确ID或完整真实唯一键匹配；必填幂等键 |
| bulk_create | `POST /data/schemas/{schemaId}/instances/bulk-create` | 同Schema原子批量创建 |
| bulk_update | `POST /data/schemas/{schemaId}/instances/bulk-update` | 逐项ID、ifMatch、修改值 |
| bulk_delete | `POST /data/schemas/{schemaId}/instances/bulk-delete` | 逐项ID和ifMatch |
| bulk_upsert | `POST /data/schemas/{schemaId}/instances/bulk-upsert` | 逐项明确match、可选ifMatch及写入值 |

`update`保留PATCH语义，不增加PUT全量覆盖。四个bulk路径各对应一种操作，不接受同批混合命令；对象/Link混合事务仍为第6节候选。单条读取继续使用`GET /data/schemas/{schemaId}/instances/{entityId}`，筛选分页继续使用QuerySpec/OntologySQL。

表单发现保留`operation=create|patch`兼容，由来源实际就绪状态及当前写权派生可写性。工作台对象详情展示八项内置操作及单条/批量执行区；OntoApp通过公开HTTP契约适配，不能以客户端循环单条请求模拟原子批次。

## 3. 数据查询入口与职责

按ID读取和query仍由统一Data服务提供；字段投影、筛选、关系导航、分页与预览以[数据查询目录](数据查询/README.md)为准。OntologySQL文本入口只读，不从SELECT结果自动推断保存。查询结果修改后必须显式提交写接口；查询权不授予写权。

## 4. 单条保存的明确语义

实际`values`使用稳定field ID，也接受当前精确属性名并规范化；同一属性同时按名称和ID提交会拒绝。创建由服务端生成UUID，普通values不能覆盖系统ID、租户或只读字段。PATCH缺失字段保持原值，null只有字段允许时成立；未知字段、非法类型与必填缺失拒绝。业务JSON不隐式级联保存关联对象，当前支持的类型及约束以Schema与服务说明为准。

以下是实际创建正文示例，标识为示意，调用前须替换成当前字段ID：

```json
{
  "values": {
    "设备编码字段ID": "PUMP-001",
    "设备名称字段ID": "输送泵"
  },
  "idempotencyKey": "create-pump-001-本次意图"
}
```

更新和删除使用读取响应的完整强HTTP ETag，例如`If-Match: "不透明凭证"`；弱标签、星号、多标签和裸值不接受。凭证不是业务version，不提供读取历史对象的能力。幂等键1～128字节，相同键不同意图返回409；平台原有单条create记录及摘要保持兼容。

### 4.1 upsert 的匹配与并发

`match`二选一，不接受任意where、SQL或物理索引：

| 匹配方式 | 实际规则 |
| --- | --- |
| `match.id` | UUID稳定实例ID；创建分支保留明确ID，更新不改ID。只有upsert允许创建时指定身份 |
| `match.indexId + match.values` | 引用当前已生效且经物理核验的唯一索引；用稳定field ID提供完整且非null的键值，沿数据库真实类型比较 |

匹配键在更新分支不变；values重复键字段时必须与match按真实类型等价。创建分支将match键合入values，仍校验默认值、必填与权限。其他唯一键冲突不会转而更新另一记录。匹配与分支写入在同一本地事务内执行，使用真实唯一约束和锁；不使用任意冲突的`ON DUPLICATE KEY UPDATE`替代匹配协议。

```json
{
  "match": {"indexId": "唯一索引稳定ID", "values": {"设备编码字段ID": "PUMP-001"}},
  "values": {"设备名称字段ID": "输送泵"},
  "conflictPolicy": "check",
  "idempotencyKey": "upsert-pump-001-本次意图"
}
```

| 策略 | 实际行为 |
| --- | --- |
| `check`，默认 | 无If-Match只允许创建，已存在返回428；有If-Match只允许更新对应旧对象，目标消失或凭证过期返回412 |
| `overwrite`，显式同步用途 | 有则按PATCH更新，无则创建；另需`instance.upsert.overwrite`，不能同时提交If-Match。未提交字段保持，不绕过行列、类型、唯一或关系约束 |

首次创建返回201，更新或幂等重放返回200。单条回执包含`schemaId/outcome/id/etag`和允许返回的values，并通过HTTP ETag返回新凭证。无字段读权只给最小回执，不回显隐藏值。权限与隐藏行匹配规则唯一见[八操作授权](权限/权限设计.md#内置八种写操作的授权2026-11-08)。

## 5. 批量操作复用同一套规则

bulk在同Schema、同一本地事务内执行有界循环，共享单条的领域校验，不调用逐条HTTP。默认`atomic=true`，仅支持该模式；`false`明确拒绝。整批1～100项，不能按条件批量改删。

```json
{
  "atomic": true,
  "items": [
    {"clientKey": "pump-1", "values": {"设备编码字段ID": "PUMP-001", "设备名称字段ID": "输送泵"}},
    {"clientKey": "pump-2", "values": {"设备编码字段ID": "PUMP-002", "设备名称字段ID": "冷却泵"}}
  ],
  "idempotencyKey": "bulk-create-pumps-本次意图"
}
```

| 规则 | 实际协议 |
| --- | --- |
| 项目对应 | 每项唯一且非空的clientKey，成功按输入顺序返回；不替代实例ID |
| create | values非空，服务端分配ID，不隐式转upsert |
| update/delete | 每项id及完整带双引号的强`ifMatch`；update另有非空values，单个HTTP If-Match不能代表整批 |
| upsert | 每项match/values，整个批次同一conflictPolicy；check的逐项ifMatch沿单条规则 |
| 重复目标 | 重复ID、匹配键或最终命中同一实例拒绝，不用数组顺序决定覆盖 |
| 事务与结果 | 任一失败全部回滚，数据、幂等、outbox一起提交；成功返回schemaId、atomic、committed、replayed及逐项results |
| 预算 | 1～100项，8MiB请求及完整响应、15秒整体时限，沿用服务准入；超限在提交前拒绝，不拆成多次提交 |
| 幂等 | 整批键必填，作用域为租户/用户/Schema/操作；摘要绑定顺序、项目、匹配、并发凭证和策略，同键不同意图409 |

upsert和bulk使用操作维度回执；数据、完整历史证据与outbox在同事务保存。重放重新检查当前操作、原结果及当前行权限并裁剪字段，删除重放还须匹配原授权摘要。没有自动清理或过期策略，运维不可在仍需重试期间随意删除记录；保留期与有界归档另行设计。

按确定顺序执行目标，死锁/锁超时和upsert竞争最多重试三次，每次重跑整批校验且受请求时限限制。公开错误不输出SQL、物理约束名或隐藏键值；当前失败使用统一安全错误，不承诺逐项错误回执或部分成功。

### 跨Schema对象事务（2026-11-08已实现）

用户要求直接写接口及Action/Function均支持事务写入。本批增加`POST /data/transactions`，请求为`{idempotencyKey,operations}`；每项为`{schemaId,operation,clientKey,id?,ifMatch?,match?,values?,conflictPolicy?}`，实际契约见[transactions.go](../contracts/transactions.go)。四种operation为create/update/delete/upsert，规则与上述单条写入共用；bulk在调用侧展开为项目，总计1～100项。支持同租户默认平台MySQL内多个Schema的混合操作，使用同一SQL事务，任一失败不保留业务变更或outbox。映射Schema、跨库、Link命令、临时创建引用及事务内重复修改同一目标均明确拒绝。

事务幂等键在租户与提交主体内唯一，摘要绑定完整请求，包括项目顺序、并发条件和策略；状态与数据在同一事务提交。已受理的安全业务/预检拒绝以HTTP200、`status=failed,committed=false`返回持久失败回执；仅在业务写已实际回滚且失败回执提交后才能宣称failed。身份、请求结构、服务不可用、提交超时等仍可能返回HTTP错误，不能据此断言未写入。同键不同意图409；持久failed不会因同键重放自动重新执行。

`POST /data/transactions/status`接受原完整请求，只核对回执、不执行写入。`status=committed`证明已提交，`failed`证明已回滚或预检拒绝；`not_found`只表示当前尚未看到回执，不能排除在途提交。核对仍使用当前会话及授权，成功回执按当前权限重新裁剪；已失去数据权限时不返回历史成功内容。最小失败回执无历史行值，原主体可按原意图核对确定性拒绝。网络不确定时保留原键和请求，禁止换键盲目重试。

Action/Function声明`sideEffects=dataWrite`与显式`dataWrite`范围后，三语言SDK可暂存相同写命令。代码正常结束且声明输出合法后，Execution才交给上述Data事务一次提交；异常、超时、取消或非法输出不提交。SDK没有查询、事务内读取、即时生成ID、手动commit/rollback或嵌套事务，读取与写后读取另行设计。源码协议唯一见[Function](模块/Function.md)，原调用者权限交集见[权限设计](权限/权限设计.md)，持久计划及未知提交恢复见[执行与调度](执行与调度.md)。多个独立HTTP请求仍不自动合并为一个事务。

需显式应用Data迁移`009_data_transaction_receipts`，普通启动与请求不建表；本批不迁移既有部署。预算继续为8MiB、15秒及现有服务准入，不因多个Schema增加额度；脚本私有输出和写计划另受运行器256KiB总预算。失败回执、成功回执与outbox均须纳入备份，不能在仍需恢复期间删除。

## 6. 对象和 Link 一起保存（候选）

仅保存设备属性用实例 CRUD；连接设备与产线、维护前后顺序用关系用例。需要“新建设备并放到产线末尾”时，建议通过有界 mutations 或等价事务命令，一次提交对象创建和受控序列插入，失败一起回滚。成员及单链规则以 [Link 的保存示例](模块/Link.md) 为准，不能先提交新成员再逐条补边。

候选事务命令可包含实例创建/修改/删除、普通关系增删和受控的序列/组合命令。请求内的 operation key 可临时引用同请求新建实例，Data 预分配实际 ID 并解析依赖，校验最终图后保存；临时引用只在本次命令内有效，持久事实仍保存真实 Schema/实例 ID。拒绝模糊循环创建依赖，不能靠嵌套 JSON 自动决定要创建、覆盖或删除哪些对象。

事务只覆盖 Data 已认证的同一本地存储及会话，物理分表也须满足其事务/全局约束条件。跨 Schema 不等于跨数据库：同一可覆盖事务中的多个 Schema 可组合提交，不同数据源/数据库或外部设备控制不自动获得原子性。具体组合没有能力证明时明确拒绝；跨源业务通过任务、幂等及明确补偿另行设计。Metadata 定义替换和 Execution 状态也不加入一个假定的分布式事务。

普通关系 CRUD 同样须维护当前所有引用约束；受控序列/组合命令绑定同一 Data 事务会话，不在事务里再调用多个远程 CRUD 后声称它们原子。可验证的数据写入、stored_sync、定位/唯一登记、边事实和所属 outbox 按同一本地契约提交。并发图约束、全范围编辑权限、幂等及预算沿用 Link；通用实例/关系入口不能绕过受控命令的最终约束。

审批、启停、校准、派工等业务动作用 Action 表达。Action 的多次远程调用不天然原子；需要本地原子数据效果时，应明确调用一次 Data 事务命令；外部副作用按 [执行与调度](执行与调度.md) 声明幂等、核对和补偿。

## 7. 统一执行与大规模导入（扩展设计）

公共行列、操作、调用路径和委托候选统一见[权限设计](权限/权限设计.md)，不在 CRUD 中另建允许名单。Data 在实际保存边界落实旧行/新行条件、可写字段及连带关系权限；Action 仅能在明确获准的调用能力范围内写入，不能绕过全局拒绝。单条、批量、mutations 和每个导入块共用当前授权，后续验收引用 AUTH-05、AUTH-07～AUTH-09、AUTH-12。

单条、批量、事务命令及 Action 最终写入共用 Data 的领域校验和存储契约：可信租户与权限 → 当前 Schema/Link/Enum 及就绪映射 → 类型/单位/只读字段/依赖校验 → 受控事务中的并发及真实约束 → 数据、同步计算、定位/关系、outbox 提交。纯预检查不代替提交时校验，直接 SQL 和批量路径也不能绕过此流程。

大规模导入建议独立任务入口，先校验格式和映射，再按受控分块执行并保存进度、逐项错误及幂等信息；任务状态遵循执行设施契约。分块导入明确可能部分完成，不把整文件描述为一个数据库事务；每块执行同一批量规则，暂停、重试、取消及错误修正行为需可追踪。

导入使用的目标字段和映射发生变化时，不能让后续分块继续使用旧规则。首批候选采用受影响任务暂停，结合 [定义生效与迁移](发布与迁移.md) 处理已提交数据，并按当前定义重校验未处理内容后恢复；不兼容变更仍须排空受影响运行操作。性能测量比较批量 SQL、循环写入及单条基线，但不牺牲原子性、权限、计算或事件正确性。

## 9. 显式来源写入与启用边界

默认平台MySQL已使用统一八操作引擎。显式来源仅认证专用MySQL、单主表、完整物理业务列映射、非生成且长度36的规范小写UUID系统主键、InnoDB及`utf8mb4_0900_bin`、真实主键/唯一索引、无触发器和级联副作用；不允许将系统ID再映射为普通属性。业务列还须精确匹配平台物理类型、长度和精度（如VARCHAR(255)、DATETIME(6)及声明的DECIMAL），文本使用`utf8mb4_0900_bin`，UUID使用`ascii_bin`或`utf8mb4_0900_bin`，避免数据库转换后回执与读取状态不一致。仅满足反向只读兼容不等于可写；`schema_2_db`/`db_2_schema`名称及账号有写权本身均不能证明可写。

共享源、多表/跨源属性、PostgreSQL、生成主键和不满足检查的来源保持不可写。具有Link时普通属性更新与关系修改分别处理：不能直接改外键关系列；当前任何已绑定Link的来源端点均暂不开放delete/bulk_delete，由逐操作能力给出原因，不因已有物理外键就认定复杂关系删除已认证。实例写接口不等于关系事实写接口。

来源账号须有完整约束目录可见性：直接授予该库或全局SELECT/TRIGGER，以及全局REFERENCES（或全局SELECT）。这是为了识别被目录权限隐藏的触发器与跨库入站级联外键；全局REFERENCES提供约束元数据可见性，不要求全实例业务SELECT。仅目标表授权、角色间接授权及复杂通配模式尚未认证，保守拒绝写入。代码不会自动为已有账号授这些数据库权限，仍须由来源管理员配置；仅有INSERT/UPDATE/DELETE不足以证明安全。

必须先显式执行平台迁移`008_data_write_receipts`，再在Data服务环境中逐Schema执行：

```powershell
go run ./cmd/server -initialize-mapped-writes -tenant <租户ID> -schema <SchemaID>
```

此命令校验当前定义与真实来源，显式创建来源内identity/gate/receipts/outbox及迁移记录，绑定来源所有者和目标表，不修改业务行或来源配置；普通启动与请求不调用它。新来源签名密钥仅保存在来源控制表，备份恢复须包含这些表。未初始化仍只读，不自动启用现有知识库。

写事务在来源库内持有源gate及目标锁，数据、幂等和outbox使用同一来源事务。发布prepare持久关闭来源gate并排空已准入事务，activate在权威当前定义核对后恢复；失败保留阻塞，通过同操作重试恢复。平台锁不被描述为另一数据库的原子提交，来源DDL和平台定义切换仍使用持久协调。

已启用来源的读取和写回执采用完整规范化状态的HMAC ETag，绑定租户/Schema/ID/定义且不受投影影响；在来源事务锁内重算验证，隐藏字段变化也使旧凭证失效，不返回隐藏值。未启用映射保留只读读取协议。来源其他写入者与DDL仍须受控，真实Link约束、异常恢复、多副本和性能按已验证范围使用。

本批不自动配置已有角色、修改442个知识库对象、初始化现有来源、迁移现网或重启服务。MCP凭据的scope与写路由保持窄白名单，Action/Function受控事务写调用见本页跨Schema事务及所属执行文档。

## 2026-11-08 同源外键持键对象创建

已认证并显式初始化的专用 MySQL 单主表，创建对象时允许填写同源已发布 `foreign_key` 的持键字段。除实例创建和列权限外，还要求该 Link 的 `link.create`、两端 `instance.read` 和行条件；目标必须存在、同源、单主表且已初始化。平台端点/Link gate、来源写 gate、目标行锁及提交前授权复核共同保护该动作，外键事实与对象、回执/outbox 同源提交。现有外键更改、端点删除、关联表写入、跨源写入继续拒绝。详细实现和分项验证见 [Data 服务](../services/data/README.md)。
