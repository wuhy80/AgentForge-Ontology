# 模型发布与迁移需求

状态：需求草案。实现方案见 [元数据与发布设计](../设计文档/元数据与发布设计.md)，多副本条件见 [横向扩展与可靠性需求](横向扩展与可靠性需求.md)。

## 1. 两种迁移

| 类型 | 对象 | 触发来源 |
| --- | --- | --- |
| 平台数据库迁移 | 元数据、任务、调度等服务自身的数据表 | 平台软件版本发布 |
| Ontology 模型迁移 | Schema、Enum、Link 变化引起的实例数据、索引及物理结构 | 本体定义版本发布 |

需要提供专门的 migrate 机制，记录执行状态、失败原因和恢复进度。模型变化不一定产生 DDL，仍需校验数据与新定义的兼容性。

## 2. 发布及兼容性

发布前需要完成定义校验、依赖检查和差异分析，确定变更的前置条件、影响范围和迁移计划。只有迁移及数据验证达到激活条件后，新版本才可进入可用状态；各副本不能通过自行猜测进度决定版本是否可用。

迁移计划应说明结构变更、回填任务、验证方式及失败后的恢复路径。长时间回填需保存检查点，支持故障后继续执行。平台与模型迁移均需避免对相同目标并发修改；锁或租约失效后，旧执行者不能继续写入。协调方案见 [元数据与发布设计](../设计文档/元数据与发布设计.md)。

滚动升级期间，新旧服务、模型版本及运行中任务需要明确兼容窗口；不兼容任务应阻止执行或按明确规则升级版本。不能默默把已经受理的任务切到另一套定义。

删字段、缩小类型、删除枚举值等变更可能不可逆，需要备份恢复、补偿或后续修复方案。是否可在线执行、是否需要维护窗口、能否自动回滚必须按具体数据库版本和变更评估，不统一承诺无停机或自动回滚。

## 3. 需求与验收

| 编号 | 要求 | 验收方法 |
| --- | --- | --- |
| PUB-01 | 平台迁移与模型迁移分别记录，由对应数据所有者执行 | 能定位迁移目标、来源版本、执行状态和失败原因；软件升级与定义发布不会混用记录 |
| PUB-02 | 发布有校验、差异、计划、数据验证和激活条件 | 校验或迁移失败不能激活新版本；多副本对发布状态和指定版本读取保持一致 |
| PUB-03 | 迁移并发安全、失败可恢复，旧执行者不能继续提交 | 两副本竞争同一目标、回填中断及租约失效场景均有明确结果，恢复不重复破坏数据 |
| PUB-04 | 变更评估兼容窗口与可逆性，执行任务固定版本 | 滚动升级覆盖新旧服务和未完成任务；破坏性变更能给出维护、恢复或补偿方案 |

## 4. 待定事项

需根据首个数据库与存储模型确定 DDL 能力、锁及旧执行者隔离方式、回填策略、激活状态机、兼容窗口、备份恢复条件和破坏性变更的发布流程。选型未完成前不将特定数据库迁移算法作为既定需求。
