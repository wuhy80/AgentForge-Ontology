# 项目需求总览

状态：分析草案。更新日期：2026-10-17。

## 1. 已明确的目标

1. 代码按模块组织，各类能力可以独立演进，控制模型辅助开发造成的代码膨胀；允许采用微服务。
2. 服务支持横向扩展，访问压力增长时可以通过增加对应服务的 Pod 扩容。
3. 性能满足业务要求，并有可重复的测量与验收依据。
4. 在 `docs/需求文档/` 维护需求，在 `docs/设计文档/` 维护实现方案。

“独立演进”包括独立修改、验证，以及服务级的独立构建、发布和扩容；涉及公共契约、跨对象约束或存储兼容性的变更，仍需显式协调。每个类型需要有清晰模块边界，是否单独部署取决于负载、数据一致性和维护成本。

## 2. 当前项目分析

| 关注点 | 仓库现状 | 当前缺口与本轮处理 |
| --- | --- | --- |
| 代码模块化 | 仓库没有 Go 模块或业务服务代码 | 先确定类型职责、依赖规则和独立构建边界，见 [模块化需求](模块化与演进需求.md) |
| 服务划分 | 现有架构草案采用多服务；工业规划保留模块化单体作为场景参考 | 当前建议采用单仓库、多服务部署；具体设计见 [总体架构](../设计文档/总体架构设计.md) |
| 横向扩展 | 已讨论无状态、租约、幂等及多副本；尚无部署配置 | 补充扩容条件、数据库连接预算、缩容与故障验收，见 [扩展需求](横向扩展与可靠性需求.md) |
| 性能 | 工业规划有候选数值，缺少统一数据集、环境与测试记录 | 建立按工作负载区分的候选基线，见 [性能需求](性能与容量需求.md) |
| 文档 | 基础业务语义和实现建议已按主题归入需求、设计目录 | 各主题单独维护，工业规划保留为远期场景参考 |

因此，目前能评估的是方案是否具备满足目标的条件；不能认定系统已支持横向扩展或已达到任何吞吐、延迟指标。

## 3. 基础引擎的候选范围

基础能力按主题维护：[本体建模与查询](本体建模与查询需求.md)、[模型发布与迁移](模型发布与迁移需求.md)、[执行与触发](执行与触发需求.md)。以下用于划定范围，各文档中的建议和待定事项仍需逐项确认。

| 能力 | 基础范围 |
| --- | --- |
| 建模 | Schema、Enum、Link、Action、Function 的定义、校验和版本引用 |
| 发布 | 定义依赖检查、版本激活、平台迁移和模型迁移 |
| 数据 | 实例与关系读写、过滤、分页、正反向关系及有界路径查询 |
| 执行 | 同步与异步调用、持久任务、状态查询、超时和幂等处理 |
| 触发 | 事件和周期触发，支持多副本协调 |
| 部署 | 容器化、独立服务、多副本、基础监控和容量验证 |

首期建议只落地一种数据库和一种实际可用的语言运行器。Go 是已有的服务实现方向；数据库产品、首批 Function 语言及运行方式尚未确定。工业诊断、Agent 编排、设备控制、图算法、向量检索及完整 OWL/RDF 推理属于后续独立范围，不自动进入基础版本。

## 4. 需求到验收的对应关系

| 目标 | 需求编号 | 最小可检查结果 |
| --- | --- | --- |
| 建模、类型与查询正确性 | CORE-01～CORE-06 | 字段精度、枚举、关系方向及多级过滤有可核对结果，超预算请求可控结束 |
| 发布与迁移可恢复 | PUB-01～PUB-04 | 校验失败不激活，迁移中断可恢复，滚动升级和运行中任务遵循兼容窗口 |
| 执行与触发可追踪 | RUN-01～RUN-05、TRG-01～TRG-02 | 同步/异步调用、取消超时、重复事件及周期争抢有明确业务结果 |
| 模块独立演进 | MOD-01～MOD-08 | 一个 Enum 校验改动只涉及所属模块及必要契约；无跨服务业务包或数据表依赖；单服务可独立构建 |
| 增加 Pod 扩容 | SCALE-01～SCALE-10 | 查询服务、任务 Worker 分别完成多副本验证；扩缩容和 Pod 退出不破坏已接收任务的可追踪性 |
| 性能可验收 | PERF-01～PERF-06 | 在确定的数据、查询、硬件和版本下出具延迟、吞吐、错误率与扩容曲线 |
| 文档可持续维护 | DOC-01～DOC-03 | 需求、设计、后续验收记录能够相互定位 |

### 文档要求

- **DOC-01**：需求说明目的、范围、优先级或阶段、可观察的验收结果；设计引用需求编号。
- **DOC-02**：明确区分已明确目标、建议方案、待定指标和实测结果，草案数值不能写成已达成能力。
- **DOC-03**：一种指标保留一个定义来源；新增文档更新 [文档入口](../README.md)，设计变更记录原因及影响。

## 5. 建议实施顺序

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| A：契约与边界 | 类型模型、服务所有权、接口、候选负载 | 定义与实例、执行状态的责任清楚；跨模块依赖可检查 |
| B：建模与查询 | Metadata、Data、迁移命令 | 发布、写入、正反向查询闭环可运行；从第一版验证两个副本 |
| C：执行与触发 | Execution、一个 Worker、Scheduler | 同步/异步、重复提交、任务恢复与周期去重可验证 |
| D：容量与发布 | Kubernetes 部署、压测报告、扩缩容策略 | 完成 1/2/4 Pod 对比、混合负载、故障恢复和滚动升级验证 |

每个阶段控制交付范围，不用文件数量或服务数量代替功能完成度。阶段 D 的性能结果决定是否需要缓存、查询预计算、独立消息系统或存储扩容。

## 6. 需要补齐的信息

| 待定事项 | 对方案的影响 |
| --- | --- |
| 实体/关系规模、热点分布、增长速度与保留期 | 存储、索引、迁移和容量规划 |
| 峰值请求率、读写比例、关系查询形态、可接受延迟 | 性能验收基线和服务副本数 |
| 首个数据库及版本，是否必须兼容 MySQL/达梦或跨源访问 | 适配器范围、事务与迁移能力 |
| 独立业务表、统一实例表或混合存储，以及 Schema 到物理结构的映射 | 数据布局、查询编译、模型迁移及回填方式 |
| Link 仅固定路径还是包括不定长遍历、最短路径或图算法 | 查询协议、执行预算及存储候选 |
| Function 语言、代码可信程度、典型耗时与外部依赖 | Worker 分组、隔离和弹性指标 |
| Action/Function 的读写、副作用、事务、重试及权限语义 | 运行器协议、幂等核对和补偿流程 |
| 对外调用/查询协议、身份隔离、版本发布及结果保留方式 | 接口契约、权限、兼容窗口及存储期限 |
| 集群资源、可用性及故障恢复目标 | HPA 上限、数据层高可用及运行成本 |

这些信息可以随分析逐步补充。指标未确定前，按 [性能需求](性能与容量需求.md) 的候选负载开展原型验证，并保留实际配置与结果。
