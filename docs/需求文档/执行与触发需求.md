# 执行与触发需求

状态：需求草案。实现建议见 [执行与调度设计](../设计文档/执行与调度设计.md)；多副本恢复及容量分别见 [可靠性需求](横向扩展与可靠性需求.md) 和 [性能需求](性能与容量需求.md)。

## 1. 调用方式

Action 与 Function 均支持同步、异步调用；限时等待可作为兼顾即时结果与后台运行的建议方式。

| 方式 | 返回行为 | 适用情况 |
| --- | --- | --- |
| 同步 | 等待完成并返回结果或错误 | 可在请求时限内完成的调用 |
| 异步 | 持久化接收任务后返回任务 ID | 耗时长、需要排队或重试的调用 |
| 限时等待（建议） | 提交持久任务，等待指定时间；未完成返回任务 ID | 希望尽快拿到结果，但允许转为后台查询 |

同步和异步使用一致的权限、定义版本及执行语义。同步边界由耗时分布与超时预算决定，不以 100 ms 作为统一标准。客户端超时不代表任务取消，也不代表外部操作未发生；客户端应能核对任务状态或通过幂等重试确认结果。

## 2. 执行记录与结果

执行记录至少需要关联调用者、定义版本、输入、状态、结果、错误、执行尝试、时间和幂等键。状态需表达等待、运行、成功、失败及取消，超时、重试和外部效果不明应能区分并追踪，具体状态表示仍为设计草案。

取消是尽力而为，不能保证撤销已产生的业务效果。异步任务需要支持结果轮询；SSE、Webhook 可作为通知扩展，通知允许重复、延迟或失败，任务状态查询是最终结果来源。Webhook 需明确鉴权及重试约定，结果保留期限与通知协议尚待确定。

## 3. 重复处理与运行隔离

消息与任务按至少一次处理设计，并通过幂等、执行租约及故障恢复维持可追踪性。外部写入需要接收方幂等或结果核对，不能仅凭消息确认承诺恰好执行一次。跨系统操作默认不保证原子事务，必须明确部分成功和补偿行为。外部效果不明时，应先核对而不是无条件重试。

多语言运行器需要按代码可信程度限制 CPU、内存、执行时间、文件和网络权限；业务凭据按调用身份提供，防止跨任务泄露。容器运行本身不等于完整代码沙盒。首批语言、脚本/容器/外部服务的优先级及依赖分发方式见 [执行与调度设计](../设计文档/执行与调度设计.md) 中的待定事项。

## 4. 事件与周期触发

业务数据提交成功后产生事件，按事件类型、对象和条件触发指定版本的 Action 或 Function。模型事件由 Metadata 负责，实例与关系事件由 Data 负责。触发应能处理重复、重试、失败留存及必要的对象级顺序；限制递归调用和循环触发。重放历史事件是否再次产生业务操作需要显式约定。

支持 CRON 等周期规则，需明确表达式格式、时区、启停、错过周期的处理、同一任务是否允许重叠及积压策略。多个调度副本不能因争抢同一周期而重复产生逻辑任务；外部副作用仍遵循上述幂等与核对规则。

## 5. 需求与验收

| 编号 | 要求 | 验收方法 |
| --- | --- | --- |
| RUN-01 | 支持同步/异步，共用权限与版本语义；异步受理前持久化 | 同一调用两种模式结果和权限一致；成功受理后可在任一服务副本查询 |
| RUN-02 | 执行记录可关联输入、版本、状态、结果及每次尝试 | 任务可追溯到具体定义和制品；轮询在通知重复或丢失时仍能得到权威结果 |
| RUN-03 | 超时和取消不被等同为外部效果撤销 | 覆盖客户端超时、执行超时、取消竞态及外部已经成功的情况，结果可核对 |
| RUN-04 | 重复处理和跨系统部分成功有幂等、核对或补偿规则 | 重试与重复事件不产生未经核对的重复效果；无法判断的操作保留待核对记录 |
| RUN-05 | 运行器资源及身份隔离可配置 | 验证资源超限可控、凭据按身份授予、不同任务文件与凭据不会越界 |
| TRG-01 | 事件触发只基于已提交变化，目标版本和重放语义明确 | 回滚不触发；重复、乱序、循环和重放样例按定义处理，失败可追踪 |
| TRG-02 | 周期触发明确时区、错过/重叠策略并可安全多副本运行 | 两调度副本争抢、重启错过周期、运行重叠及积压时结果符合配置 |

## 6. 待定事项

运行器语言与代码可信度、状态机与取消协议、重试/补偿条件、幂等记录保留期、事件顺序范围、CRON 格式与时区规则、通知与结果保留方式、同步超时预算均需在对应设计中完善。具体延迟与吞吐指标只在性能需求中维护。
