# 发布、版本与迁移

状态：方案草案，尚未实现。本文统一维护定义发布、平台/模型迁移、版本读取、恢复和验收。

## 1. 范围与数据所有权

| 类型 | 对象 | 触发来源 |
| --- | --- | --- |
| 平台数据库迁移 | 元数据、任务、调度等服务自身的数据表 | 平台软件版本发布 |
| Ontology 模型迁移 | Schema、Enum、Link 变化引起的实例数据、索引及物理结构 | 本体定义版本发布 |

需要提供专门的 migrate 机制，记录执行状态、失败原因和恢复进度。模型变化不一定产生 DDL，仍需校验数据与新定义的兼容性。

五类定义由 Metadata 对应模块维护，发布协调层通过窄接口检查引用；实例与关系迁移由 Data 执行，各服务平台表由各自迁移管理。模块实现版本、API 版本和 Ontology 定义版本分别表达。

## 2. 发布集与流程

建议引用包含稳定标识和版本，发布生成含完整引用关系的不可变发布集。计量属性的受控单位字典随发布集固定，详细规则见 [Schema](模块/Schema.md)；已有任务不能被新草稿或字典重新解释。

建议流程：`草稿 → 校验与差异分析 → 生成迁移计划 → 执行并记录进度 → 数据验证 → 激活版本`。

Metadata 负责定义、依赖检查及激活状态；涉及实例、关系、索引或物理结构时，通过受控接口向 Data 提交迁移计划。Data 所有的迁移任务执行并返回持久化进度及验证结果，Metadata 确认后切换激活指针。跨服务步骤通过状态机和幂等重试推进，不能假定共享事务原子完成全部发布。

计划应记录前置条件、影响范围、DDL（如需要）、回填任务、验证及恢复方式。发布中的定义不可任意修改，让各副本自行推断当前数据形态。发布失败保留可核对进度，达到激活条件前不切换新版本；具体状态和接口仍需细化。

## 3. 迁移执行与恢复

平台数据库迁移由各服务维护，跟随软件版本；Ontology 模型迁移由 Data 负责实际数据与结构变更，跟随本体发布。两者分别记录，执行器可为独立命令或部署 Job，不必建立常驻迁移微服务。

两类迁移共用 [存储引擎](存储引擎.md) 的方言、类型能力、目录读取及执行设施，各自保存迁移记录。MySQL、PostgreSQL、达梦的 DDL 事务性、锁及在线变更能力分别认证。GORM Migrator 可辅助生成或执行 DDL，`AutoMigrate` 不能替代发布计划、回填、协调及激活；在线服务启动时不自动执行结构迁移。

平台和模型迁移都需使用持久化记录、数据库锁或带租约的互斥机制，防止相同目标并发修改。锁失效后旧执行者还需被阻止继续写入；具体数据库如何隔离旧执行者、DDL 是否支持所需协调必须先验证，不能只检查租约过期时间就宣称并发安全。

在线变更优先考虑：`新增兼容结构 → 分批回填与校验 → 切换读写 → 删除旧结构`。是否双写、是否支持在线 DDL 取决于数据库版本及变更类型。回填保存检查点，分批提交，不能用一个长期事务完成全部大规模迁移。

删字段、缩小类型、删除 Enum 取值等操作可能无法逆转，需要事先说明备份恢复、补偿或向前修复方案。维护窗口和自动回滚能力逐项评估，不能以迁移框架存在为依据承诺无停机发布。

规范单位、物理量类型和转换规则变化同样需要兼容性评估；更改显示符号与将历史 kPa 数值转换为 Pa 是不同变更。按 Schema 的 SEM-07 处理历史值、阈值、字典版本和旧客户端。

## 4. 版本读取与滚动升级

请求入口解析一次发布版本并传给下游；已经受理的任务固定定义与制品版本。新旧 Schema 和物理结构在兼容窗口内共存，不兼容任务应阻止执行或按显式升级规则处理。

缓存以隔离域、发布版本和对象标识为键；事件可以加快更新，但正确性依赖版本读取及激活指针校验。Data 强制可写版本规则，避免旧客户端绕过新约束。模型发布完成产生的模型事件由 Metadata 负责，事件持久化与投递方式见 [执行与调度](执行与调度.md)。

## 5. 验收条件

| 编号 | 要求 | 验收方法 |
| --- | --- | --- |
| PUB-01 | 平台迁移与模型迁移分别记录，由对应数据所有者执行 | 能定位迁移目标、来源版本、执行状态和失败原因；软件升级与定义发布不会混用记录 |
| PUB-02 | 发布有校验、差异、计划、数据验证和激活条件 | 校验或迁移失败不能激活新版本；多副本对发布状态和指定版本读取保持一致 |
| PUB-03 | 迁移并发安全、失败可恢复，旧执行者不能继续提交 | 两副本竞争同一目标、回填中断及租约失效场景均有明确结果，恢复不重复破坏数据 |
| PUB-04 | 变更评估兼容窗口与可逆性，执行任务固定版本 | 滚动升级覆盖新旧服务和未完成任务；破坏性变更能给出维护、恢复或补偿方案 |

验证跨类型引用错误、Enum 兼容性、发布校验失败、迁移中断恢复、并发迁移、旧租约执行者、激活前后版本读取，以及滚动升级中未完成任务的版本一致性。

## 6. 待定事项

需根据三个目标数据库的具体版本与存储模型确定 DDL 能力、锁/租约及旧执行者隔离方式、差异分类、迁移计划格式、回填与切换、激活状态机、兼容窗口、备份恢复和破坏性变更流程。各模块接口尚未定稿，认证前不将特定数据库迁移算法作为通用保证。实体语义见 [Schema](模块/Schema.md)，关系查询见 [Link](模块/Link.md)，物理映射与驱动契约统一见存储引擎。
