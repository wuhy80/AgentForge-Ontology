# 工业 Agent Ontology Go 框架功能规划

## 1. 建设目标

系统需要把工业现场的设备、工艺、物料、组织、时序数据、事件、规则与 Agent 能力统一为可查询、可推理、可执行、可追溯的语义模型。它不是单纯的“知识图谱管理后台”，而是工业 Agent 获取上下文、形成计划、调用工具并验证执行结果的语义运行底座。

首期建议聚焦一个可验证闭环：**设备异常诊断**。系统接收设备告警，基于本体补全设备、测点、工艺和维护上下文，执行规则或外部推理，生成诊断建议，并完整记录证据和执行轨迹。

### 1.1 核心价值

- **统一语义**：解决 MES、SCADA、ERP、EAM、PLM 等系统对象命名和编码不一致的问题。
- **可解释决策**：Agent 的结论必须关联事实、规则、数据时间和来源，而不是只返回自然语言。
- **安全执行**：区分建议、仿真和真实控制，真实动作必须通过权限、策略与人工审批。
- **持续演进**：本体、规则、映射和 Agent 能力均可版本化、验证、灰度发布和回滚。

### 1.2 首期不建议做的内容

- 不自研通用大模型训练或推理平台，只通过适配器接入模型服务。
- 不替代现有时序数据库、MES、SCADA 或 EAM，只保存语义索引和必要快照。
- 不在 MVP 中直接闭环控制 PLC；先完成只读诊断和人工确认后的工单类动作。
- 不追求覆盖所有工业行业，先用可扩展的上层本体加一个垂直领域包验证。

## 2. 典型用户与用例

| 角色 | 主要诉求 | 典型用例 |
| --- | --- | --- |
| 本体工程师 | 建模、校验、发布和维护领域语义 | 定义泵、测点、故障模式及关系 |
| 集成工程师 | 接入异构数据并完成语义映射 | 将 OPC UA 节点映射为测点实例 |
| Agent 开发者 | 查询上下文、发现工具、执行工作流 | 构建异常诊断或维修助手 |
| 运维工程师 | 查看诊断依据并确认处置 | 审核建议、创建工单、反馈结果 |
| 安全/审计人员 | 控制访问并还原决策过程 | 检查某次动作的发起者和证据链 |

优先用例建议依次为：资产语义检索与问答；告警关联、故障诊断与处置建议；维修知识推荐与工单生成；工艺约束检查和操作前风险评估；能耗、质量及生产优化。

## 3. 功能全景

### 3.1 本体建模与生命周期

- 支持类、属性、关系、实例、枚举、约束及多语言标签。
- 支持命名空间、模块导入和领域包，避免形成不可维护的单体本体。
- 支持草稿、评审、发布、废弃状态，以及语义化版本号和变更说明。
- 提供版本差异、兼容性检查、迁移脚本、回滚和指定版本查询。
- 导入/导出至少支持 JSON-LD；后续按需要支持 RDF/Turtle、OWL、SHACL。
- 发布前校验重复标识、悬空关系、基数、数据类型、必填属性和循环依赖。

建议将模型分为上层本体、工业核心本体、行业领域包、企业扩展层和实例层。工业核心至少覆盖资产、设备、测点、工艺、物料、产品、告警、工单、人员、组织、位置、事件和文档。

### 3.2 语义图谱存储与查询

- 对实体和关系提供增删改查、批量写入、分页遍历和条件查询。
- 支持邻域、路径、子图、依赖和影响范围查询。
- 提供全文检索、标签/别名检索和向量语义检索，结果统一返回实体 ID。
- 查询支持租户、工厂、数据域、本体版本和有效时间过滤。
- 区分“当前状态”和“历史事实”，事实至少包含 `valid_time` 与 `observed_at`。
- 为 Agent 提供受控查询 DSL；底层 SPARQL/Cypher 可由适配器实现，不直接暴露给模型。

### 3.3 数据接入与语义映射

- 首期支持 REST、CSV/JSON、MQTT；随后接入 OPC UA、Kafka 和数据库 CDC。
- 提供外部字段到本体类、属性、关系的映射配置、转换函数和单位换算。
- 支持实体解析：按外部 ID、业务键、别名或组合规则识别同一对象。
- 记录数据来源、采集时间、质量码、映射版本和原始记录引用。
- 提供幂等键、断点续传、重试、死信队列、背压和接入质量指标。
- 大规模时序值保留在专业时序库；图谱只保存测点定义、数据引用和必要聚合结果。

### 3.4 规则、约束与推理

- **模型约束**：校验实例是否符合本体定义。
- **确定性规则**：根据事实推导风险、状态或候选故障。
- **关系推理**：传递关系、逆关系、层级继承和影响传播。
- **时序推理**：支持时间窗、持续时间、事件顺序和迟到数据处理。
- **外部推理**：可调用算法服务或大模型，但输出必须结构化并附带证据。
- 推理结果包含结论、置信度、证据集合、规则/模型版本、生成时间和失效时间。
- 规则提供测试样例、优先级、冲突消解、启停、版本、灰度和执行超时限制。

### 3.5 Agent 注册与编排

- Agent 注册信息包括身份、版本、职责、输入/输出 Schema、能力、工具和负责人。
- 能力注册表描述能力适用对象、前置条件、效果、风险等级和所需权限。
- 上下文构建器按任务检索相关子图、时序摘要、文档片段和历史案例，并控制 token 预算。
- 规划器将目标拆分为可验证步骤；执行器调用工具；验证器检查结果和本体约束。
- 优先支持单 Agent 工作流，后续再增加多 Agent 委派、协商、超时和终止策略。
- 每次运行保存输入、计划、工具参数、结果、证据、模型版本、耗时、成本和最终状态。
- 记忆分为会话、任务和经审核的长期知识，禁止模型输出直接污染知识库。

### 3.6 工具与工业动作网关

- 统一工具描述：名称、版本、Schema、超时、幂等性、风险等级和回滚能力。
- 工具适配 REST/gRPC、数据库查询、算法服务、EAM 工单和消息系统。
- 执行前完成参数校验、身份鉴别、策略判断和速率限制。
- 动作按风险分为 `read`、`recommend`、`write`、`control`。
- `write` 默认要求审批，`control` 默认禁用；启用时还需双人审批、联锁校验和紧急停止。
- 真实写操作使用幂等键，保存执行前后状态；支持仿真、dry-run、补偿或回滚。
- LLM 不能直接持有设备或业务系统凭据，所有调用必须经过动作网关。

### 3.7 安全、治理与合规

- 支持 OIDC/OAuth2 身份认证、服务身份和短期凭据。
- 授权采用 RBAC 与 ABAC 组合，属性至少包括租户、工厂、产线、资源、动作和风险等级。
- 对提示词、工具参数、敏感属性和凭据进行加密或脱敏。
- 外部文本标记为不可信数据，工具调用只接受 Schema 内字段，以防御提示注入。
- 审计日志防篡改，覆盖本体发布、数据变更、规则命中、Agent 决策、审批和动作执行。
- 支持数据保留、删除、导出以及按租户隔离；所有查询默认强制租户条件。
- 设置人工介入点、最大工具调用数、成本上限、超时和熔断策略。

### 3.8 可观测性与运营

- 统一 trace ID 串联数据接入、语义查询、推理、模型调用和工具执行。
- 指标包括查询延迟、摄取吞吐、规则命中、任务成功率、工具错误率、token 与费用。
- 记录结构化日志和分布式追踪，并提供告警、健康检查和依赖状态。
- 建立评测集，持续评估实体匹配、上下文召回、诊断准确率、证据完整率和误动作率。
- 支持任务回放与影子运行，在不执行真实动作的情况下比较新旧版本效果。

### 3.9 管理端与开发者体验

- MVP 采用 API/CLI 优先，同时提供 OpenAPI 文档、Go SDK 和可执行示例。
- 后续管理端包含本体浏览器、映射编辑器、规则测试台、Agent 运行详情和审批中心。
- 提供本地开发环境、示例领域包、模拟工业数据源和端到端诊断样例。

## 4. 核心领域模型

建议所有持久化对象包含 `id`、`tenant_id`、`version`、`created_at`、`updated_at`，所有事实额外包含来源与时间信息。

| 对象 | 关键字段 | 说明 |
| --- | --- | --- |
| Ontology | name, namespace, version, status | 本体发布单元 |
| Class | iri, labels, parent_ids, constraints | 概念定义 |
| Property | iri, data_type, unit, cardinality | 数据属性定义 |
| RelationType | iri, source_classes, target_classes | 关系类型定义 |
| Entity | class_id, external_ids, attributes | 具体工业对象 |
| Relation | type_id, from_id, to_id, valid_time | 实例间关系 |
| Fact | subject, predicate, value, provenance | 可追溯事实 |
| Rule | condition, conclusion, priority, version | 确定性推理规则 |
| AgentDefinition | capabilities, io_schema, tools, policy | Agent 定义 |
| ToolDefinition | input_schema, risk, timeout, endpoint | 工具定义 |
| AgentRun | goal, plan, status, evidence, trace_id | 一次运行记录 |
| ActionRequest | tool, arguments, risk, approval | 受控动作请求 |

事实来源至少应回答：数据来自哪个系统和记录、由哪个映射版本写入、何时观察到、质量如何，以及是否由某条规则或某个模型派生。

## 5. Go 总体架构建议

初期采用**模块化单体 + 异步 Worker**，先保证领域边界清晰，避免过早拆微服务。当摄取、查询或 Agent 执行出现独立扩缩容需求时，再按模块拆分部署。

```text
Client / CLI / Admin UI
          |
       HTTP/gRPC
          |
  API + Application Services
          |
  +-------+----------+-----------+-----------+
  | Ontology | Graph | Inference | Agent Run |
  +-------+----------+-----------+-----------+
          | ports (Go interfaces)
  +-------+----------+-----------+-----------+
  | PostgreSQL | Graph Adapter | TSDB | MQ   |
  +------------------------------------------+
                    |
             Connector Workers
```

### 5.1 推荐目录

```text
cmd/
  server/                 # API 服务入口
  worker/                 # 摄取、推理和任务 Worker
  ontologyctl/            # 管理 CLI
internal/
  ontology/               # 本体定义、版本和发布
  knowledge/              # 实体、关系、事实和查询
  mapping/                # 数据映射与实体解析
  inference/              # 规则与推理
  agent/                  # Agent 定义、规划和运行
  action/                 # 工具、审批和安全执行
  policy/                 # 授权及风险策略
  audit/                  # 审计与证据链
  platform/               # 配置、日志、数据库、消息等
api/
  openapi/                # HTTP 契约
  proto/                  # 内部或高吞吐接口契约
ontology/
  core/                   # 工业核心本体
  domains/                # 行业领域包
migrations/
test/
  integration/
  e2e/
deploy/
docs/
```

### 5.2 工程原则

- 领域层只依赖 Go 标准库和自身类型，通过小接口定义存储、消息和模型服务端口。
- API DTO、数据库模型与领域对象分离，避免协议或存储结构污染核心模型。
- 写操作使用事务；跨边界事件使用 outbox，消费端使用幂等键实现至少一次投递。
- 所有边界接收 `context.Context`，统一设置超时、取消和 trace。
- API 返回稳定错误码，日志中不得记录密钥、完整提示词或未脱敏工业数据。
- Schema、规则、本体与 API 均应在 CI 中执行兼容性检查。

### 5.3 存储选型策略

- **PostgreSQL**：租户、版本、权限、Agent 运行、审批和审计等强一致数据。
- **图存储适配器**：先以 PostgreSQL 关系表/递归查询完成 MVP；复杂路径需求明确后再选图库。
- **对象存储**：原始导入文件、文档、模型产物和大体积证据。
- **时序数据库**：复用现场已有系统，框架只定义 `TimeSeriesReader` 端口。
- **消息系统**：MVP 可用数据库队列/outbox；吞吐量增长后适配 Kafka/NATS 等。

不要在需求确认前锁定特定图数据库或大模型供应商，应以接口和契约隔离选型。

```text

POST   /v1/rules/{id}/test

POST   /v1/agents

```

所有写接口应支持请求 ID/幂等键；所有列表接口使用游标分页；长任务返回任务 ID，由客户端轮询或订阅事件，不占用长 HTTP 请求。

### 6.2 Go 核心端口示意

```go
type GraphRepository interface {
	UpsertEntities(ctx context.Context, entities []Entity) error
	Query(ctx context.Context, query SemanticQuery) (Subgraph, error)
}

type TimeSeriesReader interface {
	ReadWindow(ctx context.Context, pointIDs []string, window TimeWindow) ([]Series, error)
}

type ToolExecutor interface {
	Describe(ctx context.Context, toolID string) (ToolDefinition, error)
	Execute(ctx context.Context, request ActionRequest) (ActionResult, error)
}

type ModelProvider interface {
	Generate(ctx context.Context, request ModelRequest) (ModelResponse, error)
}
```

真实接口还应使用领域类型表达租户、版本、风险和来源，避免到处传递无约束字符串。

## 7. 非功能指标建议

具体数值需要通过现场规模校准，MVP 可先采用以下验收基线：

| 维度 | MVP 基线 |
| --- | --- |
| 可用性 | 核心只读查询月可用性 99.9% |
| 查询性能 | 单工厂常用一跳/二跳查询 P95 小于 500 ms |
| 接入能力 | 持续 1,000 条事实/秒，峰值通过队列削峰 |
| 数据正确性 | 幂等重放后无重复业务事实，来源信息完整率 100% |
| 可追溯性 | Agent 结论和动作的审计覆盖率 100% |
| 安全性 | 未审批高风险动作执行数为 0 |
| 恢复能力 | 明确 RPO/RTO，并通过定期恢复演练验证 |

这些指标应在领域试点前，依据实体数量、关系数量、测点规模、事件频率和并发任务数重估。

## 8. 迭代路线

### 阶段 0：需求与语义基线（1～2 周）

- 选择一个工厂、一个设备类型和一个异常诊断场景。
- 盘点数据源、业务编码、样例数据、系统接口和安全边界。
- 输出核心术语表、能力清单、数据契约、成功指标与测试金标集。
- 形成 20～50 个核心类、关键关系和 3～5 条可验证规则。

**退出标准**：同一诊断问题的输入、期望结论、证据和业务负责人均已明确。

### 阶段 1：Ontology MVP（3～5 周）

- 实现本体、实体、关系、事实的存储、版本、校验和查询 API。
- 实现 JSON-LD/CSV 导入、字段映射、来源记录和幂等写入。
- 建立设备、测点、告警、故障模式和工单的核心本体。
- 提供 CLI、OpenAPI、迁移脚本和基础可观测性。

**退出标准**：可重复导入试点数据，并稳定回答预先定义的资产与关系查询。

### 阶段 2：诊断 Agent 闭环（3～5 周）

- 实现规则引擎、上下文构建器、Agent 注册及运行状态机。
- 接入一个模型提供商和一个只读时序数据适配器。
- 诊断输出强制包含结构化结论、置信度和证据。
- 完成运行追踪、回放、失败重试和评测集自动化。

**退出标准**：在金标集上达到约定准确率，且每个结论都能追溯到事实或规则。

### 阶段 3：受控动作（2～4 周）

- 实现工具注册、风险分级、策略校验、人工审批与审计。
- 先接工单系统，支持 dry-run、幂等提交和结果回写。
- 开展故障注入、越权、提示注入和恢复演练。

**退出标准**：系统不能绕过审批执行高风险动作，工单全链路可回放。

### 阶段 4：规模化与行业扩展

- 增加 OPC UA/Kafka/CDC 连接器、行业领域包和管理端。
- 按压测结果优化索引、缓存和图存储，并按需拆分服务。
- 建立本体治理委员会、变更流程、SLO 和持续评测机制。

## 9. MVP 验收场景

以“泵振动异常诊断”为例：

1. MQTT 或 REST 写入告警，事件携带外部设备编码和时间。
2. 映射服务解析为设备实例，并关联测点、所在产线、设备型号和维护历史。
3. 上下文构建器读取告警前后时序窗口及适用规则。
4. 规则引擎生成候选故障；模型仅用于解释、排序或补充问题，不覆盖确定性约束。
5. Agent 输出候选原因、置信度、证据、建议检查项和风险等级。
6. 运维人员确认后，动作网关向 EAM 创建检查工单。
7. 系统保存从原始告警到工单结果的完整 trace，并用实际维修结果更新评测集。

验收测试至少覆盖正常路径、未知设备、缺少数据、迟到数据、规则冲突、模型超时、重复事件、越权调用、审批拒绝以及下游系统失败。

## 10. 关键风险与应对

| 风险 | 表现 | 应对策略 |
| --- | --- | --- |
| 本体过度设计 | 长期建模却无法形成业务价值 | 从诊断问题反推最小模型，按用例扩展 |
| 数据质量不足 | 编码不一致、时间错位、测点失真 | 来源与质量码必填，隔离低质量事实 |
| 图数据库先行 | 被特定产品语法和模型锁定 | 先定义领域端口，以真实查询压测选型 |
| 模型幻觉 | 生成无证据结论或虚构工具参数 | 结构化输出、证据校验、Schema 白名单 |
| 现场误动作 | Agent 直接操作控制系统 | 分级、审批、联锁、dry-run、紧急停止 |
| 知识污染 | 未审核输出进入长期知识 | 派生事实隔离、置信度、有效期与审核流 |
| 多租户泄露 | 查询或缓存跨工厂返回数据 | 存储、查询、缓存和日志全链路租户隔离 |

## 11. 启动前需要确认的问题

1. 首个行业、工厂、设备类型和业务场景分别是什么？
2. 主要使用者是谁，最终动作是建议、工单还是设备控制？
3. 现有 MES、SCADA、EAM、时序库、数据湖分别是什么，接口和数据样例是否可用？
4. 实体、关系、测点、事件日增量和并发 Agent 任务量级是多少？
5. 是否已有 ISA-95、OPC UA 信息模型、企业数据标准或知识图谱需要复用？
6. 部署在云、边缘还是混合环境，离线运行和国产化是否为硬性要求？
7. 哪些数据不能离开工厂，保存周期、审计和合规要求是什么？
8. 是否允许调用外部大模型，模型供应商、成本和响应时间约束是什么？
9. 谁负责本体和规则审批，变更的兼容性及回滚责任如何划分？
10. 试点成功由哪些可量化指标判断，例如诊断准确率、平均修复时间或误报率？

## 12. 建议的近期决策顺序

1. 先确定**试点用例和成功指标**，再确定本体范围。
2. 再确认**数据可得性和动作安全边界**，避免设计无法落地。
3. 用真实样本完成最小本体、映射和查询 PoC。
4. 根据查询与吞吐压测结果选择图存储和消息基础设施。
5. 最后确定大模型、管理端和多 Agent 等增强能力。

按这个顺序，可以把最早版本控制在“可解释的只读诊断”范围内，以较低风险验证 Ontology 是否真正提升 Agent 的上下文质量和工业决策效果，再逐步扩展到受控执行。
