# 部署、横向扩展与运维

状态：方案草案，尚无部署实现或故障实测。目标是在已验证的基础设施容量内，增加对应服务 Pod 即可提高处理能力，无需修改业务代码或人工分配任务。

## 1. 扩展边界

HTTP 服务副本应可替换，负载均衡无需绑定用户会话到特定 Pod。任务 Worker 通过持久化任务源领取工作。调度器允许多副本部署，但增加调度副本可能只提高可用性；是否增加调度吞吐取决于任务分片方案。

数据库、消息系统、对象存储和外部计算服务有独立容量上限。增加应用 Pod 不能自动消除数据库锁竞争、慢查询、连接耗尽或下游限流。扩容设计必须同时说明应用层容量和共享依赖容量。

## 2. 容器与发布方式

Docker Compose 用于本地或单机多副本验证，需配套入口负载均衡、服务发现及无冲突的端口配置。跨主机调度、自动弹性及故障恢复使用 Kubernetes 等平台；增加 Compose 副本本身不等于高可用或自动扩缩容。

在线服务和 Worker 分别建立 Deployment、配置、资源配额与弹性策略；入口通过 Service 发现可用副本。调度器允许多副本，先以选主实现故障接管；只有调度吞吐成为瓶颈时再增加分片。两种模式均保留持久化唯一约束及触发幂等。

readiness 表示能否接收新流量，startup 处理初始化，liveness 仅用于进程不可恢复的失效检测。依赖故障应暴露状态并限制流量，避免把数据库瞬断变成所有 Pod 重启。滚动发布时摘流、停止领取新任务，等待有界时长后退出，未完成任务由租约与恢复逻辑处理。

HPA 最大副本数须受数据库连接、集群资源和下游配额共同约束；Worker 以待执行任务和等待时间为主要负载信号。具体负载信号与连接预算见下文。多节点环境使用副本分散和适当的中断预算；这些不能替代数据库复制及备份恢复。

副本可替换并不禁止本地缓存，但正确性不能依赖某个副本的内存或本地磁盘。Redis 是否需要，按缓存与协调用途评估，不作为必选依赖。

## 3. 扩缩容信号

| 服务 | 主要信号 | 需要同时检查 |
| --- | --- | --- |
| Metadata | 请求率、CPU、响应时间 | 定义缓存命中率、发布写入冲突 |
| Data | 在途请求、CPU、延迟 | 数据库慢查询、连接等待、IO 和锁 |
| Execution | 接收速率、分派延迟、状态写入耗时 | 任务存储容量；Worker 积压不能仅靠增加 Execution 副本解决 |
| Worker | 最老任务等待时间、可运行任务量、活跃执行数 | 语言/资源类别、平均耗时、CPU/内存、外部接口配额 |
| Scheduler | 到期任务积压、触发延迟 | 领导者或分片分配、唯一约束冲突 |

Kubernetes HPA 可基于 CPU 或自定义指标扩缩容；队列弹性可选 KEDA 或自建指标适配。自动弹性是设计建议，手动增加副本也必须安全。须设置最大副本数、冷启动时间、缩容稳定窗口及最低可用副本；积压指标接入缺失时不能宣称已具备队列自动扩容。

## 4. 连接与资源预算

对同一个数据库端点，必须满足：

`Σ(服务峰值副本数 × 每副本连接池上限) + 迁移/运维预留连接 ≤ 数据库可用连接预算`

峰值副本数包含滚动升级临时增加的副本，连接池包含同一 Pod 内所有进程和 Worker 的连接。按每个数据库端点分别核算；必要时采用连接代理。资源请求与限制、连接池和任务并发应与压测配置一起记录。

[存储引擎](存储引擎.md) 为每个明确的连接配置持有长期复用的池，ORM 与直接 SQL 共享该池，不能每请求重新打开或由 ORM 隐式再创建一套。启动时检查驱动版本和必要能力，结构迁移由独立入口执行；数据库连接等待、占用、超时及语句执行指标需要纳入各库监控。

扩容遇到数据库饱和时，先根据实测定位索引、查询、锁和 IO，再决定增加数据库资源、读副本或分区。[Schema](模块/Schema.md) 定义同库分表/原生分区的路由、约束及维护迁移，性能对照见 [性能与容量](性能与容量.md)；同库分表仍共享数据库容量。副本延迟、跨库关系/事务和跨库扩容另行验证，不能视为增加应用 Pod 或物理表数的自然效果。

## 5. 验收条件

| 编号 | 要求 | 验收方法 |
| --- | --- | --- |
| SCALE-01 | 关键状态持久化；本地磁盘、内存缓存不作为唯一状态来源 | 请求在不同副本间读取一致的当前定义及任务；替换 Pod 后已接收任务可继续追踪 |
| SCALE-02 | 副本自动发现并接收负载，不依赖固定 Pod 地址 | 将服务从 1 扩到 2、4 个副本，观察各副本实际处理请求和吞吐变化 |
| SCALE-03 | 每个服务有独立资源配额、并发限制和扩缩容配置 | 单独扩容 Data 或一个 Worker 池，其他服务副本数无需变化；实例能读到配置 |
| SCALE-04 | 多 Worker 竞争任务安全；成功受理前持久化；恢复采用租约和尝试标识 | 在领取、业务执行、结果提交及确认之间终止 Worker，已接收任务均可追踪到恢复或明确终态，旧尝试不能覆盖新结果 |
| SCALE-05 | 请求、事件和周期触发有稳定幂等标识 | 重复投递、客户端重试和两个调度副本同时触发时，仅生成一个逻辑任务；外部效果按幂等协议核对 |
| SCALE-06 | 缩容与滚动升级支持摘流、停止领任务和有界退出 | 长请求、运行中任务遇到缩容仍可完成或被恢复；不兼容任务不能被错误版本 Worker 领取 |
| SCALE-07 | 当前定义生效和迁移有跨副本互斥及一致性 | 并发迁移不会重复修改目标；失去租约的执行者被拒绝；旧缓存不继续服务，请求不混合变更前后定义，不兼容变更期间受影响入口暂停 |
| SCALE-08 | 限制排队、并发、重试及数据库连接总量 | 达到下游预算后明确限流或排队，不能因扩容引发连接耗尽和无限重试；测试恢复后的积压消化 |
| SCALE-09 | 提供服务探针、资源及负载指标，自动弹性可配置 | 未就绪副本不接流量；可观测请求延迟、连接等待、队列长度/最老任务年龄、活跃任务与失败率 |
| SCALE-10 | 应用多副本与数据层恢复分别验证 | 杀死一个应用 Pod、短暂中断依赖、恢复数据库/任务存储分别演练，报告故障影响、恢复耗时和数据损失范围 |

任务“恢复”并不表示任意副作用可以自动重做。对支持幂等键的操作可以重试；无法确定外部效果的操作进入待核对状态，明确恢复或补偿流程。不能因队列确认或租约机制就承诺端到端恰好执行一次。

## 6. 故障验证与待定目标

正常吞吐测试与故障测试分别报告。故障测试记录：所有已成功受理的任务 ID、各次执行尝试、最终状态、重复效果核对结果、检测及恢复耗时。HTTP 超时请求允许客户端通过幂等键核对是否已受理。

初期至少验证两个应用副本和两个 Worker 的中途退出、一次滚动发布、重复事件、调度争抢及依赖短暂不可用。多副本部署时使用跨节点分布，才能验证节点级故障；单节点多 Pod 只能验证进程级恢复。

可用性、恢复时间（RTO）及允许丢失的数据时间范围（RPO）数值尚待确认。持久化确认后的任务可追踪性是业务要求；数据库自身损坏或丢失时的承诺，需要结合备份、复制和恢复策略单独定义。
