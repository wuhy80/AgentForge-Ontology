# 执行、任务与调度

状态：方案草案，尚未实现。本文统一维护 Function/Action 的调用、任务状态、故障恢复、事件/周期触发及验收。

## 1. 范围与服务协作

[Function](模块/Function.md) 与 [Action](模块/Action.md) 维护各自定义和运行要求；Metadata 负责定义，Execution 负责调用、持久任务、尝试和事件订阅，Worker 执行代码，Scheduler 负责周期登记。运行器清单、语言与制品方式统一见 Function。

## 2. 调用方式

Action 与 Function 均支持同步、异步调用；限时等待可作为兼顾即时结果与后台运行的建议方式。

| 方式 | 返回行为 | 适用情况 |
| --- | --- | --- |
| 同步 | 等待完成并返回结果或错误 | 可在请求时限内完成的调用 |
| 异步 | 持久化接收任务后返回任务 ID | 耗时长、需要排队或重试的调用 |
| 限时等待（建议） | 提交持久任务，等待指定时间；未完成返回任务 ID | 希望尽快拿到结果，但允许转为后台查询 |

同步和异步使用一致的权限、定义版本及执行语义。同步边界由耗时分布与超时预算决定，不以 100 ms 作为统一标准。客户端超时不代表任务取消，也不代表外部操作未发生；客户端应能核对任务状态或通过幂等重试确认结果。

## 3. 执行记录、状态与通知

同步与异步调用共用执行记录、权限和版本逻辑，返回行为见上文。Execution 持久化任务及待分派记录后确认受理，同步或限时等待模式在请求时限内等待同一任务的结果。

建议记录调用者、定义版本、输入、状态、结果、错误、尝试次数、时间和幂等键。状态候选包括 `queued`、`running`、`succeeded`、`failed`、`cancelled`，另行记录超时原因、重试状态和各次尝试。外部效果不明时需要待核对状态或标记，其具体表示及转换尚待确定，不能直接标为可重试失败。

取消不能撤销已经产生的业务效果。状态机需要明确请求等待超时、运行超时、取消请求和最终状态之间的关系。

异步任务支持结果轮询，任务查询提供权威结果。SSE、Webhook 可作为通知扩展；通知可能重复、延迟或失败。Webhook 需定义鉴权、重试及重复处理，结果保留和通知协议在具体接口设计时确定。

## 4. 分派、隔离与故障恢复

Worker 从持久任务源领取带租约的执行尝试，通过任务 ID 和尝试标识提交结果。Execution 拒绝过期尝试覆盖新结果，缩容时先停止领取新任务，再有界等待退出；未完成任务由恢复逻辑处理。

消息与任务采用至少一次处理，使用幂等键处理客户端重试及重复投递。平台租约只能限制平台状态写入，外部系统仍需接收方幂等或结果核对，不能因消息已确认就承诺端到端恰好执行一次。跨系统不默认有原子事务，部分成功需定义补偿；效果不明时先核对，不能直接重复执行。

任务成功受理、分派、运行、结果提交与确认之间的故障窗口均需验证。Worker 池按语言和资源类别独立部署，长任务、外部接口调用及 CPU 密集任务分别评估并发与扩容信号。

运行器按代码可信度限制 CPU、内存、执行时间、文件和网络访问，按调用身份提供凭据，任务工作目录与缓存按边界隔离。资源配置、运行时版本与制品需要可核对，不能仅凭使用容器就认定具备完整代码沙盒。

## 5. 事件触发

Metadata 负责模型事件，Data 负责实例与关系事件。建议用事务 outbox，在业务变更的同一个事务中持久化待发事件，提交后再异步投递至 Execution 的订阅分派模块。

事件至少携带事件 ID、类型、对象、定义版本、时间和追踪信息。订阅按事件类型、对象和条件匹配指定版本的 Action/Function；消费者按事件与订阅标识去重。需要定义重试、死信及必要的对象级顺序，不能把任意重放等同于重新执行业务动作。

触发链需限制递归及循环，重放是否再次触发、是否保留原定义版本应显式约定。重复投递与产生新业务操作的主动重放需要可区分的语义，具体标识协议仍待设计。

## 6. 周期触发

Scheduler 持久化 CRON 等规则，规则应包括表达式格式、时区、启停、错过周期处理、重叠执行和积压策略。选主或租约用于副本协调，吞吐需要时再考虑分片。

同一时间点用 `(schedule_id, scheduled_at)` 唯一登记待触发任务，登记及待发送记录在同一事务内持久化，再通过 outbox 重试提交 Execution。Execution 使用同一触发键去重，覆盖“已登记未发出”和“已发出未确认”两种窗口。唯一约束与任务幂等共同保证逻辑任务不重复，外部效果仍由接收方幂等及核对处理。

## 7. 验收条件

| 编号 | 要求 | 验收方法 |
| --- | --- | --- |
| RUN-01 | 支持同步/异步，共用权限与版本语义；异步受理前持久化 | 同一调用两种模式结果和权限一致；成功受理后可在任一服务副本查询 |
| RUN-02 | 执行记录可关联输入、版本、状态、结果及每次尝试 | 任务可追溯到具体定义和制品；轮询在通知重复或丢失时仍能得到权威结果 |
| RUN-03 | 超时和取消不被等同为外部效果撤销 | 覆盖客户端超时、执行超时、取消竞态及外部已经成功的情况，结果可核对 |
| RUN-04 | 重复处理和跨系统部分成功有幂等、核对或补偿规则 | 重试与重复事件不产生未经核对的重复效果；无法判断的操作保留待核对记录 |
| RUN-05 | 运行器资源及身份隔离可配置 | 验证资源超限可控、凭据按身份授予、不同任务文件与凭据不会越界 |
| TRG-01 | 事件触发只基于已提交变化，目标版本和重放语义明确 | 回滚不触发；重复、乱序、循环和重放样例按定义处理，失败可追踪 |
| TRG-02 | 周期触发明确时区、错过/重叠策略并可安全多副本运行 | 两调度副本争抢、重启错过周期、运行重叠及积压时结果符合配置 |

## 8. 基础设施与待定事项

持久化任务及 outbox 可先使用所属服务数据库。Kafka、RabbitMQ、NATS 属于不同特性的消息设施候选，Temporal 是工作流编排候选；这些工具职责不同，不要求同时引入。是否需要独立消息系统或工作流引擎，按任务持久性、吞吐和多步骤编排需求判断。

还需确定首批语言、代码可信度、脚本/容器优先级、依赖构建与分发、运行器协议、完整状态机、租约与重试规则、取消和补偿协议、幂等保留期、事件顺序与重放语义、CRON 语法/时区、结果保留和通知方式。性能数值只在 [性能与容量](性能与容量.md) 中维护。
