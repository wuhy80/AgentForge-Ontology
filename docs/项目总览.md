# 项目总览

状态：Ontology 需求分析与设计阶段，当前仅维护文档，尚未进入编码阶段。更新日期：2026-10-18。

## 1. 已明确的目标

1. 代码按模块组织，各类能力可以独立演进，控制模型辅助开发造成的代码膨胀；允许采用微服务。
2. 服务支持横向扩展，访问压力增长时可以通过增加对应服务的 Pod 扩容。
3. 性能满足业务要求，并有可重复的测量与验收依据。
4. 按模块维护一份完整说明，功能要求、实现方案、接口示例、验收和待定问题放在同一文档，适合单人持续开发。
5. 平台数据、五类定义及业务实例共用一套可注册数据库适配器的存储引擎，支持 MySQL、PostgreSQL、达梦等后端；选型以高频调用性能为首要验收条件，并说明选择理由。
6. 五类定义按租户、分类、分组组织；租户之间完全隔离，分类内五类定义不重名，名称只展示，内部保存及引用使用不同的稳定 ID，详见 [组织与隔离](组织与隔离.md)。
7. Schema 支持 db_2_schema 反向建模与 schema_2_db 正向生效，显式定义索引，并支持模型结构、差异和 SQL 预览，详见 [Schema](模块/Schema.md)。
8. Schema、Enum、Link、Action、Function 均只维护一份当前生效定义，不设置业务 version，引用只保存稳定 ID；编辑可有一份草稿，生效前检查依赖和必要迁移，统一规则见 [定义生效与迁移](发布与迁移.md)。
9. Schema 增加计算属性并关注查询及写入性能；建议按字段选择查询时计算、同事务保存或后台刷新，初期实现范围及候选策略见 [Schema](模块/Schema.md)，不预设所有公式都存储或都同步更新。
10. Schema 支持分表，一个逻辑 Schema 可对应多个物理表或分区，保持稳定 ID、租户隔离及全局查询/约束语义；布局、路由、预览和搬迁方案见 [Schema](模块/Schema.md)。
11. Link 创建后自动生成反向关系，两端均可发现并按正向、反向查找；建议以同一 Link ID 和方向视图共用关系事实，基数与生命周期同步，详见 [Link](模块/Link.md)。
12. Schema 间需要覆盖组合、上下级、继承等关系；实例归属/拓扑约束由 [Link](模块/Link.md) 说明，类型继承由 [Schema](模块/Schema.md) 说明，详细规则及首批范围为新增候选。
13. 产线设备需表达从前到后的顺序；进一步检查流向、依赖、连接、空间、时间、替代、互斥、角色及溯源等关系。顺序需限定在产线/路线等上下文，其他关系的约束和自动执行范围仍为候选，详见 [Link](模块/Link.md)。

“独立演进”包括独立修改、验证，以及服务级的独立构建、发布和扩容；涉及公共契约、跨对象约束或存储兼容性的变更，仍需显式协调。每个类型需要有清晰模块边界，是否单独部署取决于负载、数据一致性和维护成本。

## 2. 当前项目分析

| 关注点 | 仓库现状 | 当前缺口与本轮处理 |
| --- | --- | --- |

| 服务划分 | 现有架构草案采用多服务；工业规划保留模块化单体作为场景参考 | 当前建议采用单仓库、多服务部署；具体设计见 [总体架构](总体架构.md) |
| 组织与命名 | 已明确租户、分类、分组及展示名/ID 分离；尚无实现 | 分类内跨分组、跨类型唯一，租户隔离贯穿引用、查询、执行、缓存和数据源预览，见 [组织与隔离](组织与隔离.md) |
| 建模方向 | 已明确反向建模、正向生效、索引及预览；尚无实现 | 反向只读源结构，正向通过预览/迁移生效，索引按稳定字段 ID 定义，见 [Schema](模块/Schema.md) |
| 计算属性 | 已明确需要计算属性及性能取舍；尚无实现 | 轻量 virtual 与同实例 stored_sync 先落地，异步关联汇总作为候选扩展；依赖、索引、新鲜度及重建见 [Schema](模块/Schema.md) |
| 分表 | 已确认基础分表、关联来源/按值建表的阶段顺序及默认快照原则；尚无实现 | 分开声明取值来源、分配规则及建表时机；hash/range/list 为基础，关联属性和受控按值建表为后续扩展，具体协议及验证见 [Schema](模块/Schema.md) |
| 双向关系 | 已明确自动生成反向 Link 及正反向查找；尚无实现 | 创建一次即提供两端入口，方向基数自动交换，查询/增删共用边事实、租户权限和并发约束，见 [Link](模块/Link.md) |
| 关系语义与类型继承 | 原通用 Link 只能记录关联，尚未定义完整的组合、层级及继承约束；尚无实现 | 新增聚合/组合与树/DAG 的独占、防环及生命周期候选，以及 Schema 单继承、有效字段、抽象类型和显式子类型查询候选，规则分别见 Link、Schema |
| 顺序与其他业务关系 | 新明确产线设备前后顺序，通用有向边不等于有序成员；尚无实现 | 新增按上下文排序、前驱/后继与任意先后、工艺流向、对称及关系属性/有效时间候选；区分记录关系与自动推理、调度或控制，关系清单见 Link |
| 对象保存与批量读写 | 正在讨论每个 Schema 的单条/批量 CRUD，尚未确认接口及事务协议；尚无实现 | 建议由统一 Data 引擎动态提供能力，复用校验、计算和分表规则；对象与关系组合提交限定本地事务，大规模导入按块追踪，见 [数据读写](数据读写.md) |
| DataSet 查询与多跳性能 | 已要求独立的数据查询目录及 DataSet 文档；查询抽象、协议和范围为候选，尚无实现或实测结果 | 建议组合筛选/投影/关系路径/聚合，由服务端延迟编译执行；查询规则独立见 [DataSet](数据查询/DataSet.md)，成本对照见 [性能与容量](性能与容量.md) |
| 定义更新 | 已明确取消五类定义的业务版本；尚无实现 | 每对象一份当前定义、引用只含 ID，草稿及迁移校验后生效；运行任务保持本次执行内容，见 [定义生效与迁移](发布与迁移.md) |
| 横向扩展 | 已讨论无状态、租约、幂等及多副本；尚无部署配置 | 补充扩容条件、数据库连接预算、缩容与故障验收，见 [部署与运维](部署与运维.md) |
| 数据库适配 | 已明确统一引擎及 MySQL/PostgreSQL/达梦目标；尚无驱动代码或压测 | 建议复用标准 Go 驱动与 GORM v2，热点使用显式 SQL，选型理由及适配契约见 [存储引擎](存储引擎.md) |
| 性能 | 工业规划有候选数值，缺少统一数据集、环境与测试记录 | 建立按工作负载区分的候选基线，见 [性能与容量](性能与容量.md) |
| 文档 | 五类模块各自维护一份说明，公共机制按专题维护 | 同一规则只保留一个来源，工业规划作为远期场景参考 |

因此，目前能评估的是方案是否具备满足目标的条件；不能认定系统已支持横向扩展或已达到任何吞吐、延迟指标。

## 3. 基础引擎的候选范围

五类模块分别见 [Schema](模块/Schema.md)、[Enum](模块/Enum.md)、[Function](模块/Function.md)、[Action](模块/Action.md)、[Link](模块/Link.md)，公共流程见 [发布与迁移](发布与迁移.md) 和 [执行与调度](执行与调度.md)。以下用于划定范围，各文档中的建议和待定事项仍需逐项确认。

| 能力 | 基础范围 |
| --- | --- |
| 组织 | 租户、分类、分组、分类级名称唯一性、稳定 ID 和全链路租户隔离，见 [组织与隔离](组织与隔离.md) |
| 建模 | 五类当前定义及 ID 引用；Schema 双向建模、分表、索引、结构/差异/SQL 预览，以及属性、物理量和单位语义见 [Schema](模块/Schema.md) |
| 生效 | 当前依赖检查、草稿替换、平台迁移和模型数据/结构迁移，无业务版本选择 |
| 数据 | 实例与关系读写、自动反向关系及正/反/双向有界路径查询，见 [Link](模块/Link.md)；DataSet 筛选/多跳/聚合及分页候选独立见 [数据查询](数据查询/README.md)，动态 CRUD、批量及组合事务候选见 [数据读写](数据读写.md) |
| 关系语义（新增候选） | 组合/聚合、树/DAG 与单继承，以及产线顺序、作用域、对称/派生及关系属性；扩展清单覆盖流向/依赖/连接/空间/时间等，优先级和首批范围待确认，不自动扩大已确认基础范围，见 Schema 和 Link |
| 存储 | 平台与实例共用存储引擎、驱动注册及能力声明；三个目标后端分别通过正确性与性能验收 |
| 执行 | 同步与异步调用、持久任务、状态查询、超时和幂等处理 |
| 触发 | 事件和周期触发，支持多副本协调 |
| 部署 | 容器化、独立服务、多副本、基础监控和容量验证 |

首期以 MySQL、PostgreSQL、达梦为数据库适配目标：先验证三库关键能力，再以一个后端打通闭环，随后补齐共同验收；单个部署初期可只使用其中一种。目标数据库版本和首个闭环后端待原型确定，不能只完成一个后端就宣称已支持三库。Go 是服务实现方向，首期选择一种实际可用的语言运行器。工业诊断、Agent 编排、设备控制、图算法、向量检索及完整 OWL/RDF 推理属于后续独立范围，不自动进入基础版本。

| 读数语义可解释 | SEM-01～SEM-08 | 读取获得与实际值匹配的单位及字段描述；历史结果自描述，单位变更先迁移数据 |

| 性能可验收 | PERF-01～PERF-06 | 在确定的数据、查询、硬件和版本下出具延迟、吞吐、错误率与扩容曲线 |
| 文档可持续维护 | DOC-01～DOC-03 | 模块说明及公共专题可定位到实现和验收记录 |

### 文档要求

- **DOC-01**：每个模块或公共主题只维护一份说明，包含目的、范围、规则、实现方案和可观察的验收结果；按需要补充接口示例。
- **DOC-02**：明确区分已明确目标、建议方案、待定指标和实测结果，草案数值不能写成已达成能力。
- **DOC-03**：一种规则或指标保留一个定义来源；新增文档更新 [文档入口](README.md)，重要取舍在所属文档记录原因及影响。

## 5. 建议实施顺序

以下为进入编码阶段后的规划；当前仅更新需求、设计、示例及验收文档，不启动工程实现。分表的已确认阶段顺序统一见 [Schema](模块/Schema.md) 第 4 节。

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| A：契约与边界 | 组织/类型模型、双向建模与预览协议、服务所有权、存储引擎接口、候选负载 | 租户及稳定 ID 边界、定义/实例/执行状态责任清楚；三库目录、索引及关键能力可核对，ORM 与直接 SQL 有首轮对照 |
| B：建模与查询 | Metadata、Data、双向建模/分表/索引/预览、迁移命令与适配包 | 先跑通一个后端再补齐三库共同用例；反向导入、预览、正向生效、同库分表及查询闭环可运行，从第一版验证两个租户和两个副本 |
| C：执行与触发 | Execution、一个 Worker、Scheduler | 同步/异步、重复提交、任务恢复与周期去重可验证 |
| D：容量与发布 | Kubernetes 部署、压测报告、扩缩容策略 | 完成 1/2/4 Pod 对比、混合负载、故障恢复和滚动升级验证 |

每个阶段控制交付范围，不用文件数量或服务数量代替功能完成度。阶段 D 的性能结果决定是否需要缓存、查询预计算、独立消息系统或存储扩容。
