状态：首批后端与中文前端工作台已有实现，已补齐本地账号登录、用户与角色管理、权限策略配置闭环；完整设计与当前实现分别标记。更新日期：2026-11-07。

## 1. 已明确的目标

1. 代码按模块组织，各类能力可以独立演进，控制模型辅助开发造成的代码膨胀；允许采用微服务。
2. 服务支持横向扩展，访问压力增长时可以通过增加对应服务的 Pod 扩容。
3. 性能满足业务要求，并有可重复的测量与验收依据。
4. 按模块维护一份完整说明，功能要求、实现方案、接口示例、验收和待定问题放在同一文档，适合单人持续开发。
5. 平台数据、五类定义及业务实例共用一套可注册数据库适配器的存储引擎，支持 MySQL、PostgreSQL、达梦等后端；选型以高频调用性能为首要验收条件，并说明选择理由。
6. 五类定义按租户、分类、分组组织；租户之间完全隔离，分类内五类定义的中文业务名称不重名。定义维护和 DataSet 编写使用中文 Schema、属性及 Link 等名称，内部解析、保存及引用使用稳定 ID，改名不改变已有绑定身份，详见 [组织与隔离](组织与隔离.md)。
7. Schema 支持 db_2_schema 反向建模与 schema_2_db 正向生效，显式定义索引，并支持模型结构、差异和 SQL 预览，详见 [Schema](模块/Schema.md)。
8. Schema、Enum、Link、Action、Function 均只维护一份当前生效定义，不设置业务 version，引用只保存稳定 ID；编辑可有一份草稿，生效前检查依赖和必要迁移，统一规则见 [定义生效与迁移](发布与迁移.md)。
9. Schema 增加计算属性并关注查询及写入性能；建议按字段选择查询时计算、同事务保存或后台刷新，初期实现范围及候选策略见 [Schema](模块/Schema.md)，不预设所有公式都存储或都同步更新。
10. Schema 支持分表，一个逻辑 Schema 可对应多个物理表或分区，保持稳定 ID、租户隔离及全局查询/约束语义；布局、路由、预览和搬迁方案见 [Schema](模块/Schema.md)。
11. Link 创建后自动生成反向关系，两端均可发现并按正向、反向查找；建议以同一 Link ID 和方向视图共用关系事实，基数与生命周期同步，详见 [Link](模块/Link.md)。
12. Schema 间需要覆盖组合、上下级、继承等关系；实例归属/拓扑约束由 [Link](模块/Link.md) 说明，类型继承由 [Schema](模块/Schema.md) 说明，详细规则及首批范围为新增候选。
13. 产线设备需表达从前到后的顺序；进一步检查流向、依赖、连接、空间、时间、替代、互斥、角色及溯源等关系。顺序需限定在产线/路线等上下文，其他关系的约束和自动执行范围仍为候选，详见 [Link](模块/Link.md)。
14. 支持使用中文 Schema、属性及 Link 名称编写 OntologySQL 查询；建议文本解析后降低为 DataSet 共用 QuerySpec，再由统一查询引擎执行，避免重复维护关系、分表与权限规则，路线比较及语法候选见 [OntologySQL](数据查询/OntologySQL.md)。
15. Ontology 需要灵活配置的行过滤、列过滤及 Action、Function 调用限制；实测后本轮选择 OPA 1.21.2，验证记录、统一权限模型及执行/撤权边界见[权限设计](权限/权限设计.md)，接入协议和具体规则仍为候选。
16. 增加中文可视化查询编辑器并重视使用体验；推荐在同一工作台逐步配置，自动检查、显式运行，以中文条件和关系构造共享查询描述。页面、错误恢复、SQL 互通、组件候选及体验验收见[可视化查询编辑器](数据查询/可视化查询编辑器.md)，具体交互和范围仍为候选。
17. 提供用户管理及正常登录入口，管理用户与权限；用户于 2026-11-07 明确不接受手工签发、复制并粘贴凭证的工作台登录方案，已按本地账号密码与可撤销服务端会话落实，当前闭环与剩余边界统一见[权限设计](权限/权限设计.md#用户管理要求与实现缺口2026-11-07)。

“独立演进”包括独立修改、验证，以及服务级的独立构建、发布和扩容；涉及公共契约、跨对象约束或存储兼容性的变更，仍需显式协调。每个类型需要有清晰模块边界，是否单独部署取决于负载、数据一致性和维护成本。

## 5. 建议实施顺序

以下为完整目标的分阶段规划。当前已按 MySQL 优先推进 A、B 阶段的首批闭环，交付范围见上文“当前实现与验证”，尚未完成两个阶段的全部条件。分表的已确认阶段顺序统一见 [Schema](模块/Schema.md) 第 4 节。

| 阶段 | 交付物 | 完成条件 |
| --- | --- | --- |
| A：契约与边界 | 组织/类型及权限模型、双向建模与预览协议、服务所有权、存储引擎接口、候选负载 | 租户及稳定 ID 边界、定义/实例/执行状态责任清楚；冻结首批授权语义并完成引擎对照；三库目录、索引及关键能力可核对，ORM 与直接 SQL 有首轮对照 |
| B：建模与查询 | Metadata、Data、行列授权、双向建模/分表/索引/预览、迁移命令与适配包 | 先跑通一个后端再补齐三库共同用例；反向导入、预览、正向生效、同库分表及查询闭环可运行，从第一版验证两个租户和两个副本及读写授权 |
| C：执行与触发 | Execution、一个 Worker、Scheduler、调用与任务授权 | 同步/异步、重复提交、任务恢复与周期去重可验证；直接/间接调用、执行身份、结果访问和撤权遵循确认后的权限契约 |
| D：容量与发布 | Kubernetes 部署、压测报告、扩缩容策略 | 完成 1/2/4 Pod 对比、混合负载、故障恢复和滚动升级验证 |

每个阶段控制交付范围，不用文件数量或服务数量代替功能完成度。阶段 D 的性能结果决定是否需要缓存、查询预计算、独立消息系统或存储扩容。
