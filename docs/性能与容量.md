# 性能与容量

状态：性能规划草案；本文件全部候选数值均待业务确认和实测，不代表当前能力。

## 1. 可验证的性能要求

| 编号 | 要求 | 验收输出 |
| --- | --- | --- |
| PERF-01 | 每个指标绑定数据集、访问形态、并发、环境和版本 | 可重复执行的压测配置与数据生成说明 |
| PERF-02 | 按请求类型统计端到端延迟、吞吐及错误 | P50/P95/P99、实际成功请求率、超时/失败/拒绝比例；不能只报告平均值 |
| PERF-03 | 对查询、写入、提交任务、执行任务分别建基线 | 单类与混合负载报告，任务等待与运行时间分别统计 |
| PERF-04 | 横向扩容需验证有效吞吐提升及共享依赖余量 | 1/2/4 Pod 曲线、连接/CPU/IO/锁和队列情况，以及饱和原因 |
| PERF-05 | 超载不能导致无限内存增长、无限排队或失控重试 | 限流、排队上限、超时、过载恢复与任务核对结果 |
| PERF-06 | 与同环境基线比较，显著退化需调查后再发布 | 关键请求 P95、吞吐、资源消耗的差异及原因；候选调查阈值为退化 10% |

P95 表示 95% 的该类请求延迟不超过该值。测量从压测客户端计划发出请求到完整接收响应，包含入口、网络、鉴权及服务内调用；使用能记录发送滞后的工具，避免系统变慢后发包变少而隐藏排队。报告成功请求的延迟，同时单列所有失败、超时及未完成请求；不能删除慢请求再计算达标率。

## 3. 候选服务指标

下表各行独立施压，不将各行请求率相加作为已支持的系统总吞吐。要求在目标到达率下同时满足延迟和错误率，P99 也必须记录，正式门槛待实测确定。

| 工作负载 | 候选到达率 | 候选 P95 | 限定条件 |
| --- | --- | --- | --- |
| 当前生效定义读取 | 100 请求/秒 | ≤ 100 ms | 返回单个当前定义，固定测试内容摘要，记录缓存及权威当前状态校验成本 |
| 实例按 ID 查询 | 200 请求/秒 | ≤ 100 ms | 命中索引，返回约 2 KiB 对象 |
| 实例过滤与分页 | 100 请求/秒 | ≤ 200 ms | 选择性约 1%，有匹配索引，首个游标页最多 100 条 |
| 1～2 跳关系查询 | 100 请求/秒 | ≤ 500 ms | 普通分支、固定查询集；正向/反向分别统计，热点单列 |
| 3～4 跳关系查询 | 10 请求/秒 | ≤ 1,500 ms | 有选择性过滤和执行预算，单独统计各条路径 |
| 单实例写入 | 100 请求/秒 | ≤ 300 ms | 包含约束校验及持久化确认，不含批量导入 |
| 异步任务提交 | 100 任务/秒 | ≤ 200 ms | 约 2 KiB 参数，返回前持久化任务及待分派记录 |

正常负载下，平台错误及超时比例候选目标为 ≤ 0.1%。有效请求被 429/503 拒绝也计入未达标请求；故意构造的非法请求单独测试。业务 Function 自身失败单列，不能掩盖平台错误。热点或超预算查询的验收是有界拒绝/终止和对其他请求的隔离，不能直接套用普通查询的延迟。

混合负载建议从总计 500 请求/秒开始：按 ID 读取 30%、过滤分页 30%、1～2 跳查询 20%、单实例写入 10%、任务提交 10%。对每类请求分别验证上表延迟与错误率，避免快速请求稀释慢查询。模型发布和回填并行运行的干扰测试另行报告。

该混合比例产生 50 任务/秒，不能直接套用下节 10 任务/秒的 Worker 基线。若仍执行每任务约 100 ms CPU 的函数，仅计算就需要约 5 个满载 CPU 核，另需预留运行器及利用率余量；必须配置足够 Worker 或另选并明确测试函数。只测提交的实验需固定时长、队列上限和清理方式，不能把持续积压时的受理吞吐称为稳态处理能力。

## 4. 任务执行的性能口径

任务完成时间拆成：`提交受理 + 排队等待 + 运行器准备 + 实际执行 + 结果持久化`。平台不能为任意用户代码、大模型或外部接口统一保证完成时间。

首轮使用固定定义内容及制品摘要、无外部网络、执行约 100 ms CPU 工作的函数，在选定运行器预热后测试。候选到达率 10 任务/秒、排队等待 P95 ≤ 1 秒，分别报告运行耗时、容器/进程准备时间和完成吞吐。真实语言依赖加载、长任务、大内存任务和冷启动另建数据集。

稳态需要完成速率覆盖提交速率，队列最老任务年龄和长度不能持续增长。按类型估算所需并发：`任务到达率 × 平均占用时间 ÷ 目标利用率`，再结合每任务 CPU/内存与下游配额确定副本数。突发流量允许积压时，应另定可接受等待时间和消化期限。

## 5. 压测与扩容方法

1. 固定服务、协议、数据集和基础设施版本，校验查询结果与写入效果正确；记录样本数和资源限制。
2. 候选流程为预热 5 分钟、稳态 30 分钟、重复 3 次；数据规模变化、写入清理及缓存处理策略须保持可比。低频场景需补足样本，P99 不足以稳定估计时明确标注。
3. 各类请求单独测，再按混合比例测；用逐步增加的开放到达率找到同时满足延迟与错误率的最大成功吞吐。
4. 单独将 Data 或同一 Worker 池改为 1、2、4 Pod，每 Pod 资源相同，其余组件与数据保持固定且有容量余量。分别测最大达标吞吐，避免固定低请求率掩盖扩容效果。
5. 报告 `扩容效率 = N 副本达标吞吐 ÷ (N × 单副本达标吞吐)`。当瓶颈确在应用层且依赖有余量时，候选目标为 2 Pod 达到至少 1.6 倍、4 Pod 至少 3 倍；共享依赖饱和则报告上限和原因，不能宣称线性扩展。
6. 单独做超载与故障测试：达到限额、热点关系、Worker 退出、依赖中断、缩容及滚动升级；按 [部署与运维](部署与运维.md) 核对任务与恢复情况。

正式报告至少包含配置、数据生成方式、请求集、到达率与实际成功率、P50/P95/P99、错误分布、CPU/内存/连接/IO/锁、队列等待、原始结果位置和瓶颈结论。没有这些条件的单一“QPS”数字不能作为容量承诺。

## 6. 存储引擎选型对照

[存储引擎](存储引擎.md) 建议复用 GORM v2 基础能力，并保留同一连接与事务体系中的直接 SQL 热点路径。性能对照必须在大范围业务开发前完成首轮，不能到最终部署时才发现 ORM、方言或物理布局不适合。

### 对照方式

MySQL、PostgreSQL、目标达梦版本分别测试，不用其中一个数据库的结论替代其余后端。每个后端固定服务器/通信驱动/方言版本、存储布局、索引、统计信息、连接池、事务隔离、持久化配置、参数、投影和返回数据量。

| 对照项 | 用途 |
| --- | --- |
| 原生 `database/sql` + 显式 SQL/扫描 | 相同业务操作的最低公共基线，仍保留必要事务、结果校验和持久化 |
| 引擎内 GORM CRUD | 测固定记录的对象映射、语句构造和回调成本；提取实际 SQL 核对往返次数 |
| 引擎内直接 SQL + 显式扫描 | 测引擎包装成本，以及绕过 ORM 热点后能否接近基线；必须走同一池/事务与观测设施 |
| GORM Raw/SQL 构造（按需） | 分辨 SQL 构造与对象扫描开销；不能自动视为等同原生执行 |

隔离框架开销时使用相同 SQL、参数、结果及事务次数；ORM 自动生成的 SQL 若不同，先单独报告计划/往返差异，再做相同 SQL 对照。默认写事务、日志、缓存及预处理开关全部记录，不能给基线和候选使用不同一致性语义。每种方案分别调优后的结果另列，附调优原因。

### 代表性用例

| 用例 | 需要发现的问题 |
| --- | --- |
| 当前定义读取、批量获取、状态校验与缓存回源 | 框架分配、文档解码、当前状态校验、反复查元数据及冷启动集中回源 |
| 实例按键读、数值/时间筛选及游标翻页 | decimal 扫描、单位归一化、索引使用、深分页和动态投影成本 |
| DataSet 条件、关系存在性、有限展开及分组 | 按独立 [DataSet](数据查询/DataSet.md) 文档核对 N:M 根对象去重、逐父分页和聚合基数，测同语义 SDK/JSON/OntologySQL 的编译及执行成本；精确总数单独计量和统计，不默认每页全量 COUNT |
| 1～4 跳正反向 Link，普通/热点分别测 | JOIN/EXISTS 计划、基数估算、N+1、扫描与结果预算 |
| Link 自动正反入口发现及 both 查询 | 固定参与关系数、同租户跨分类端点和自关联数据，记录两端 Metadata 索引、方向缓存校验及 both 的全局去重/分页成本；同一边双向可见且不重复计数，边事实不因反向入口翻倍 |
| 组合/树/DAG 候选约束及查询 | 固定树深、分支、DAG 多父及约束范围；比较认领/换父、并发防环、归属登记和有界祖先/后代查询的锁等待、扫描及写放大；先核对 LINK-05～LINK-06 正确性，不套用普通邻接查询的性能结论 |
| Schema 继承及子类型端点候选 | 固定继承深度、具体子类型数、表/分表数和总行数，比较精确读取、显式多类型查询及双向 Link 的计划与全局分页；记录有效定义展开/缓存和基类变更的迁移成本，核对 SCHEMA-15～SCHEMA-17、LINK-07 |
| 有序产线/路线及直接前后候选 | 固定范围数、成员数、重复位置、并发编辑及插入/移动比例，测量有序页、邻居、任意先后、冲突重试及重排的扫描/锁/写放大；按 LINK-08～LINK-09 验证，不用设备全局排序或全图扫描替代范围索引 |
| 对称/派生与关系属性/有效时间候选 | 固定上下文数量、区间重叠、属性大小及推导深度，按 LINK-10～LINK-11 先核对事实、权限、去重和时态约束，再比较双向计划、索引/存储成本及查询预算；不声称已提供完整空间或流程引擎 |
| 单条/批量实例写入 + outbox、批量读取 | 按 [数据读写](数据读写.md) 固定对象数、字段、字节、分表及一致性语义，比较实际 SQL/网络往返、参数上限、提交次数、锁、失败回滚和成功对象吞吐，不以请求数掩盖批量大小 |
| 对象创建与产线关系组合提交 | 校验对象、成员、序列、同步计算及 outbox 的同事务效果；记录约束检查、并发竞争和事务耗时，注入失败无孤立对象或半链；不能以多个独立提交作为原子事务的性能替代 |
| 多副本任务领取、幂等创建和条件更新 | 唯一键竞争、锁等待、死锁及过期尝试；对应方言的竞争策略是否可扩展 |
| 模型扩展、回填和当前定义替换 | DDL 锁、暂停及恢复时间、缓存校验、旧计划、迁移 IO 与在线兼容变更的延迟干扰 |

实例数据规模沿用上文；候选并发档位为 1/16/64/128，批量大小为 1/100/1000，均受真实驱动参数和资源上限约束。不同到达率、连接池大小分别做实验，不同时改变多个变量。定型有类型列布局前，与候选文档布局对比相同过滤/关联用例，并报告两者的索引和迁移成本，避免把布局优势误算为 ORM 优势。

### 测量与选择条件

数据库端到端测试统计最大达标吞吐、P50/P95/P99、错误率、实际 SQL/计划、每操作往返次数、CPU、内存、锁、IO、连接等待和回滚结果。使用 Go benchmark 与 pprof 补充编译、参数绑定、扫描的 `ns/op`、`B/op`、`allocs/op`、CPU 和 GC 数据；纯 Go 微基准只能定位开销，不能替代数据库性能结论。

1. 首先通过 DB-01～DB-06 的适用正确性检查及本文件对应服务指标。为提速损失精度、权限、事务或持久化的方案不参与比较。
2. 候选热点门槛：在相同资源和业务语义下，引擎的最大达标吞吐不低于原生基线的 90%，共同稳态负载下 P95 不高于基线的 110%。P99、CPU/分配及绝对延迟同时报告，不能只凭平均值判断；这些是待原型校准的验收目标，不是已有测量结果。
3. 达不到门槛时按证据处理：SQL/索引问题先修查询计划；ORM CPU/分配显著时切换该路径为直接 SQL/扫描；引擎自身过重时精简公共路径；数据库资源成为瓶颈时报告容量上限。原生基线也未达服务目标时，不能只换 ORM 就认定解决。
4. 固定结构 CRUD 若已达标且额外成本可接受，保留 GORM 以降低维护量；高频路径按实测选择实现。最终在存储引擎文档记录各路径的选择、理由、版本及报告位置。
5. 初期逐后端报告容量，随后在同一数据库内验证 1/2/4 Pod 曲线。不同数据库都能正确执行同一接口，不代表它们具有相同吞吐；尚未测的后端明确标注未验证。

当前没有上述实测结果，本轮选型基于能力、可控的执行路径和维护成本，性能结论待原型验证。

## 7. 计算属性的性能对照

计算属性的策略、依赖及新鲜度语义由 [Schema](模块/Schema.md) 唯一维护。本节比较 virtual、stored_sync 和候选 stored_async；先核对结果、单位、权限、分页及声明的一致性，异步旧快照不能与即时结果混为相同的实时性能。

| 对照负载 | 需要固定及测量的内容 |
| --- | --- |
| 同实例轻量公式，例如电压 × 电流 | 相同 decimal 精度及数据，比较 SQL 按需计算、当前页应用计算、同步派生列读取，报告每行成本与端到端差异 |
| 按计算值过滤、排序和分页 | 相同结果及选择性，比较表达式扫描、已认证表达式索引和物化列索引，记录真实候选/扫描行数、计划与索引空间 |
| 不同读写比、计算投影率及批量 | 固定总行数及公式，改变读取/依赖更新的比例；记录未投影是否跳过、写入 P95、事务/锁/索引成本及无关字段更新的重算次数 |
| 关联汇总与依赖链 | 普通/热点节点分别测，固定平均及最大扇出、链深、去重语义与单目标源数据量；测 JOIN 聚合与后台合并刷新，不逐实体远程调用 |
| 异步稳态及突发 | 报告每次源变更的影响目标数、合并前后任务数、完成率、最老待办年龄及恢复时间；源捕获、排队和计算合计 P95/P99 新鲜度，水位未知单列 |
| 公式更新与全量重建 | 报告迁移/回填的读写 IO、索引构建、暂停时间、变更追平和旧任务拒写；不能用生效后仍返回旧公式值降低成本 |

初始规模沿用现有 100 万实体、普通平均出度约 5 和万级出度热点数据，计算字段数、依赖深度、投影比例及源更新频率在每组报告中固定。另用扩大影响范围的场景定位扇出上限，不能由普通节点结果推断高扇出仍可同步处理。

与无计算属性的相同读写工作负载对照，分别报告读侧节省和新增写放大、CPU、内存、扫描、存储/索引空间及事件量。重复/乱序、源硬删除、改关联、重算中再次写入、Worker 中断和补算后，结果与独立批量全量核对一致；依赖变化持续发生时，异步队列及最老待办不能无限增长。

选择 stored_sync 的依据是读侧收益足以覆盖实际写入和索引成本，且写入仍满足已有工作负载门槛；选择 stored_async 还必须有业务明确接受的端到端新鲜度和稳态吞吐。默认不设通用于所有公式的刷新秒数或额外 QPS 承诺。未知延迟容忍度时，不将影响约束、控制或实时决策的属性默认设为异步。

## 8. 分表的性能对照

分表的逻辑语义和候选范围由 [Schema](模块/Schema.md) 维护。使用相同总行数、字段、逻辑索引、请求和数据库资源，对比 single、已认证的 native_partitioned 和 sharded_tables；表数候选为 1/16/64，范围表另固定区间数量与冷热分布。先通过 SCHEMA-09～SCHEMA-14 中对应开放能力的检查，不能用每表少装数据、漏查成员或放宽唯一性换取分表收益。

| 对照负载 | 需要固定及测量的内容 |
| --- | --- |
| 按 ID 和完整分表键读取/更新 | 直接路由与定位目录的往返、缓存校验、锁及 P95/P99；验证不随表数逐次广播 |
| 时间/键范围与无分表条件查询 | 实际候选/访问成员、扫描行数、裁剪效果、跨表并发/内存/连接占用、取消及超预算拒绝 |
| 跨表分页、聚合及计算值筛选 | 与单表相同快照/结果对照，包含重复排序值、空表、全局 DISTINCT、加权 AVG 及深分页；记录合并与计算位置 |
| 写入、唯一性及普通/热点 Link | 相同事务和持久化语义，比较目录/唯一登记/索引/outbox 写放大、冲突、热点和端点定位，禁止逐边扫描全部表 |
| 新建范围、改桶数与搬迁 | 成员/索引创建、目录和计划失效、搬迁 IO、暂停及恢复时间；注入中断、旧 Pod 写入、旧异步结果和源拓扑漂移 |
| 关联属性来源、list/by_value 与按需建表 | 固定不同源对象/值数量和分布，记录批量取值往返、锁竞争、路由快照/定位成本、全局唯一登记及建表队列；源属性改变后查询不漏历史成员，冷热值突增及多 Pod 首写受配额约束，不重复建表或假报成功；准备中重试、源值变化及定义替换后结果可核对 |

hash 均匀、热门键倾斜、range 当前区间集中写和迟到数据分别测试；热点不会因为物理表变多而自然消失。记录表/索引及定位目录规模、计划缓存和预处理数量、目录读取与监控成本，验证增加 Pod 后所有副本路由一致，失败成员不被当作空结果。

同库分表仍共享数据库 CPU、IO、锁和连接预算，不能将表数乘以单表吞吐作为容量承诺。是否启用分表、选择何种键及成员数由实测访问形态和维护成本决定；跨库扩容另设事务、查询及迁移验收，不沿用本节结论。

## 9. DataSet 与多个 Link 的查询性能

查询抽象、结果模式及多跳执行边界由[数据查询目录](数据查询/README.md)的独立 [DataSet](数据查询/DataSet.md) 文档维护。本节只维护成本分析和后续测量方法，不构成当前性能结论。DataSet 延迟构造查询描述，是否高效取决于生成的实际计划、索引、数据分布和结果要求，不能将其等同于在内存加载全集后逐层遍历。

[OntologySQL](数据查询/OntologySQL.md) 建议作为同一引擎的文本前端，性能对照增加文本解析及降低到 QuerySpec 的独立耗时；同语义 SDK/JSON 可省去 SQL 词法/语法解析，但仍须通过相同绑定与校验。SQL JOIN 的重复行、EXISTS、DISTINCT 和聚合必须与对照入口选择相同结果语义，不能用去重实体页冒充同成本的扁平路径行。

### 多跳成本如何判断

成本至少分为中文名称解析/ID 绑定、当前定义/权限校验、计划编译、数据库扫描/关联、排序/去重/聚合、跨源或成员往返以及结果传输。中文名称在编译阶段按明确范围批量解析，不对结果逐行/逐边查名；已绑定计划仍校验当前定义及权限。同库固定路径优先比较 SQL JOIN/EXISTS 等计划，DataSet 本身不强制每个 Link 一次 HTTP 调用；名称绑定、编译和元数据解析开销仍须独立测量，不能宣称封装没有成本。

例如一条路径经过 10 条产线、每线 100 台设备、每台匹配 20 个工单，在未过滤且每个分支均匹配的示意条件下，可能形成 10 × 100 × 20 = 20,000 个路径匹配；这不是实测扫描量，同一设备或工单还可能重复出现。终点去重可以减少返回实体，却不自动消除中间工作。相反，多级 1:1 路径可能始终只有少量候选，不能只用“几跳”推算延迟。

| 查询形态 | 主要成本和候选处理 |
| --- | --- |
| 按具体对象查一跳邻居 | 起点/方向/上下文索引定位及终点批量读取，分别测试普通节点和热点节点 |
| 固定多跳、条件选择性强 | 保留每层条件和权限，选择合法驱动集合与 JOIN 顺序，尽量减少早期候选；“只返回有匹配关联的对象”优先比较 EXISTS/半连接 |
| 多跳 N:M 或 both | 中间路径可能显著增长，去重、排序与内存成本高；明确实体/边/路径结果，逐层计量匹配量，不能只记录最终行数 |
| 完整路径、精确总数和分组聚合 | 即使返回一页也可能处理大量输入；分开测量与终点实体页的成本，不将 page.limit 当扫描上限 |
| 分表、继承多具体表 | 每层成员裁剪、定位和全局合并会增加工作；与相同结果的单表基线比较，记录访问成员数 |
| 跨数据源 | 网络、批次、参数上限和不同读取快照增加成本；受控分阶段批量关联需要独立基线，不能沿用同库延迟目标 |

### 优化及超限处理

关系两端及上下文使用 Link 已声明的访问索引，常用实体筛选、排序和外键定位使用经执行计划验证的 Schema 索引。可下推的选择条件、投影和基本聚合尽量在数据库执行，但须保持单位、空值、每层权限和结果语义；对 SQL 无法下推的受支持计算或跨源步骤使用有界批量处理。不能先截断一层、先分页再计算筛选，或漏掉成员来降低成本。

编译计划可按当前 Schema/Link/映射、查询结构、权限和后端能力缓存，每次使用校验权威当前状态，参数仍逐次绑定；具体规则沿用存储引擎。结果缓存、热点路径物化、汇总表或专用图索引只在实测显示必要时另行选择，明确失效、重建、权限及新鲜度，不能默默把实时查询改为过期结果。增加 Data Pod 可分摊编译与请求处理，无法自动消除数据库扫描或高分支路径成本。

服务端预算须覆盖结构深度、中间候选/匹配行、访问成员、字节/内存、SQL 参数/往返和总耗时。预览能够估计的先拒绝，执行时仍需适配器超时/取消及资源约束；未知估计不等于无成本。每项计量的可观测性与执行中限制能力逐库验证，不能只在加载完中间结果后检查长度。同步预算不足时明确失败；后续若提供异步导出/分析，需独立任务契约，不能将部分结果当作完整查询。

### 后续对照与报告

| 对照维度 | 需要固定或分别统计的内容 |
| --- | --- |
| 查询编写入口 | 等价 OntologySQL、SDK/JSON 共享计划与参数化 SQL 基线分别报告；拆分文本解析、名称绑定、IR/物理编译、执行及解码耗时，并记录计划/参数和结果语义，不假定多一层编译必然更慢或完全无成本 |
| 中文名称与 ID 绑定 | 相同查询分别以中文名称和等价 ID 构造，核对绑定与底层计划语义；测名称索引/缓存冷暖及权威当前状态校验成本，包含改名、跨分类同名和同名重建，不增加逐行查名 |

| 物理位置 | 同库单表、同库分表/继承展开、已认证跨源组合分别报告；记录网络和事务/快照条件 |

| 预算及故障 | 构造小最终页但巨大中间集合、超时、取消及成员读取失败，核对资源释放、有界失败和其他租户的请求影响 |

每次报告 P50/P95/P99、成功率/超限率、实际 SQL 与执行计划、各层可取得的扫描/匹配/去重计数、临时磁盘与排序、数据库/应用 CPU/内存、返回字节、网络往返和连接等待。若为诊断使用 EXPLAIN ANALYZE 等实际执行工具，仅在授权的隔离验证中使用，不改变在线只读预览的边界。
