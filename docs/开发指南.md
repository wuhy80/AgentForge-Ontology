## 本地启动与停止

需要 Go 1.22+、PowerShell、运行中的 Docker Desktop 及 Docker Compose。在仓库根目录运行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-dev.ps1
```

上述命令仅为当前子进程指定脚本执行策略，不更改系统设置。脚本创建Metadata、Data、Execution三个隔离的MySQL开发库、OPA和本地Go服务，密钥保存在被忽略的`.cache/dev/secrets.json`。平台迁移先显式执行，成功后才启动服务；直接运行服务入口不会自动建平台表。重复启动复用本项目已经运行的进程，不重复生成凭据。Execution使用Docker运行Python、JavaScript和Go；启动脚本检查Python/Node镜像，缺失时显式拉取，每次按仓库源码构建默认Go专用镜像以更新可信启动器。镜像由部署方通过`ONTOLOGY_PYTHON_IMAGE`、`ONTOLOGY_JAVASCRIPT_IMAGE`、`ONTOLOGY_GO_IMAGE`配置；自定义Go镜像须预先准备，脚本只核验其存在。`-DependenciesOnly`仍只启动数据库/OPA。镜像默认值、构建操作及资源边界统一见[Execution](../services/execution/README.md)；普通服务入口和请求不自动下载或构建镜像，不降级到宿主解释器/编译器。

本次新增数据源配置及映射控制表迁移 `004`～`007`。更新已运行服务时先执行 `scripts/stop-dev.ps1`，再运行启动脚本重建并显式迁移；不删除既有模型或实例。脚本为已有本地密钥文件补充独立 `DataSourceKey`，传入 `ONTOLOGY_DATA_SOURCE_KEY`，不可随意重置。

外部 PostgreSQL 数据源验证可选运行 `scripts/start-dev.ps1 -DependenciesOnly -SourceDatabases`，启动独立的 `127.0.0.1:25432/ontology_sources`（用户 `ontology`）；密码由脚本保存在同一忽略文件的 `SourcePostgresPassword`，不要提交。默认启动不要求 PostgreSQL。两个平台控制库仍使用原 MySQL，不因新增外部源改变部署后端。

| --- | --- |
| `http://127.0.0.1:18080` | Metadata；`/healthz`、`/readyz` 为探针 |
| `http://127.0.0.1:18081` | Data；`/data/capabilities` 返回当前能力 |
| `http://127.0.0.1:18082` | Execution；`/execution/capabilities`按实际就绪情况返回语言及运行能力 |
| `http://127.0.0.1:18084/mcp` | MCP Streamable HTTP；受保护资源元数据和 OAuth 公开端点由同一服务提供 |

| `127.0.0.1:23306`、`127.0.0.1:23307`、`127.0.0.1:23308` | 分别为Metadata、Data、Execution的独立开发MySQL |
| `http://127.0.0.1:5173` | 单独启动的前端工作台，代理三个后端公开API |

启动脚本显式执行新增账号迁移，再以 `-bootstrap-admin` 初始化 `demo-tenant / admin`；随机初始密码仅保存于 `.cache/dev/admin.json`。重复启动或初始化不会重置已有账号、角色或权限。首次登录后可自行修改密码，文件中的初始密码不随账号改密自动更新；忘记密码由另一名租户管理员在页面重置。外部认证目录仍未接入。OPA 的管理接口仅作为环回开发工具，正常服务使用数据库中的当前用户/角色/策略生成动态授权输入，不使用示例静态主体授权作为回退。

停止应用进程或连同开发依赖一起停止：

本轮 MCP 新增 Metadata 身份迁移 `015`～`017`；更新已运行服务时先停止，再运行启动脚本显式迁移并重建。工作台“外部连接”可创建并撤销个人连接凭据，dsh 使用其安全凭据存储引用 Bearer；具备 OAuth 交互能力的客户端使用授权码 + PKCE。完整配置、受众与范围规则见[MCP 接入](MCP接入.md)和[MCP 服务](../services/mcp/README.md)。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\stop-dev.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\stop-dev.ps1 -Dependencies
```

停止脚本只处理记录的本项目二进制进程，保留数据库卷。无法读取进程路径时会明确失败并保留 PID 记录，应使用启动服务时相同的用户及权限运行；启动脚本也会核验记录的进程与新启动的二进制，避免仅因端口有响应就误报成功。日志在 `.cache/dev/*.stderr.log`。凭据文件与数据库卷应一起保留；已有卷不会因改变环境变量就自动更改数据库密码。

## 前端工作台

需要Node.js 22.12+或24；本轮实测Node.js 24.4.0。保持上述后端和OPA运行，在另一个终端启动前端：

```powershell
Set-Location apps/web
npm.cmd ci
npm.cmd run dev
```

访问`http://127.0.0.1:5173`，输入租户、用户名和密码登录。服务端设置HttpOnly、SameSite=Strict的随机会话cookie，数据库只保存会话摘要；密码经bcrypt保存，不在浏览器持久存储密码或可读会话凭证。刷新通过当前会话恢复，退出执行服务端注销；停用、重置密码及角色/管理员身份变化吊销旧会话。修改请求同时验证来源与CSRF。页面通过同源`/api/metadata`、`/api/data`、`/api/execution`代理访问公开接口，不接收服务凭据、签名密钥或数据库连接；生产HTTPS网关和外部认证仍需另行配置。

管理员进入“用户与权限”管理用户和角色，再以中文选择角色、操作、当前模型及属性，保存策略草稿、模拟并生效。草稿不影响当前访问；允许规则保留字段与行条件，拒绝规则只支持整个操作。不同字段集合或无法保持旧/新行条件配对的多角色组合明确拒绝。管理员身份只授予用户/策略管理权，业务访问仍需显式角色授权；初始管理员角色提供首批业务操作。具体边界统一见[权限设计](权限/权限设计.md)。

“用户组”页按组选择角色与成员，可创建、编辑、启用和停用。角色与成员列表支持搜索；用户列表分别显示直接角色、所在用户组及继承来源。组成员统一在用户组编辑器维护，编辑用户的直接角色不会覆盖组关系。调整组成员、角色或启停状态后，受影响成员须重新登录；仅改组名或说明保留会话。用户组不授予管理员身份，且独立于模型目录的业务分组；实际规则与预算见[用户组与有效角色](权限/权限设计.md#用户组与有效角色)。

先在独立的“分类与分组”页面创建分类和分组，再从工作台顶栏选择当前分类，进入“模型管理”以中文表单创建定义；表单固定当前分类，仅选择其下已有分组。概览、模型目录和数据探索共享这个分类，规则统一见[组织与隔离](组织与隔离.md#工作台当前分类2026-11-07-已确认)。Schema 新增属性先保存以取得稳定 ID，再选择属性配置索引；保存草稿后可预览和发布。草稿目录使用 `view=draft`，受 `definition.edit` 授权，与默认当前态目录分别读取；尚未发布的模型不会进入业务查询。已生效定义的结构控件锁定，允许保持 ID 的展示信息修改；发布结果不确定时保留原请求供恢复。

仅验证分类界面交互且保持开发库干净时，在 `apps/web` 执行 `npm.cmd run test:e2e -- category-context.spec.ts`；该用例使用浏览器内模拟接口，不读取本地账号或写数据库。`workspace.spec.ts` 仍是连接真实服务、创建验收资料的完整流程，按下述范围使用。

“数据探索”的实际交互与边界统一见[可视化查询编辑器](数据查询/可视化查询编辑器.md)。Link须先配置关系映射、保存并发布；现有租户管理员须在“用户与权限”中显式添加`link.query/create/delete`授权并生效，端点仍检查实例权限。具体模式及限制见[Link](模块/Link.md#当前关系数据库实现2026-11-07)。前端终端使用Ctrl+C停止；后端停止脚本不管理手工启动的Vite进程。

Function和直接源码Action在各自编辑页选择Python、JavaScript或Go实现，按声明的中文参数名编写入口；各语言的入口签名和示例统一见[Function](模块/Function.md#javascript与go扩展2026-11-08已确认)。源码编辑器提供对应语言高亮与本地参数补全，`Ctrl+Space`可显示候选；Python使用Ruff WASM，JavaScript使用本地Prettier Worker提供解析与格式化，Go显式检查/格式化须先保存草稿取得定义ID，再调用受编辑权保护的容器源码工具。静态检查不替代实际试运行。Action也可保留绑定输入输出一致Function的方式。普通运行使用当前生效定义，独立的草稿试运行须先保存并携带草稿ETag；未保存编辑不参与执行。已有租户须按[权限设计](权限/权限设计.md#首批纯计算调用2026-11-07已实现)显式配置相应调用权，草稿试运行另须编辑资格，编辑或绑定本身不授调用许可。当前仅纯计算，不支持联网AI请求或业务数据写回；测试样例和诊断边界见Function，实现选择见[Action](模块/Action.md)，服务操作见[Execution](../services/execution/README.md)。

```powershell

npm.cmd run build
# 先启动本项目后端与前端，再执行真实浏览器验证；默认使用本机 Microsoft Edge。

```

浏览器用例使用 `.cache/dev/admin.json` 中的本地账号和真实服务，在独立验收分类内创建模型与实例；用户权限和用户组用例另建随机账号、角色、用户组及权限规则，不修改既有规则。组验收在没有既有未生效草稿时追加自己的角色规则，存在草稿则明确失败，避免覆盖用户编辑。定义删除尚未开放，因此验收模型与授权资料会保留；测试只删除自己创建的实例。未配置本地账号文件时明确跳过。浏览器trace/video关闭，截图仅在登录完成后生成到 `.cache/frontend-verification/`，不归档密码。产物预览可用 `npm.cmd run preview`，但会话来源绑定 `ONTOLOGY_PUBLIC_ORIGIN`，使用4173时须相应配置并重启后端；生产静态站点仍需HTTPS与公开API网关。

## 创建、预览、生效及查询

以下示例对应本轮已实现协议，面向开发者。服务端分配定义与属性 ID，业务选择使用中文名称，不需要手工填写 UUID。

```powershell
$initial = Get-Content .cache/dev/admin.json -Raw -Encoding UTF8 | ConvertFrom-Json
$loginBody = @{ tenant=$initial.Tenant; username=$initial.Username; password=$initial.Password } | ConvertTo-Json
$webSession = New-Object Microsoft.PowerShell.Commands.WebRequestSession
$login = Invoke-RestMethod -WebSession $webSession -Method Post -Uri 'http://127.0.0.1:5173/api/metadata/auth/login' -ContentType 'application/json' -Headers @{Origin='http://127.0.0.1:5173'} -Body $loginBody
$headers = @{ Origin='http://127.0.0.1:5173'; 'X-CSRF-Token'=$login.csrfToken }
$contentType = 'application/json; charset=utf-8'
$category = Invoke-RestMethod -WebSession $webSession -Method Post -Uri 'http://127.0.0.1:5173/api/metadata/categories' -Headers $headers -ContentType $contentType -Body (@{name='生产管理'} | ConvertTo-Json)
$group = Invoke-RestMethod -WebSession $webSession -Method Post -Uri 'http://127.0.0.1:5173/api/metadata/groups' -Headers $headers -ContentType $contentType -Body (@{name='设备模型'; categoryId=$category.id} | ConvertTo-Json)

$definition = @{
    categoryId=$category.id; groupId=$group.id; kind='schema'; name='设备'
    schema=@{
        mode='schema_2_db'; storageLayout='single'
        properties=@(
            @{name='设备编码'; dataType='string'; required=$true},
            @{name='设备名称'; dataType='string'; required=$true}
        )
    }
}
$draft = Invoke-RestMethod -WebSession $webSession -Method Post -Uri 'http://127.0.0.1:5173/api/metadata/definitions' -Headers $headers -ContentType $contentType -Body ($definition | ConvertTo-Json -Depth 12)
$definitionUrl = "http://127.0.0.1:5173/api/metadata/definitions/$($draft.definition.id)"
$preview = Invoke-RestMethod -WebSession $webSession -Method Post -Uri "$definitionUrl/preview" -Headers $headers
$publishHeaders = @{ Origin='http://127.0.0.1:5173'; 'X-CSRF-Token'=$login.csrfToken; 'If-Match'=('"' + $draft.etag + '"') }
$publication = Invoke-RestMethod -WebSession $webSession -Method Post -Uri "$definitionUrl/publish" -Headers $publishHeaders

$values = @{}
foreach ($property in $draft.definition.schema.properties) {
    if ($property.name -eq '设备编码') { $values[$property.id] = 'PUMP-001' }
    if ($property.name -eq '设备名称') { $values[$property.id] = '输送泵' }
}
$instanceUrl = "http://127.0.0.1:5173/api/data/schemas/$($draft.definition.id)/instances"
$instance = Invoke-RestMethod -WebSession $webSession -Method Post -Uri $instanceUrl -Headers $headers -ContentType $contentType -Body (@{values=$values; idempotencyKey=[guid]::NewGuid().ToString()} | ConvertTo-Json -Depth 12)

$query = @{
    from=@{category='生产管理'; schema='设备'}
    select=@('设备编码','设备名称')
    where=@{op='startsWith'; field='设备编码'; value='PUMP-'}
    orderBy=@(@{field='设备编码'; direction='asc'})
    page=@{limit=50}
}
$result = Invoke-RestMethod -WebSession $webSession -Method Post -Uri 'http://127.0.0.1:5173/api/data/query' -Headers $headers -ContentType $contentType -Body ($query | ConvertTo-Json -Depth 12)
$result
```

分类与定义示例只需创建一次；重复执行时应按真实名称唯一性处理冲突。PATCH/删除需要实例当前 `ETag` 对应的带引号 `If-Match`，不能用定义 ETag 替代。新请求读取当前定义；发布失败时按同一草稿 ETag 重试原发布，不能通过普通 CRUD 绕过暂停状态。详细路由与错误码见所属服务 README。
