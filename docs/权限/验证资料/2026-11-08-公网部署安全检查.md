## 已复现的问题

### SEC-01：限流机制可以阻断正常登录

登录键由租户、归一化用户名和 `RemoteAddr` 的 IP 组合而成。当前 Nginx 经回环连接后端，所有浏览器的后端对端地址都是 `127.0.0.1`，转发的客户端地址没有参与限流。攻击者对已知账号提交五次失败尝试，会占用其他访问者对该账号的同一限流键。

更直接的问题是全服务仅允许 1024 个活动登录键；填满后，任何新键都会收到 429，持续到现有窗口过期，窗口为 15 分钟。计数发生在身份校验之前，不要求账号或租户真实存在。本地直接调用限流器，填入 1024 个不同账号键后，无关合法用户的新键被拒绝；模拟不同浏览器 IP、同一回环代理连接，计算出的同账号限流键相同。

建议在可信入口配置独立的请求频率和连接预算，并采用同时受 IP、账号和总服务预算约束的限流方式。总容量达到上限时应限制攻击来源，避免冻结所有新用户。若识别代理后的 IP，必须限定可信代理并由入口覆盖客户端提交的地址头，不能直接信任任意 `X-Forwarded-For`。多副本下还需共享或协调限流状态。

### SEC-02：匿名注册可无限产生持久记录

`POST /oauth/register` 是公开接口，每个有效请求都向 `af_identity_oauth_clients` 插入记录，有效期为 365 天。入口无 `limit_req` 或注册专属配额，处理器没有总量限制，仓库中也没有对应的过期清理逻辑。仅设置 `expires_at` 不会释放存储空间。

使用实现 `database/sql/driver` 的内存桩连续提交 1050 次合法匿名注册，同一来源全部返回 201，桩收到 1050 次 INSERT。该复现未连接真实数据库，也未对公网发送注册请求。

建议给注册、授权码交换和撤销接口分别设置频率与并发预算；动态注册增加全局存储上限和过期清理。若当前实际客户端不依赖匿名动态注册，可在明确兼容需求后采用预注册或受控注册。具体方案待实现，不能将本建议表述为接口已经关闭。

### SEC-03：合法 HTTPS 登录在回源后被误拒绝

复现条件与仓库 Nginx 配置相同：公开 Host 为 `47.100.85.94:30011`，浏览器 `Origin` 为 `https://47.100.85.94:30011`，后端收到普通 HTTP 请求和 `X-Forwarded-Proto: https`，因此 `r.TLS == nil`。向 `ProtectSessionRoutes` 提交登录请求，实际返回 `403 invalid_origin`，登录处理器未被调用。

这是来源校验与部署方式不兼容的可用性阻塞，本次没有发现借此绕过认证的路径。检查过程中工作区新增 `78247b4`，通过 `TrustTLSProxy` 仅认可明确CIDR内的实际对端和单一HTTPS协议头，保留来源、Host和CSRF校验。已复核实现，并重跑Platform全模块测试，包含真实本地TLS代理后的登录/查询处理器及伪造头、重复头、不可信对端、错误CSRF等回归，均通过。

本项更新为“代码已修复，线上待验证”。三个浏览器会话后端仍需显式配置 `ONTOLOGY_TRUSTED_PROXY_CIDRS`；单机配置要求见[部署与运维](../../部署与运维.md)。本次没有确认服务器已加载该提交和环境配置；最终回归应覆盖TLS代理后的真实登录、改密、查询、草稿执行和OAuth同意。不能通过删除来源检查或直接信任任意客户端转发头解决。

### SEC-05～07：密码、数据库目的地及 TLS 默认值

本地调用密码校验器，`123456` 被接受。bcrypt 存储本身已有实现，但不能补足密码强度；建议提高长度下限并拒绝常见弱口令，评估已有账户及管理员的升级方式。

本地数据源配置校验接受 `127.0.0.1`、`::1`、`10.0.0.1`、`169.254.169.254` 以及外部域名，端口可取 22，省略 TLS 时结果为 `disable`。该复现只验证配置接受情况，没有连接这些地址。连接器随后直接使用配置中的目的地；尚无平台层的目的地允许范围或连接时 IP 核验。

这一能力只对当前租户管理员开放，不能表述为匿名任意 HTTP SSRF，也没有证据表明已读取云元数据或跨租户数据。对于平台不完全信任的租户管理员，现有实现仍提供了从服务网络发起数据库协议连接的能力。建议由部署方配置可连接的数据库范围，连接时验证实际解析地址并配合网络出口控制；本机业务库可显式放行，不能简单禁用所有内网地址而破坏已有场景。

跨公网数据源建议默认使用 `verify-full`，显式区分传输加密和服务器身份验证；`require` 当前映射 MySQL `skip-verify`，不等于验证了服务器证书。回环或受控网络中关闭 TLS 的场景应保留明确的配置边界。

## 执行隔离与入口加固

SEC-04 的已实现措施包括每次独立容器、非 root、禁网、只读根文件系统、无宿主挂载及平台凭据、移除 capabilities、资源与时限限制，以及失败清理确认。没有发现请求可以自选宿主命令、挂载或 Docker 安全选项的入口。

但是，普通容器仍共享宿主内核，且部署脚本将 Execution 服务用户加入宿主 `docker` 组；该组对 Docker daemon 的权限通常等价于宿主 root。systemd 的 `NoNewPrivileges` 等限制不能约束 daemon 代为创建的任意容器。如果 Execution 服务被攻破，宿主权限影响很大。本次没有演示容器逃逸或宿主代码执行。

按当前[Function 隔离边界](../../模块/Function.md)，这仍是面向受控代码的首批措施。若公开产品允许不可信用户编写代码，建议先将执行环境与持有数据库、密钥的应用宿主分离，采用权限受限的运行代理及更强隔离运行时，并补充恶意代码、资源耗尽及回收验证。未落实前，不宜对不可信租户开放源码编辑与执行。

SEC-08：Nginx 没有配置 CSP `frame-ancestors` 或 `X-Frame-Options`，拥有会话的页面存在被嵌入后诱导点击管理操作或 OAuth 同意的风险。`SameSite=Strict` 不替代防嵌入策略。建议在文档响应配置 `frame-ancestors 'none'` 或业务明确的可信父页面，并落实 `X-Frame-Options`、`Referrer-Policy` 和适配现有 WASM/Worker 编辑器的 CSP。增加头时要检查 Nginx 的继承规则：`/` 和 `/assets/` 自己声明了 `add_header`，在常见默认配置下不再继承 server 级 `add_header`，所以 server 处单独增加安全头并不足够。

SEC-10：自签证书若经过可信渠道预先安装和核对，仍可提供身份验证；直接让公网用户忽略证书警告不应成为登录流程。公开用户及 MCP/OAuth 客户端需要可验证的证书信任和续期安排。本项依据仓库部署记录，线上实际证书未核实。
