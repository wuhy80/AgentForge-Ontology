## 原问题与修复前复现

### OA-01（P1）：登录计数不跨实例共享

位置：[登录预算](../../../services/metadata/identity/throttle.go)第 17、40、61 行，[Store](../../../services/metadata/identity/store.go)第 30 行。

登录键含租户、规范化账号及可信来源 IP，但计数和来源/总请求预算均在 Store 内存。隔离探针创建两个 Store：第一个相同键前五次获准，第六次拒绝；第二个相同键仍获准。重启或切换副本可获得新的预算。此结论不等于会话也只存内存；会话实际保存在 MySQL。

待处理：使用共享存储原子计数或其他能证明跨副本一致的限制机制，并覆盖重启、切换副本、两个公开前缀及并发失败。阈值、窗口、恢复和共享存储不可用时的行为由权限主说明维护。单实例两个别名若进入同一 Store，按当前键计算会共用计数；现有网关尚未配置该别名，不能据此宣称联合入口已验收。

### OA-02（P1，内部凭据已知时影响更大）：公开网关缺少请求边界

位置：[Nginx](../../../deploy/single-host/nginx.conf)第 27～43 行，[服务读取例外](../../../libs/platform/session.go)第 197 行，[Metadata 包装器](../../../services/metadata/handler.go)第 84 行。

当前网关按 `/api/metadata/`、`/api/data/`、`/api/execution/` 整个前缀回源，未实现请求头与方法白名单。使用仓库 Nginx 配置和容器内合成回显上游，确认客户端的 `Authorization`、`X-Tenant-ID` 被透传；`DELETE /api/data/query` 也被转发。正式 Data 路由自身会拒绝不支持的方法，回显返回 204 仅用于证明网关没有拦截。

Metadata 对精确的定义/草稿读取和 resolve 路由保留服务令牌读取通道；合法服务 Bearer 可以在没有 Cookie 时进入该通道，再由 `X-Tenant-ID` 选择内部读取租户。使用至少 32 字节的合成服务密钥已确认入口行为。**这需要有效内部密钥，不是任意伪造身份头即可越权，本轮也未发现密钥泄漏。** 但按清单，公网入口应剥离这类内部身份，不能仅依靠 `/internal/` 返回 404。

待处理：按公开协议列出路径、方法及必要请求头；工作台、OAuth、MCP、执行等分别补齐自己的公开集合。普通浏览器路由剥离服务 Authorization 和身份头；MCP/OAuth 所需公开凭据按路由保留，不能简单删除全部 Authorization。后续可将内部定义读取迁至专门内部路由，进一步分离信任边界。

### OA-03（P1）：Data 缺少服务级并发与返回字节预算

位置：[Data 请求与编码](../../../services/data/handler.go)第 82、88、120 行，[查询结果积累](../../../services/data/instances.go)第 517、579 行，[正文上限](../../../contracts/limits.go)，[服务内存预算](../../../deploy/single-host/agentforge-ontology@.service)第 28 行。

已有 15 秒请求 context、8 MiB 输入上限和最多 100 行分页，但结果在内存积累后直接 JSON 编码，没有总响应字节封顶，也没有 Data 服务级并发准入。网关按 IP 的连接限制、数据库连接池和 SQL context 不能替代这些预算。单个 longtext 可达 4 MiB；例如 100 行各含 2 MiB 可读正文，原值就约 200 MiB，已经超过模板 160M 的单服务内存预算，尚未计入其他分配。没有执行 OOM 或公网压力测试。

待处理：在结果积累阶段计入响应预算，达到上限时返回受控 JSON 错误或按明确协议分页；在昂贵操作前设置服务级并发及有界排队。超时需验证实际后端取消与回收，不把设置 context 当作超时压力验收；过载和超时避免返回网关 HTML 或截断 JSON。

### OA-04（P2）：Nginx 默认访问日志包含查询串

位置：[Nginx 配置](../../../deploy/single-host/nginx.conf)，该文件未覆盖访问/错误日志格式。

本地实际 Nginx 容器沿用默认 combined 日志，对合成请求 `?review_marker=SYNTHETIC_URL_ONLY` 的日志包含完整查询串。OAuth code/state 或业务查询参数进入 URL 时可能被同样记录。没有使用真实凭据或业务内容验证。此证据不表示默认日志也记录 Cookie 或请求正文。

待处理：使用仅含必要事件信息的日志格式，不记录完整请求行、args、鉴权头和正文；控制错误日志中可能附带的请求/upstream 内容。核对网关请求/响应缓冲临时文件及留存，当前未禁止代理响应临时文件。应用已有管理审计，仍需核验登录、鉴权、查询、创建安全事件，以及 APM、追踪、数据库慢查询采集的脱敏配置。

### OA-05（P2）：合法目录超过 OntoApp 字节预算，目录游标未绑定上下文

位置：[查询目录](../../../services/data/ontology_sql_http.go)第 289、393、422、536 行。

使用 50 个合法 Schema，各含 100 个可读 text 属性，属性名为 125 个汉字加三位序号，总长 128 字符；每个 Schema 均通过现有 `validateSchema`。模拟 Metadata 上游与授权，调用真实 Data HTTP handler：上游定义列表为 **2,353,226 字节**，低于 Data 的 4 MiB 上游读取预算；目录 HTTP 200，正文 **2,521,413 字节**，超过 OntoApp 单页 1 MiB。该客户端会拒绝这份完整响应，不能靠减少字段来静默适配。这是合法上界样例，不是实际业务目录的规模或性能测量。

另有两项协议差异：Data 每批拉取最多 100 份完整 definition，上游超过 4 MiB 会报 `metadata_unavailable`，不会自动缩小批次；目录逐模型授权，整体 context 为 15 秒，不能保证满足 OntoApp 单次 5 秒及目录阶段 15 秒预算。代表性真实目录的大小与延迟仍待实测。

目录 nextCursor 直接使用最后一个 Schema ID，未签名或绑定当前用户、查询上下文。每页会按当前权限重新读取与授权，因此本轮未发现利用它扩大访问范围；它与已有签名并绑定上下文的**业务数据游标**不同，不能将业务游标测试结果用于证明目录游标满足同一要求。

待处理：双方确定目录按字节分页/单模型字段分页或明确调整预算，覆盖单个大模型、Metadata 批次、累计 4 MiB、100 页及时延边界；目录游标按清单统一约束或明确记录协议例外。

### OA-06（P2，授权语义差异）：表单接口读取整份 definition

位置：[完整定义响应](../../../services/metadata/handler.go)第 401 行，现有边界见[权限设计](../权限设计.md)“当前实现协议”。

`definition.read` 当前授予整份定义读取，接口不会按 `instance.query` 的 ReadFields 裁剪属性、映射及默认值等定义内容。查询目录则按可读字段输出安全摘要。因而一个拥有 definition.read、但实例查询仅允许部分字段的用户，仍可在直接读取 definition 时看到其他属性的元数据。

这是已明确的整定义权限语义，不能称为隐藏字段原值泄漏或无授权读数据；没有 definition.read 的定义读取仍被拒绝。但它与 OntoApp“按当前用户权限返回表单所需 definition”的最小发现要求不一致，不能仅验证目录裁剪就判定本项通过。

待处理：优先设计只返回当前可见/可写字段的表单发现协议，避免向普通业务用户授整定义读取；或双方明确该公开接口要求整定义可见的角色范围。不能直接裁剪管理工作台共用响应，造成编辑器丢字段或破坏既有绑定。

### OA-07（P2）：格式错误的同名 Cookie 被解析器丢弃

位置：[公共会话提取](../../../libs/platform/session.go)第 103 行，[身份模块会话提取](../../../services/metadata/identity/sessions.go)第 178 行。

两处均对 Go `r.Cookies()` 解析后的结果计数。普通重复、空值或格式不合法的单一会话会被拒绝；但在有效 Cookie 后加 `; ontology_session=bad\value` 或 `; ontology_session="unclosed`，解析器会丢弃第二项，代码仍看到一个有效会话。

公共提取探针确认这两种形式被接受；隔离 MySQL 中，合法登录后向真实身份 handler 提交第二种形式，`GET /metadata/auth/session` 返回 200。该问题需要原有有效会话，不能据此伪造会话或越权；它不满足清单明确要求的异常/重复拒绝。

待处理：公共层与身份层统一检查原始 Cookie 头中的同名项及解析错误，覆盖多个 Cookie 头、空值、引号、非法字符及普通重复，防止两项目解析结果不一致。当前只有 8 小时绝对到期，没有独立空闲超时；空闲策略还需在接入验收中明确，不能将持续访问误写为自动续期。

### OA-08（P2）：两项目网关模板尚不兼容

Ontology 当前模板对 `/ontoapp/` 与 `/api/ontoapp...` 返回 503，后者也覆盖 `/api/ontoapp-ontology/...`。实际 Nginx 探针确认专用目录别名返回 503，当前模板不是两应用联合入口。

OntoApp 模板设置 X-Forwarded-For 和 X-Forwarded-Proto，但未设置 X-Real-IP。Ontology 的 [ClientAddress / TrustTLSProxy](../../../libs/platform/proxy.go)只从明确可信 TCP 代理采纳单一有效 X-Real-IP。探针确认：同一可信回环代理仅提供 XFF 时，后端看到 `127.0.0.1`；补上覆盖后的 X-Real-IP 才看到对应客户端地址。联合网关缺此头会再次合并后端登录计数，不能靠放宽为信任任意 XFF 解决。

OntoApp 模板的 `Host $host` 在非默认公开端口下会丢端口。如果沿用 Ontology 的 30011，浏览器 Origin 含 `:30011`，后端 Host 不含时会被精确来源校验拒绝；使用标准 443 时不触发这一差异。共同网关必须保留完整权威主机及端口，同时验证允许的 Host。

待处理：形成一份实际联合网关配置，保留真实 Origin，覆盖可信 IP/协议头、完整 Host、两个 API 别名及共享预算；逐项增加 Ontology 工作台必需路由与 CSP，不能把 OntoApp 独立模板直接当作整个 Ontology 工作台模板使用。

## 回传OntoApp的接入约定

1. 使用共同网关的 `/api/ontoapp-ontology/metadata/*`、`/data/*` 别名；现有客户端在配置Ontology来源时会使用此别名。登录/会话/查询/创建/修改/删除沿用公开Cookie协议，不提供内部密钥。主来源的完整定义路径仍属于显式整定义权限，普通业务用户应走表单别名。
2. 表单别名默认create；编辑操作须显式 `?operation=patch`，可用createAllowed/patchAllowed显示操作能力。最小发现不返回私有默认值，客户端不能再依赖完整definition中的default判断所有必填例外；实际创建/更新继续由服务端校验，缺隐藏必填的错误不回显隐藏字段名。
3. 目录保持limit 1～50，同时按1MiB完整模型分页；必须继续读nextCursor，不能假定每页恰好limit个模型。游标不透明，查询条件或limit变化后从第一页重读。累计4MiB/100页和客户端目录阶段15秒限制仍由OntoApp执行，超过时明确拒绝，不能截断字段或当作完整目录。
4. 使用本仓库联合网关配置，或等效落实X-Real-IP、含非默认端口的Host、原始Origin、请求白名单及表单别名映射。OntoApp原独立Nginx模板尚未同步，本轮没有改动另一仓库；不能直接覆盖共同工作台配置。正式环境仍须提供可信HTTPS及受控回环/网络。
