# 执行与调度设计

状态：设计草案，尚未确定首批语言、消息设施及完整状态机。对应 [CORE-06](../需求文档/本体建模与查询需求.md)、[RUN-01～05、TRG-01～02](../需求文档/执行与触发需求.md)、[SCALE-04～06](../需求文档/横向扩展与可靠性需求.md) 和 [PERF-03](../需求文档/性能与容量需求.md)。

## 1. 定义与运行器

Metadata 管理 Action/Function 定义，Execution 管理调用、执行记录、分派及事件订阅，Worker 执行具体代码。建议 Function 默认处理查询与计算，Action 表达业务效果并可调用 Function；权限、副作用和重试条件通过清单明确，不根据名称推断。

建议统一运行清单包含语言、运行时版本、入口、输入输出、依赖、制品版本、超时和资源要求。可用的实现方式如下，首期不要求同时实现全部方式或语言。

| 方式 | 执行方式 |
| --- | --- |
| 脚本包 | Python、JavaScript 等运行器加载版本化代码及依赖 |
| 容器 | 按约定入口与协议执行 Go 等编译语言或带专有依赖的实现 |
| 外部服务 | 通过 HTTP/gRPC 调用已有计算服务 |

运行器按统一协议扩展。平台服务采用 Go 不限制用户 Function 的语言。制品与依赖版本应固定，缓存按版本隔离；大型输入输出优先传递引用，保留执行记录与实际制品之间的对应关系。

根据代码可信程度设置 CPU、内存、时间、文件及网络权限，业务凭据按调用身份提供，隔离任务工作目录。容器运行不等于完整沙盒，所需隔离强度仍需根据代码来源确定。

## 2. 调用、状态与通知

同步与异步调用共用执行记录、权限和版本逻辑，返回行为定义于 [执行与触发需求](../需求文档/执行与触发需求.md)。Execution 持久化任务及待分派记录后确认受理，同步或限时等待模式在请求时限内等待同一任务的结果。

建议记录调用者、定义版本、输入、状态、结果、错误、尝试次数、时间和幂等键。状态候选包括 `queued`、`running`、`succeeded`、`failed`、`cancelled`，另行记录超时原因、重试状态和各次尝试。外部效果不明时需要待核对状态或标记，其具体表示及转换尚待确定，不能直接标为可重试失败。

请求超时不自动意味着执行取消；取消也不能撤销已经产生的业务效果。需要明确请求等待超时、运行超时、取消请求和最终状态之间的关系。同步时限由耗时分布与超时预算决定，不采用统一的 100 ms 切分规则。

任务查询提供权威结果。SSE、Webhook 可作为通知扩展；通知可能重复、延迟或失败。Webhook 需定义鉴权、重试及重复处理，结果保留和通知协议在具体接口设计时确定。

## 3. 任务分派与故障恢复

Worker 从持久任务源领取带租约的执行尝试，通过任务 ID 和尝试标识提交结果。Execution 拒绝过期尝试覆盖新结果，缩容时先停止领取新任务，再有界等待退出；未完成任务由恢复逻辑处理。

消息与任务采用至少一次处理，使用幂等键处理客户端重试及重复投递。平台租约只能限制平台状态写入，外部系统仍需接收方幂等或结果核对，不能因消息已确认就承诺端到端恰好执行一次。跨系统不默认有原子事务，部分成功需定义补偿；效果不明时先核对，不能直接重复执行。

任务成功受理、分派、运行、结果提交与确认之间的故障窗口均需验证。Worker 池按语言和资源类别独立部署，长任务、外部接口调用及 CPU 密集任务分别评估并发与扩容信号。

## 4. 事件触发

Metadata 负责模型事件，Data 负责实例与关系事件。建议用事务 outbox，在业务变更的同一个事务中持久化待发事件，提交后再异步投递至 Execution 的订阅分派模块。

事件至少携带事件 ID、类型、对象、定义版本、时间和追踪信息。订阅按事件类型、对象和条件匹配指定版本的 Action/Function；消费者按事件与订阅标识去重。需要定义重试、死信及必要的对象级顺序，不能把任意重放等同于重新执行业务动作。

触发链需限制递归及循环，重放是否再次触发、是否保留原定义版本应显式约定。重复投递与产生新业务操作的主动重放需要可区分的语义，具体标识协议仍待设计。

## 5. 周期触发

Scheduler 持久化 CRON 等规则，规则应包括表达式格式、时区、启停、错过周期处理、重叠执行和积压策略。选主或租约用于副本协调，吞吐需要时再考虑分片。

同一时间点用 `(schedule_id, scheduled_at)` 唯一登记待触发任务，登记及待发送记录在同一事务内持久化，再通过 outbox 重试提交 Execution。Execution 使用同一触发键去重，覆盖“已登记未发出”和“已发出未确认”两种窗口。唯一约束与任务幂等共同保证逻辑任务不重复，外部效果仍由接收方幂等及核对处理。

## 6. 基础设施与待定事项

持久化任务及 outbox 可先使用所属服务数据库。Kafka、RabbitMQ、NATS 属于不同特性的消息设施候选，Temporal 是工作流编排候选；这些工具职责不同，不要求同时引入。是否需要独立消息系统或工作流引擎，按任务持久性、吞吐和多步骤编排需求判断。

还需确定首批语言、代码可信度、脚本/容器优先级、依赖构建与分发、运行器协议、完整状态机、租约与重试规则、取消和补偿协议、幂等保留期、事件顺序与重放语义、CRON 语法/时区、结果保留和通知方式。性能数值只在 [性能与容量需求](../需求文档/性能与容量需求.md) 中维护。
