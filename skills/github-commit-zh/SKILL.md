# GitHub 中文提交

使用中文与用户沟通，提交信息的摘要、正文和破坏性变更说明均使用中文。保留 Git 命令、Conventional Commits 关键字、代码标识符和必要的技术名称。

## 判断执行范围

- “生成提交信息”“写一个 message”：检查改动并输出可直接使用的提交信息。
- “提交代码”“创建 commit”：完成本地提交；只有用户也要求推送时才推送。
- “提交到 GitHub”“提交并推送”：完成检查、本地提交和推送，已有授权无需重复确认。
- 已有符合任务范围的提交时，直接按请求推送，避免创建空提交。
- 创建 PR、合并 PR、发布版本按用户实际请求执行，不从普通推送请求推断这些操作。

## 确定仓库规范与改动范围

1. 阅读适用的 `AGENTS.md`、`CONTRIBUTING*`、提交规范，以及项目已有的 commitlint、提交钩子或其他提交校验配置；查看近期提交以了解惯例。硬性规范优先于本 skill 的默认格式，近期历史仅作参考。若硬性规则与中文要求无法同时满足，指出具体冲突并向用户确认取舍，同时继续其他不受影响的准备工作。
2. 检查 `git status --short`、`git diff`、`git diff --cached` 和相关未跟踪文件。根据用户指定范围与实际 diff 决定提交内容；仅暂存本次任务涉及的文件或代码块，避免无差别执行 `git add .` 或 `git add -A`。
3. 若暂存区包含明确无关的改动，先生成本次任务的 message，并说明具体文件、确认提交范围后再 commit；不要擅自重置暂存区或覆盖他人改动。没有可提交的改动时如实说明。
4. 多个相互独立的目的适合分别提交；相互依赖的实现、测试和必要文档可以放在同一提交中。不要为了拆分而重写已有提交。

## 默认提交信息格式

没有仓库硬性规范时，采用 Conventional Commits：

```text
type(scope): 中文摘要
```

- `scope` 可省略；需要时使用项目已有模块名，不凭空添加模块。
- `type` 使用标准英文关键字：`feat` 新功能、`fix` 修复、`docs` 文档、`style` 格式、`refactor` 重构、`perf` 性能、`test` 测试、`build` 构建或依赖、`ci` 持续集成、`chore` 其他维护、`revert` 回退。
- 冒号使用半角 `:`，后跟一个空格。摘要使用“增加”“修复”“补充”“移除”等中文动词，明确对象和效果，避免“更新代码”“修改文件”等空泛描述，末尾不加句号。
- 标题默认不超过 72 个 Unicode 字符，包含类型和范围；仓库另有限制时遵守其限制。
- 仅在需要解释原因、行为变化或迁移方式时添加正文，正文与标题之间空一行。正文用中文，只描述此次提交实际包含的内容。
- 破坏兼容性时在类型或范围后加 `!`，并添加 `BREAKING CHANGE: 中文影响和迁移说明`，与正文之间空一行。
- Issue 关联使用仓库支持的 footer，例如 `Refs: #123`。只有确认本次提交会解决对应 Issue 时才使用 `Closes: #123`；编号必须来自已知上下文。
- 不虚构功能、测试结果、性能收益、Issue 编号或协作者信息，不擅自添加签名或 `Co-authored-by`。

示例：

```text
feat(auth): 增加短信验证码登录
```

```text
fix(storage): 修复空索引查询导致的异常
```

```text
docs: 补充本地启动步骤
```

```text
refactor(api)!: 统一分页响应字段

BREAKING CHANGE: 将分页总数字段由 count 调整为 total，调用方需更新字段映射
```

## 提交与推送

1. 按仓库要求运行与改动相关的检查；纯文档等改动只运行适用的检查。如无法运行，说明原因，不声称通过。提交前检查暂存内容和 `git diff --cached --check`，根据最终暂存 diff 确定 message。
2. 若存在仓库提供的 message 校验命令，使用该命令检查完整 message。确保标题格式、中文摘要和实际改动一致；不得绕过提交钩子或使用 `--no-verify`。
3. 将完整提交信息写入工作区以外的 UTF-8 临时文件，使用 `git commit -F <临时文件路径>`，避免 shell 展开反引号、变量或命令替换。保留用户已有的签名配置。提交后通过 `git log -1` 和 `git status --short` 确认结果。
4. 推送前检查当前分支、upstream 和远程地址，复用已明确的目标；没有 upstream 时，向已确认的远程同名分支推送并设置 upstream，不硬编码 `main`、`master` 或远程名。多个目标无法可靠判断时，只询问缺失的远程或分支信息。
5. 不擅自强制推送、改写历史或更改全局 Git 配置。遇到远程拒绝、认证失败或钩子失败，先诊断；可在原任务范围内修复并重试，若需要额外权限或无法安全解决，报告具体阻碍并保留已完成的结果。
6. 推送成功后核对远程分支是否包含刚提交的 SHA。推送失败时明确区分“本地提交成功”和“远程推送失败”。

## 结果反馈

只生成 message 时，输出一个包含完整提交信息的代码块；确有多个独立提交时分别给出。执行提交后，用中文简要报告 message、短 SHA、分支、检查结果和推送状态；仅在已知时给出 GitHub 链接。
